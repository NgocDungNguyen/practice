🛒RMIT Store: Manual Deploy (A–E)

Do the Assignment 2 pipeline the right way — by hand first. This follows the repo README's own Plan A–E exactly, taking the Django + Vue store from your laptop to Docker Compose. It stops at Plan E: Plan F (Jenkins, Ansible, CloudFormation, Kubernetes) is the automation pipeline — a separate job for later.

7 sections78 code blocks~69 min

🎯 The route: A to E, one plan at a time

  1. ARun it locally💻 laptop
  2. BOne EC2, by hand☁️ one box
  3. CSplit across servers🐍 api · 🌐 web · RDS · S3
  4. DContainerise🐳 two images
  5. EDocker Compose🧱 one file
  6. FAutomatelater — not this guide

The golden rule

The assignment says it plainly: do not automate a process you do not yet understand. Each step is something a pipeline will later do for you — you do it by hand once first, so you know what "good" looks like.

A  Run it locally             # on your laptop
B  Deploy to one EC2 by hand  # the whole app on one AWS box
C  Split across servers       # DB / API / frontend apart, + S3, + RDS
D  Containerise with Docker   # images; no Node in prod
E  Docker Compose             # one file describes all three tiers

Then stop. Plan F (Jenkins, Ansible, CloudFormation, Kubernetes, monitoring) is the automation pipeline — later.

The three tiers

Three things you can deploy independently. Remember the ports — each one becomes a security-group rule or a container port later.

Frontend  Vue 3 (Vite)   -> static files   (nginx, port 80)
Backend   Django + DRF   -> gunicorn        (port 8000)
Database  PostgreSQL     -> stateful        (port 5432)
Images    uploads        -> local disk / S3 (Plan C)

Repo: github.com/TomHuynhSG/COSC2767-RMIT-Store-Django-Vue — read its README. This guide uses the same Plan A–E letters, so an instruction that says "Plan C" means the same thing here.

How to read the steps

Every step carries a badge that says which machine you are typing on. When the badge changes, change terminals.

  • 💻 laptop your own machine
  • 🧭 AWS console clicking in the browser, no terminal
  • ☁️ ec2 the single Plan B instance, over SSH
  • 🐍 api-server the Django box (Plans C–E)
  • 🌐 frontend-server the nginx box (Plans C–D)

A second tag says what kind of step it is: run type commands, new file create a file, edit file change one, check prove it worked.

The two ideas that make the whole thing work. (1) The frontend reads its API URL from client/public/config.js at page load, not at build time — so one built artifact deploys everywhere, you just edit a text file. (2) python manage.py migrate is a deploy step — it must run, in order, before new code serves traffic. Keep both in mind from Plan A; Plans C, D and E are mostly about honouring them across more machines.

Where the letters lead. A–B run the whole app on one box. C is the first time it lives on more than one machine — which is exactly when uploaded images break and you need S3. D and E are about packaging so that "more than one machine" stops being a manual chore. Plan F automates all of it.

🖥️ Plan A — Run it locally

GoalThe store runs on your laptop with real product images, and you have seen the built artifact — not just the dev server.
Where💻 laptop only. Two terminals by the end.
Steps8 · about 30 minutes
  1. A1

    Install the runtimes

    💻 laptoprun

    You need three things. Install them, then prove they are on your PATH.

    # Python 3.11+, Node 20+, PostgreSQL 14+
# macOS Postgres: brew install postgresql@16 && brew services start postgresql@16
python3 --version
node --version
psql --version

    Use when: a fresh machine. If any command errors, fix that before going on.

  2. A2

    Get the code

    💻 laptoprun

    Clone your team's fork of the repo and step into it.

    git clone <your-repository-url>
cd COSC2767-RMIT-Store-Django-Vue

    Use when: the very start. Use your team's fork — you need push access for the pipeline later.

  3. A3

    Create the database

    💻 laptoprun

    Make a role and a database for the app. macOS/Homebrew can run psql directly.

    # macOS (Homebrew)
psql -d postgres -c "CREATE ROLE rmit LOGIN PASSWORD 'rmit' CREATEDB;"
psql -d postgres -c "CREATE DATABASE rmit_store OWNER rmit;"

# Linux: prefix both with  sudo -u postgres
psql -U rmit -d rmit_store -c "SELECT version();"

    Use when: once per machine. If SELECT version() works, Django will connect.

  4. A4

    Set up the API

    💻 laptoprun

    A virtualenv keeps the Python packages isolated. Copy the example env file — the defaults are fine for local dev.

    cd server
python3 -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env             # open it and read the comments

    Remember: read server/.env. Each variable becomes a real deployment decision later.

  5. A5

    Migrate and seed

    💻 laptoprun

    migrate builds the tables; seed_demo fills them with a real catalogue and demo accounts. Seeding is idempotent.

    python manage.py migrate

python manage.py seed_demo \
    --admin-email admin@rmit.edu.au \
    --admin-password 'RmitStore2767!' \
    --demo-users

    Gives you: 47 products, an admin, a demo member, a demo seller. Add --no-images to finish in seconds while testing.

  6. A6

    Run the API

    💻 laptop · terminal 1run

    This command does not return — it holds the terminal open. Leave it running.

    python manage.py runserver 0.0.0.0:8000

curl http://localhost:8000/healthz/   # {"status": "ok"}
curl http://localhost:8000/readyz/    # {"database": "ok", "storage": "ok"}

    Explore: http://localhost:8000/api/docs/ drives the whole backend with no frontend running.

  7. A7

    Run the frontend

    💻 laptop · terminal 2run

    Leave the API running and open a second terminal. Vite serves the SPA and proxies /api to port 8000, so the browser sees one origin.

    cd /path/to/COSC2767-RMIT-Store-Django-Vue/client
npm install
cp .env.example .env
npm run dev                      # open http://localhost:5173

    Proof: product photos load. Grey placeholder boxes = SPA up but API not (check terminal 1).

  8. A8

    Build the real artifact

    💻 laptop · terminal 2run

    npm run dev is not deployment. See what you actually ship: static files in dist/. There is no Node in production.

    cd client
npm run build                    # produces client/dist/
npx vite preview --port 4173

# the trick — repoint the built artifact WITHOUT rebuilding:
nano dist/config.js              # set API_BASE_URL to http://localhost:8000/api

    The whole lesson: hard-reload :4173 with the network tab open — requests move to the new API, and the hashed bundle filename is byte-for-byte unchanged. This is what Plans C–E lean on.

✅ Done with A when

  • The store loads at localhost:5173 with real images.
  • curl /readyz/ returns database: ok and storage: ok.
  • You walked acceptance journeys A and B from the README, so you know what a working deploy looks like.

☁️ Plan B — Deploy to one EC2 by hand

GoalThe whole app on one AWS box, served the real way: nginx on port 80, gunicorn behind it, both as services that survive you logging out.
Where🧭 AWS console to launch, then ☁️ ec2 over SSH for everything else.
Steps14 in two halves: get it running with dev servers (B1–B8), then serve it properly (B9–B14).

Stay as ec2-user the whole way. Do not sudo su - or sudo -i. If you become root, the clone lands in /root/, nginx cannot traverse into it, and you get a 403 on every product image with nothing obviously wrong. Check with whoami (should print ec2-user). Use sudo only on the individual commands already written with it.

Part 1Get it running with the dev servers

  1. B1

    Launch the instance

    🧭 AWS consoleclick

    Amazon Linux 2023. t3.small is comfortable; t3.micro works but the frontend build is memory-hungry.

    # Security group inbound rules
22    My IP      # SSH
8000  Anywhere   # API (temporary)
5173  Anywhere   # dev server (temporary)
80    Anywhere   # nginx, from B9

    Never open 5432 to the world. Scope it to My IP only if you need a GUI client.

  2. B2

    Install the runtimes

    ☁️ ec2run

    SSH in, then install git, Python, Postgres and Node.

    sudo dnf update -y
sudo dnf install -y git python3.11 python3.11-pip postgresql16 postgresql16-server

curl -fsSL https://rpm.nodesource.com/setup_22.x | sudo bash -
sudo dnf install -y nodejs

python3.11 --version && node --version

    Use when: a fresh instance, right after first login.

  3. B3

    Start PostgreSQL

    ☁️ ec2run

    Initialise the cluster, start it, and create the same role and database as local.

    sudo postgresql-setup --initdb
sudo systemctl enable --now postgresql

sudo -u postgres psql -c "CREATE ROLE rmit LOGIN PASSWORD 'rmit' CREATEDB;"
sudo -u postgres psql -c "CREATE DATABASE rmit_store OWNER rmit;"

    Use when: once per DB instance. One more fix follows — do not skip it.

  4. B4

    Allow password logins

    ☁️ ec2run

    Amazon Linux's fresh initdb uses ident auth on 127.0.0.1, so Django is refused with "Ident authentication failed". Switch TCP lines to scram-sha-256.

    sudo sed -i 's/^\(host.*\)ident$/\1scram-sha-256/' /var/lib/pgsql/data/pg_hba.conf
sudo systemctl reload postgresql

PGPASSWORD=rmit psql -h 127.0.0.1 -U rmit -d rmit_store -c "SELECT 1;"

    Why: Django connects over TCP with a password. If SELECT 1 works, every later step can reach the DB.

  5. B5

    Code and dependencies

    ☁️ ec2run

    Clone into ec2-user's home — later paths expect it there.

    cd ~
git clone <your-repository-url>
cd COSC2767-RMIT-Store-Django-Vue/server
python3.11 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

    Must be: /home/ec2-user/COSC2767-.... Not /root/.

  6. B6

    Configure the API

    ☁️ ec2edit file

    Copy the env file (cp .env.example .env) and set the values that matter for a real host.

    SECRET_KEY=<generate a real one>
ALLOWED_HOSTS=<your-ec2-public-ip>,localhost,127.0.0.1
CLIENT_URL=http://<your-ec2-public-ip>:5173
CORS_ALLOWED_ORIGINS=http://<your-ec2-public-ip>:5173
DATABASE_URL=postgres://rmit:rmit@localhost:5432/rmit_store

    Use localhost in DATABASE_URL when the DB is on the same box — routing out to the public IP and back is slower and often blocked. (This changes in Plan C.)

  7. B7

    Migrate, seed, run

    ☁️ ec2 · terminal 1run

    Same two DB commands, then the dev server. It holds the terminal open — leave it.

    python manage.py migrate
python manage.py seed_demo --admin-email admin@rmit.edu.au \
                           --admin-password 'RmitStore2767!' --demo-users

python manage.py runserver 0.0.0.0:8000
# check http://<your-ec2-public-ip>:8000/healthz/

    Leave running. Open a second SSH terminal for the frontend.

  8. B8

    Run the frontend

    ☁️ ec2 · terminal 2run

    Second SSH session. No virtualenv needed — the client is a Node project.

    cd ~/COSC2767-RMIT-Store-Django-Vue/client
npm install
cp .env.example .env
npm run dev -- --host 0.0.0.0
# open http://<your-ec2-public-ip>:5173

    Now: the app runs on AWS — but it is not a deployment yet (both processes die when SSH closes).

Part 2Serve it properly — nginx + gunicorn + systemd

Stop both dev servers (Ctrl-C in each terminal). From here, nginx owns port 80, serves the built SPA and images from disk, and reverse-proxies API traffic to gunicorn on 127.0.0.1:8000. One origin, so CORS never enters the picture (yet — Plan C changes that).

  1. B9

    Build the SPA, install nginx

    ☁️ ec2run
    cd ~/COSC2767-RMIT-Store-Django-Vue/client
npm run build

sudo dnf install -y nginx
sudo systemctl enable --now nginx
sudo cp -r dist/* /usr/share/nginx/html/

    Expected: page loads, nothing works yet — nothing proxies /api/ until B12. Keep config.js at default API_BASE_URL: "/api".

  2. B10

    Reconfigure the API for prod

    ☁️ ec2edit file

    Same file as B6 — reopen server/.env and change these lines now that you are going to production.

    nano ~/COSC2767-RMIT-Store-Django-Vue/server/.env
    DJANGO_SETTINGS_MODULE=config.settings.prod
ALLOWED_HOSTS=<your-ec2-public-ip>,127.0.0.1,localhost
CLIENT_URL=http://<your-ec2-public-ip>
CORS_ALLOWED_ORIGINS=http://<your-ec2-public-ip>
CSRF_TRUSTED_ORIGINS=http://<your-ec2-public-ip>
SESSION_COOKIE_SECURE=False
CSRF_COOKIE_SECURE=False

    Gotcha: on plain HTTP, leaving the cookie flags True makes the admin accept your password then bounce you back to login. Turn them on the day you add TLS.

  3. B11

    gunicorn under systemd

    ☁️ ec2new file
    python manage.py collectstatic --noinput
sudo nano /etc/systemd/system/rmit-api.service
    [Unit]
Description=RMIT Store API (gunicorn)
After=network.target postgresql.service

[Service]
User=ec2-user
WorkingDirectory=/home/ec2-user/COSC2767-RMIT-Store-Django-Vue/server
ExecStart=/home/ec2-user/COSC2767-RMIT-Store-Django-Vue/server/.venv/bin/gunicorn \
    config.wsgi:application --bind 127.0.0.1:8000 --workers 3 \
    --env DJANGO_SETTINGS_MODULE=config.settings.prod
Restart=always

[Install]
WantedBy=multi-user.target
    sudo systemctl daemon-reload
sudo systemctl enable --now rmit-api

    Bind 127.0.0.1 — once nginx is in front, gunicorn should not be reachable from outside. Logs: journalctl -u rmit-api -f.

  4. B12

    Configure nginx

    ☁️ ec2new file

    Create a new config file. Everything below goes inside one server { } block — the location lines are not valid on their own.

    sudo nano /etc/nginx/conf.d/rmit-store.conf
    server {
    listen       80 default_server;
    listen  [::]:80 default_server;
    server_name  _;

    root  /usr/share/nginx/html;   # the built SPA from B9
    index index.html;

    client_max_body_size 10M;      # product images are bigger than the 1M default

    # serve the SPA; unknown paths are Vue routes, so fall back to index.html
    location / { try_files $uri $uri/ /index.html; }
    location = /config.js { add_header Cache-Control "no-store"; }

    # forward API-shaped paths to gunicorn
    location ~ ^/(api|admin|healthz|readyz)(/|$) {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host              $host;     # load-bearing!
        proxy_set_header X-Forwarded-Host  $host;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # serve uploaded images and Django static files straight off disk
    location /media/  { alias /home/ec2-user/COSC2767-RMIT-Store-Django-Vue/server/media/; }
    location /static/ { alias /home/ec2-user/COSC2767-RMIT-Store-Django-Vue/server/staticfiles/; }
}

    Save (Ctrl-O, Enter), exit (Ctrl-X), then let nginx reach /media/, test the config, and reload:

    chmod o+x /home/ec2-user      # let nginx traverse to /media/
sudo nginx -t && sudo systemctl reload nginx

    Why Host $host matters: without it Django builds every image_url as http://127.0.0.1:8000/..., which resolves to the browser's machine, and every image breaks with a fake "CORS" error.

  5. B13

    Verify

    💻 laptopcheck
    IP=<your-ec2-public-ip>
curl -I  http://$IP/                 # 200, text/html
curl -s  http://$IP/readyz/          # {"database": "ok", "storage": "ok"}
curl -sI http://$IP/shop             # 200 — SPA fallback works
curl -s  http://$IP/api/products/ | grep -o '"image_url":"[^"]*"' | head -1
    • The image URL must be on your public IP with no port.
    • 502 = gunicorn down. Check journalctl -u rmit-api.
    • 400 = IP missing from ALLOWED_HOSTS.
    • 403 on /media/ = the chmod o+x did not happen.
  6. B14

    Close the extra ports

    🧭 AWS consoleclick
    # in the security group, DELETE inbound 8000 and 5173
# keep 22 (SSH) and 80 (nginx)

    Re-run B13 after. If a check only passed because you were quietly hitting port 8000, this is where you catch it.

✅ Done with B when

  • The store works entirely through port 80 and images load.
  • Only ports 22 and 80 are open.
  • Closing your SSH session changes nothing — nginx and gunicorn are systemd services.

You have deployed the whole app by hand on one box.

🌐 Plan C — Split across servers

GoalDatabase on managed RDS, API on one EC2, frontend on another, uploads on S3 — with the two things that break (CORS, images) fixed on purpose.
Where🧭 AWS console · 🐍 api-server · 🌐 frontend-server — watch the badge, you will switch boxes often.
Steps13 in three parts: AWS pieces incl. Elastic IPs (C1–C4), the api-server (C5–C7), the frontend-server and the glue (C8–C13).

What changes and why. In Plan B everything shared one box and one origin. Plan C pulls the tiers apart: the database onto managed AWS RDS, the API on one instance, the frontend on another. Two things bite the moment you do — CORS (the browser now talks to two origins) and uploaded images (they live on one API box, so a second one 404s them). Solving both is the point of this step, and doing it by hand now makes the CloudFormation template in Plan F far easier.

Part 1The AWS pieces

  1. C1

    Plan the topology and make three security groups

    🧭 AWS consoleclick

    Three roles. The database is AWS RDS (managed, no box to run), the other two are EC2.

    RDS (PostgreSQL)  # managed database — private, no public access
api-server        # Django + gunicorn on :8000 (Plan B's API half, minus nginx and Postgres)
frontend-server   # nginx on :80 serving the built SPA; the browser calls the API directly

    Create three security groups: rds-sg, api-server-sg, frontend-server-sg. All rules below are Inbound rules — inbound means "who is allowed to connect TO this box." Leave Outbound at its default (All traffic → 0.0.0.0/0) on all three, or the boxes can't reach GitHub, dnf, or S3.

    The trick for the database rule: set the source to another security group, not an IP — then it keeps working even when private IPs change. (You can only point at an SG that already exists, so make all three empty first, then add rules.)

    # rds-sg — INBOUND        TYPE         PORT   SOURCE               WHY
  rule 1                  PostgreSQL   5432   api-server-sg        only the API may query the DB
# Public access on the RDS instance = No. No other inbound rule.
    # api-server-sg — INBOUND TYPE         PORT   SOURCE               WHY
  rule 1                  SSH          22     My IP                admin only
  rule 2                  Custom TCP   8000   Anywhere 0.0.0.0/0   the BROWSER calls the API directly (C9)
# nothing else
    # frontend-server-sg — INBOUND  TYPE   PORT   SOURCE               WHY
  rule 1                  SSH          22     My IP                admin only
  rule 2                  HTTP         80     Anywhere 0.0.0.0/0   public storefront — NOT your IP

    Common mistake: adding these under the Outbound tab. They go in Inbound rules → Edit inbound rules. Ports 80 and 8000 must be Anywhere, not your IP, or no one else can load the store.

    Why 8000 is public: in this design the browser loads the page from the frontend box and then calls <api>:8000/api itself, so the API must be reachable from anyone's browser. The database is the only private tier. (Alternative design: make the frontend nginx proxy /api to the api-server, then 8000 can be frontend-server-sg only. Either is valid — say which you chose in the report.)

  2. C2

    Create the database on RDS

    🧭 AWS consoleclick

    Move Postgres off the API box and onto managed AWS RDS — you get automated backups and a stable endpoint, and there is no database server to patch. State and justify this choice in the report.

    1. RDS → Create database → Standard create → engine PostgreSQL.
    2. Template Free tier (or Dev/Test). Instance class db.t3.micro is fine.
    3. DB instance identifier rmit-store — this is just AWS's name for the box. Use a hyphen, not an underscore (underscores are rejected here).
    4. Master username rmit, set a master password (write it down — you need it in C6).
    5. Under Additional configuration, Initial database name rmit_store — this is the actual Postgres database, and here an underscore is fine. (Skip this and no database is created — Django will fail to connect.)
    6. Connectivity → Public access: No. Put it in the same VPC as the api-server.
    7. VPC security group → attach rds-sg from C1 (inbound 5432, source = api-server-sg, not an IP).
    8. Create it. When status is Available, open the instance and copy the Endpoint — e.g. rmit-store.abc123.ap-southeast-2.rds.amazonaws.com. That is your DB host for C6.

    Rule: the database is never reachable from the internet. Leave Public access = No. Only the api-server's security group may reach port 5432.

  3. C3

    Launch both EC2 instances

    🧭 AWS consoleclick

    Two instances, same AMI and size, different security groups. Name them so you never SSH into the wrong one.

    # both: Amazon Linux 2023, t3.small, your key pair, same VPC as RDS
api-server        security group = api-server-sg
frontend-server   security group = frontend-server-sg

    Tip: keep two terminal tabs open, one per box, and name the tabs. Every step below tells you which one to type in.

  4. C4

    Pin an Elastic IP to each box — do it now, before any config

    🧭 AWS consoleclick

    Why now. Every time you stop and restart the Learner Lab, an EC2 instance's public IP changes. Every address you type from here on (config.js, .env, CORS) would then be wrong and you would edit them all again. An Elastic IP is a fixed public IP you pin to an instance once — it never changes. Pin both now, and every later step uses the fixed address the first time.

    EC2 public IP         -> CHANGES every restart   (the pain)
RDS endpoint          -> stays the same          (DATABASE_URL is safe)
Elastic IP (once set) -> stays the same          (the fix)
    1. EC2 console → Elastic IPs (left menu, under Network & Security) → Allocate Elastic IP address → Allocate.
    2. Select the new IP → Actions → Associate Elastic IP address.
    3. Resource type Instance → pick api-server → Associate.
    4. Repeat once more for frontend-server.

    Write both down — they are the two placeholders used in the rest of Plan C:

    <api-elastic-ip>        # api-server   — used in C6, C7, C9, C10
<frontend-elastic-ip>   # frontend-server — used in C6, C10, C12

    Learner Lab tip: keep each Elastic IP associated with a running instance. AWS charges for an Elastic IP that is allocated but attached to nothing — associated-and-running is free.

    Payoff: restart the lab as many times as you like — the addresses hold and nothing needs re-editing. Plan D and Plan F assume you did this.

Part 2The api-server

  1. C5

    One deploy key, made here, used on every box

    🐍 api-serverrun

    Your repo is private, so every instance needs an SSH key to git clone it. Don't make three keys and register three times — make one key on the api-server, add it to GitHub once, then copy it to the frontend-server in C8.

    # -N ''  = no passphrase, so servers can clone unattended
ssh-keygen -t ed25519 -C "rmit-store-deploy" -f ~/.ssh/id_ed25519 -N ''
cat ~/.ssh/id_ed25519.pub          # copy this whole line

    Register the PUBLIC half on GitHub — once. Pick one:

    • Deploy key (recommended, safest): your repo → Settings → Deploy keys → Add deploy key → paste the .pub line. Leave "Allow write access" unchecked — clone-only, and it's scoped to this one repo.
    • Account SSH key: github.com → Settings → SSH and GPG keys — works too, but grants access to all your repos, so it's broader than you need.
    ssh -T git@github.com     # first time: type "yes"; expect "Hi ...! You've successfully authenticated"

    Note the URL form for every clone from now on: git@github.com:... (SSH), not https://... — only the SSH URL uses the key. Safer alternative: never copy the private key anywhere and use agent forwarding — ssh -A — so the key never lands on any server. Mention whichever you chose in the report.

  2. C6

    Provision the api-server and point it at RDS

    🐍 api-serverrunedit file

    The box that runs Django. It's Plan B's API half — but with no Postgres server (that's RDS now) and no SPA/nginx (that's the frontend box). postgresql16 here is the psql client only, to test RDS.

    sudo dnf update -y
sudo dnf install -y git python3.11 python3.11-pip postgresql16

cd ~
git clone git@github.com:<your-team>/COSC2767-RMIT-Store-Django-Vue.git
cd COSC2767-RMIT-Store-Django-Vue/server
python3.11 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env

    Now edit server/.env. These are the only lines you change from the shipped example — everything else (email, JWT, tax, throttles) keeps its default.

    # api-server  server/.env  — fill the <...> from your own AWS console
DJANGO_SETTINGS_MODULE=config.settings.prod
SECRET_KEY=<generate a real one — see below>
DEBUG=False
ALLOWED_HOSTS=<api-elastic-ip>,<api-private-ip>,127.0.0.1
CLIENT_URL=http://<frontend-elastic-ip>

  3. C10

    Fix CORS (the thing that "suddenly" breaks)

    🐍 api-serveredit file

    Open the store in a browser now and the products won't load. The browser loads the SPA from one origin and calls the API on another — a cross-origin request.     # api-server  server/.env  — use the FRONTEND's public origin
CORS_ALLOWED_ORIGINS=http://<frontend-elastic-ip>
CSRF_TRUSTED_ORIGINS=http://<frontend-elastic-ip>
ALLOWED_HOSTS=<api-elastic-ip>,<api-private-ip>,127.0.0.1
    sudo systemctl restart rmit-api

    Why it appears now and not in B: Plan B put both tiers behind one nginx, so there was only one origin and CORS never applied. Split them and it does. (You can also keep the frontend nginx proxying /api to the api-server to stay single-origin — a valid design; note which you chose in the report.)

  4. C11

    Shared media on S3 (images stop breaking)

    🧭 AWS console🐍 api-serverclickrun

    Uploads land on one API box's server/media/. Add a second API box and half the images 404, intermittently. S3 gives every box one shared store — no code change, the backend is chosen by config.

    1. Give the api-server an IAM role, not access keys. boto3 uses the default credential chain, so an instance role that can write to the bucket means no long-lived keys in any .env. A leaked key in a repo is classic marker-bait; a role rotates automatically and never sits in a file.

    1. EC2 console → click your api-server instance.
    2. Actions → Security → Modify IAM role.
    3. Learner Lab: pick LabInstanceProfile (or LabRole). Own account: a role whose policy allows s3:GetObject, s3:PutObject, s3:DeleteObject on arn:aws:s3:::rmit-store-media-<yourteam>/*.
    4. Update IAM role. Without this, the next command fails with "Unable to locate credentials".

    2. Create the bucket — once; a bucket is global, not per-box. Names are global and unique: swap <yourteam> for something like group7. If you get BucketAlreadyExists, pick a different suffix.

    us-east-1 (the common case) — no LocationConstraint

    aws s3api create-bucket --bucket rmit-store-media-<yourteam> --region us-east-1

    Any other region — needs LocationConstraint in both spots

    aws s3api create-bucket \
  --bucket rmit-store-media-<yourteam> \
  --region <your-region> \
  --create-bucket-configuration LocationConstraint=<your-region>

    3. Turn S3 on in the API and restart, then re-seed so the demo images upload to S3:

    # api-server  server/.env   (us-east-1 shown)
USE_S3=True
AWS_STORAGE_BUCKET_NAME=rmit-store-media-<yourteam>
AWS_S3_REGION_NAME=us-east-1
    sudo systemctl restart rmit-api
cd ~/COSC2767-RMIT-Store-Django-Vue/server && source .venv/bin/activate && python3 manage.py seed_demo

    4. Let the browser read the images. Product image URLs point straight at the bucket (https://rmit-store-media-<yourteam>.s3.amazonaws.com/...). New buckets block public access, so the browser gets 403 and images look broken. Open the bucket in the S3 console and do both:

    1. Turn off "Block all public access" — bucket → Permissions tab → Block public access → Edit → untick Block all public access → Save → type confirm.
    2. Add a read-only bucket policy — same Permissions tab → Bucket policy → Edit → paste (swap in your bucket name):
    {
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "PublicReadMedia",
    "Effect": "Allow",
    "Principal": "*",
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::rmit-store-media-<yourteam>/*"
  }]
}

    This grants read-only. s3:GetObject only lets the public view images — nobody can upload or delete. Writes still go through the api-server's IAM role from part 1.

    Test: upload a product image in /admin/ (or open a seeded product), confirm the object is under media/products/ in the bucket and the image renders in the browser — then it survives an instance being replaced.

  5. C12

    Walk the store end to end

    💻 laptopcheck

    Open http://<frontend-elastic-ip> in a browser with the network tab open.

    • Products load, images grey → S3 policy or USE_S3 — check C11 part 4.
    • Nothing loads, console shows a CORS error → C10: the frontend origin in .env doesn't match the address in the browser bar exactly (http vs https, trailing port).
    • Network tab shows requests to the wrong host → C9: config.js still has the old API_BASE_URL. Hard refresh.

    Security recap: traffic flows one way

    🧭 AWS consolecheck

    Every port is a deliberate rule. Re-read your three security groups against this — it is the layout Plan F's load balancer will sit on top of.

    public → frontend-server (80)  → open to Anywhere
public → api-server (8000)     → open to Anywhere (the browser calls it directly)
api-server → RDS (5432)        → source = api-server-sg ONLY, no public access

🐳 Plan D — Containerise with Docker

GoalTwo images — rmit-api and rmit-frontend — that replace the hand-installed services from Plan C on the same two boxes. Same RDS, same S3, same Elastic IPs.
Where🐍 api-server for the API files and image, 🌐 frontend-server for the frontend files and image. Both need Docker: sudo dnf install -y docker && sudo systemctl enable --now docker.
Steps7 in two parts: write the recipes (D1–D5, nothing runs yet), then build, run, verify (D6–D7).

Why now. Plan C worked but every box was set up by hand. A container captures that setup as a file, so the next box is docker run instead of an afternoon. The repo ships no Dockerfiles — writing them is the assignment. Below is a correct starting shape based on the README's rules.

Part 1Write the recipes — nothing builds yet

Writing a Dockerfile does not build anything. D1–D5 only create files at the repo root (the folder holding server/ and client/). The actual docker build and docker run happen in D6.

  1. D1

    Dockerfile for the API

    🐍 api-servernew file

    Make Dockerfile.api at the repo root. Package Django + gunicorn. The key decision: migrate touches the database, so it belongs at run time (entrypoint), not in the image build. collectstatic needs no DB, so it can run at build.

    FROM python:3.12-slim
WORKDIR /app
COPY server/requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY server/ .
RUN python manage.py collectstatic --noinput
EXPOSE 8000
COPY entrypoint.sh /entrypoint.sh
RUN chmod +x /entrypoint.sh
ENTRYPOINT ["/entrypoint.sh"]

    The RUN chmod +x line is not optional: git usually drops the executable bit, so without it the container dies with "/entrypoint.sh": permission denied. Baking the chmod into the image fixes it for every clone.

    Pin the image (python:3.12-slim, not latest) so a rebuild next week is the same build this week.

  2. D2

    The API entrypoint

    🐍 api-servernew file

    Make entrypoint.sh at the repo root, then chmod +x entrypoint.sh. Run migrations, then hand off to gunicorn as PID 1 with exec.

    #!/bin/sh
set -e
python manage.py migrate --noinput
exec gunicorn config.wsgi:application \
    --bind 0.0.0.0:8000 --workers 3 \
    --env DJANGO_SETTINGS_MODULE=config.settings.prod

    Why exec: gunicorn becomes PID 1 and receives Docker's stop signals, so the container shuts down cleanly instead of being killed.

  3. D3

    Dockerfile for the frontend, plus its nginx.conf

    🌐 frontend-servernew file

    Two files at the repo root: Dockerfile.frontend and nginx.conf. Multi-stage: Node builds the bundle, then the result is copied into an nginx image. The final image must not contain Node.

    # build stage
FROM node:22-slim AS build
WORKDIR /app
COPY client/package*.json ./
RUN npm ci
COPY client/ .
RUN npm run build

# runtime stage — nginx only, no Node
FROM nginx:alpine
COPY --from=build /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf

    That last line needs the second file. Without nginx.conf next to the Dockerfile the build fails with "/nginx.conf": not found:

    server {
    listen 80;
    server_name _;
    root /usr/share/nginx/html;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }
}

    The try_files ... /index.html line matters: the store is a Vue single-page app, so refreshing a deep link like /products must still serve index.html and let Vue route it. Without it, any refresh off the home page 404s.

    Prove it (after D6): docker run --rm rmit-frontend which node finds nothing. That is the point of the multi-stage build.

  4. D4

    A .dockerignore

    🐍 api-server🌐 frontend-servernew file

    Make .dockerignore at the repo root on each box — wherever you run docker build. Keep build context small and secrets out of the image.

    # .dockerignore
**/.venv
**/node_modules
**/.env
**/__pycache__
server/media
server/staticfiles
.git

    Never copy .env into an image — pass config at run time with --env-file or an orchestrator secret.

  5. D5

    Keep config.js a runtime thing

    🌐 frontend-servernew file

    Remember A8/C9: the API URL is read at page load. Do not bake it into the image — mount an environment-specific config.js over the baked-in one when the container starts, so one image works in every environment. The file lives outside the repo at /opt/rmit/config.js.

    Trap — create the file BEFORE the first docker run. If /opt/rmit/config.js does not exist when you run with -v, Docker silently creates it as an empty directory, and the next run fails with not a directory: Are you trying to mount a directory onto a file? A -v mount must match types — file onto file.

    Make it now, seeded from the repo's default, then set the API Elastic IP:

    sudo mkdir -p /opt/rmit
sudo cp ~/COSC2767-RMIT-Store-Django-Vue/client/public/config.js /opt/rmit/config.js
sudo nano /opt/rmit/config.js          # set API_BASE_URL to http://<api-elastic-ip>:8000/api
ls -l /opt/rmit/config.js              # must be a FILE, not a directory

    🔧 Already ran the container and got the "not a directory" error?

    Docker made a folder by mistake. Delete it and make a real file — a one-time fix. Once it is a real file it stays a file; rebuilds, restarts and IP edits never bring the error back.

    sudo docker rm web
sudo rm -rf /opt/rmit/config.js
sudo mkdir -p /opt/rmit
# seed it from the image's baked-in config, then set the API IP:
sudo docker run --rm rmit-frontend cat /usr/share/nginx/html/config.js \
  | sudo tee /opt/rmit/config.js
sudo nano /opt/rmit/config.js          # set API_BASE_URL to the API Elastic IP
ls -l /opt/rmit/config.js              # must be a FILE, not a directory

    Why: build the image once, promote the same artifact — the idea Plan F's pipeline depends on.

Part 2Build, run, verify

  1. D6

    Free the ports, build, run

    🐍 api-server🌐 frontend-serverrun

    Free the ports first. Plan C left the rmit-api systemd service on :8000 and nginx on :80. The containers want those same ports, so a run fails with bind: address already in use. Stop the old services before running the containers.

    🐍 api-server from the repo root

    sudo systemctl stop rmit-api           # frees :8000

docker build -t rmit-api -f Dockerfile.api .
docker run -d --name api -p 8000:8000 --env-file server/.env rmit-api
curl http://localhost:8000/healthz/    # {"status": "ok"}

    🌐 frontend-server from the repo root

    sudo systemctl stop nginx              # frees :80

docker build -t rmit-frontend -f Dockerfile.frontend .
docker run -d --name web -p 80:80 \
  -v /opt/rmit/config.js:/usr/share/nginx/html/config.js:ro \
  rmit-frontend

    A failed run still leaves a container with that name, so a retry hits name already in use. Clear it before re-running: sudo docker rm api (or web). Then open the frontend Elastic IP in a browser — the store should look exactly as it did at the end of Plan C.

    Use when: proving the containers work before Compose. The DB stays on RDS from Plan C; it becomes a container in Plan E.

  2. D7

    Survive a lab restart

    🐍 api-server🌐 frontend-serverrun

    By default a Learner Lab reboot leaves Docker off and your containers down. Three one-time commands per box make everything come back on its own.

    🐍 api-server

    sudo systemctl enable docker                       # Docker starts at boot
sudo systemctl disable --now rmit-api              # kill the Plan C service that steals :8000
sudo docker update --restart unless-stopped api    # container auto-starts on boot

    🌐 frontend-server

    sudo systemctl enable docker
sudo systemctl disable --now nginx                 # kill the Plan C nginx that steals :80
sudo docker update --restart unless-stopped web

    disable --now stops the old Plan C service and stops it auto-starting, so it never fights the container for the port. unless-stopped means the container comes back on boot unless you stopped it on purpose.

    After a restart, nothing to re-run — just verify: curl http://localhost:8000/healthz/ on the api box, and open the frontend Elastic IP in a browser. The Elastic IPs hold, so config.js and server/.env stay correct.

    Catch: docker update --restart only affects a container that already exists. If you docker rm and recreate one, add --restart unless-stopped to that docker run so the policy sticks.

✅ Done with D when

  • Both images build.
  • The API image runs migrations on startup and stops cleanly.
  • The frontend image has no Node in it (which node finds nothing).
  • config.js is injected at run time, not baked in.
  • The store works from containers and comes back after a lab restart.

Next: one file to run all of them together.

🧱 Plan E — Docker Compose

GoalOne docker-compose.yml that brings up db, api and web together, in order, with one command.
Where🐍 api-server only. Unlike Plan D, the whole stack runs on one box. Compose brings its own db container, so you don't use RDS here. Every file and command lives at the repo root on that box.
Steps6 · install the plugins, write the file, run it.

What Compose adds. Plan D ran containers one docker run at a time. Compose describes the database, the API and the frontend in one file and starts them together, on one network, with the startup order handled for you. It is the last manual step — real multi-host orchestration (Swarm/Kubernetes) is Plan F.

  1. E1

    Install the Compose and buildx plugins

    🐍 api-serverrun

    Amazon Linux 2023's docker comes from Amazon's repo, not Docker's — so sudo dnf install docker-compose-plugin just says No match for argument. You must drop the plugin binaries in by hand. Compose also builds with buildx, so install both, or you'll hit unknown shorthand flag: 'd' (no Compose) then compose build requires buildx 0.17.0 or later (no buildx).

    # make the plugin folder once:
sudo mkdir -p /usr/local/lib/docker/cli-plugins

# 1) Compose:
sudo curl -SL https://github.com/docker/compose/releases/latest/download/docker-compose-linux-x86_64 \
  -o /usr/local/lib/docker/cli-plugins/docker-compose
sudo chmod +x /usr/local/lib/docker/cli-plugins/docker-compose

# 2) buildx (pin a current version — buildx has no 'latest' file):
sudo curl -SL https://github.com/docker/buildx/releases/download/v0.36.1/buildx-v0.36.1.linux-amd64 \
  -o /usr/local/lib/docker/cli-plugins/docker-buildx
sudo chmod +x /usr/local/lib/docker/cli-plugins/docker-buildx

# verify both:
sudo docker compose version      # Docker Compose version v2.x+
sudo docker buildx version       # github.com/docker/buildx v0.36.1

    Check the newest buildx tag at github.com/docker/buildx/releases and swap the version if v0.36.1 is stale. Docker's official plugin docs: docs.docker.com/compose/install/linux.

  2. E2

    The compose file

    🐍 api-servernew file

    Make docker-compose.yml at the repo root. Three services on one network. The API and frontend build from the Dockerfiles you wrote in Plan D — copy Dockerfile.frontend and nginx.conf onto this box if they only exist on the frontend-server.

    services:
  db:
    image: postgres:16
    environment:
      POSTGRES_USER: rmit
      POSTGRES_PASSWORD: rmit
      POSTGRES_DB: rmit_store
    volumes: [ "pgdata:/var/lib/postgresql/data" ]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U rmit"]
      interval: 5s
      retries: 10

  api:
    build: { context: ., dockerfile: Dockerfile.api }
    env_file: server/.env
    ports: [ "8000:8000" ]     # browser hits the API directly (Plan C design)
    depends_on:
      db: { condition: service_healthy }

  web:
    build: { context: ., dockerfile: Dockerfile.frontend }
    ports: [ "80:80" ]
    depends_on: [ api ]

volumes: { pgdata: {} }

    Publish :8000 or the store can't talk to the API. nginx (web) only serves the built Vue files on :80 — it does not proxy /api. The browser calls the API straight at <api-ip>:8000 (the same design as Plan C), so config.js API_BASE_URL must be http://<api-ip>:8000/api. Skip the api ports and the page loads but every product/login call fails.

    Note the volume: pgdata keeps the database on disk, so docker compose down does not wipe your catalogue. And server/.env must now point DATABASE_URL at postgres://rmit:rmit@db:5432/rmit_store — the service name db, not RDS.

  3. E3

    Wait for the database, don't crash-loop

    🐍 api-serveredit file

    Keep editing the same docker-compose.yml. The db healthcheck plus depends_on: condition: service_healthy makes the API wait until Postgres actually answers — not just until its container exists. Add a readiness check on the API too, so web waits for a working API.

    # already in E2:
#   db.healthcheck  -> pg_isready
#   api.depends_on.db.condition: service_healthy
# add this block into the api service:
  api:
    healthcheck:
      test: ["CMD-SHELL", "curl -f http://localhost:8000/readyz/ || exit 1"]
      interval: 10s
      retries: 5

    Why: without it the API starts before the DB is ready, fails to connect, and restarts in a loop that looks like a bug. /readyz/ is exactly the probe for this.

  4. E4

    Decide where migrations run

    🐍 api-serveredit file

    Three containers start at once — you must decide who runs migrate, exactly once, before the API serves traffic. Two clean options. Pick Option A (nothing to add) or Option B (paste the migrate service and the api.depends_on below into the same file).

    # Option A (simplest): the API entrypoint from D2 runs migrate on start.
#   Fine for one API replica. With several, they race — usually harmless
#   (migrations are transactional) but noisy.

# Option B (cleaner): a one-shot migrate service that runs and exits,
#   and the API waits for it to finish successfully.
  migrate:
    build: { context: ., dockerfile: Dockerfile.api }
    env_file: server/.env
    entrypoint: []                       # MUST clear the entrypoint, see below
    command: python manage.py migrate --noinput
    depends_on:
      db: { condition: service_healthy }
  api:
    depends_on:
      migrate: { condition: service_completed_successfully }

    The gotcha that makes Option B hang. Dockerfile.api ends in ENTRYPOINT ["/entrypoint.sh"], and that script always finishes with exec gunicorn. So a bare command: is ignored — the migrate container runs gunicorn and never exits, and api waits on it forever (docker compose ps shows migrate stuck Up, not Exited (0)). Adding entrypoint: [] clears that, so command runs directly and the container exits when migrate finishes.

    For the report: naming where migrations run and what happens if they fail is exactly the operational decision the assignment is probing.

  5. E5

    Run it and verify

    🐍 api-serverruncheck

    Free the ports first. If the one-off api/web containers from D6 (or the Plan C services) are still holding :80 and :8000, Compose can't bind and you'll hit address already in use. Clear them — the || true means "don't error if they aren't there". No such container: api is fine; it just means there was nothing to clean up.

    sudo docker rm -f api web 2>/dev/null || true            # remove D6 containers IF they exist
sudo systemctl stop rmit-api nginx 2>/dev/null || true    # stop Plan C services IF running

    One command brings the whole stack up. Seed once the DB is healthy.

    docker compose up -d --build
docker compose ps            # all healthy?

# seed the catalogue (once):
docker compose exec api python manage.py seed_demo \
    --admin-email admin@rmit.edu.au --admin-password 'RmitStore2767!' --demo-users

# API lives on :8000 (NOT behind nginx on :80):
curl -s http://localhost:8000/readyz/       # {"database": "ok", "storage": "ok"}
curl -s http://localhost:8000/api/version/  # the build you just ran

# the store page is nginx on :80 — this returns HTML, which is correct:
curl -s http://localhost/                   # <!doctype html> ... RMIT Store

    Don't be fooled: curl localhost/readyz/ (port 80) returns the store's HTML, not JSON — because nginx sends every unknown path to index.html. That is not a bug. The API check must use :8000.

    Logs: docker compose logs -f api. Tear down: docker compose down (add -v to also drop the DB volume).

  6. E6

    Know the ceiling

    read

    Compose runs on one host. It is perfect for local dev and a single demo box, but it does not spread containers across machines or scale a tier to many replicas.

    # the moment you scale the API to 2+ replicas across hosts, uploaded
# images on local disk break again — which is why Plan C added S3.
# multi-host scaling itself is Plan F: Docker Swarm or Kubernetes.

    This is the handoff line to the automation pipeline. Stop here.

✅ Done with E when

  • docker compose up -d --build brings the whole store up.
  • The API waits for a healthy database instead of crash-looping.
  • Migrations run exactly once, and you can say where.
  • /readyz/ on :8000 is green.

You can now start, stop and rebuild the entire app with one command.
