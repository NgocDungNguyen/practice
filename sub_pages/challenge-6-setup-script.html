🚀Challenge 6: Automated Setup Script

The Week 4 ultimate challenge, solved: one bash script that takes a blank EC2 instance to a live Maven webapp served by Tomcat on port 80 — with the reasoning behind every step.

4 sections11 code blocks~13 min

🎯 The ultimate challenge, solved

What the script does

All eight tutorial stages in order, each verified before the next: system update, Java 17 (Corretto), environment variables for all users, Maven, Tomcat 9 on port 80, a systemd service, then generate → build → deploy the archetype webapp.

1. yum update + Corretto 17 (-devel)
2. JAVA_HOME / M2_HOME in /etc/profile.d
3. Maven  → /opt/maven
4. Tomcat → /opt/tomcat, port 80
5. systemd unit (survives reboot)
6. mvn archetype:generate + dynamic index.jsp
7. mvn clean package → cp WAR → restart
8. poll http://localhost/helloWorld/ until 200

Use when: the assignment says "fresh instance to working website" — the end state is http://<public-ip>/helloWorld/.

How to run it

Copy the script to a brand-new Amazon Linux 2023 instance and run it as root. Everything it prints is also logged to /var/log/rmit-setup.log.

scp -i labsuser.pem setup.sh ec2-user@<public-ip>:~
ssh -i labsuser.pem ec2-user@<public-ip>
sudo bash setup.sh
# — or paste the whole script into the EC2
#   "User data" field at launch: the instance
#   then configures itself on first boot

Remember: the security group must allow inbound TCP 80 (and 22 for SSH) — no script can open that for you.

Important: the script matches the lab PDF — Corretto 17, the vn.edu.rmit / helloWorld archetype coordinates, and the port-80 end goal. It is syntax-checked but has not been executed against a live EC2 instance yet: do one real run before submitting anything that depends on it.

📜 The complete setup.sh

setup.sh — copy, save, run with sudo

Use the copy button on the block and save as setup.sh. The version variables are pinned to Maven 3.9.16 and Tomcat 9.0.120 (both verified live on the CDN); if a download ever 404s, update the two variables from maven.apache.org and tomcat.apache.org — the archive.apache.org fallback usually saves you anyway.

#!/bin/bash
###############################################################################
# Challenge 6 — Automate the Entire Setup (Java + Maven + Tomcat + deploy)
# Target: fresh Amazon Linux 2023 EC2 instance. Run as root:  sudo bash setup.sh
# End goal: http://<ec2-public-ip>/helloWorld/  (port 80)
###############################################################################
set -euo pipefail

# ----- 0. Config (check versions at maven.apache.org / tomcat.apache.org) ----
MAVEN_VERSION="3.9.16"
TOMCAT_VERSION="9.0.120"
APP_GROUP_ID="vn.edu.rmit"
APP_NAME="helloWorld"
WORKDIR="/root"
LOG_FILE="/var/log/rmit-setup.log"

# ----- Logging: everything below goes to console AND the log file -----------
exec > >(tee -a "$LOG_FILE") 2>&1
say()  { echo -e "\n=== $* ==="; }
fail() { echo "FATAL: $*" >&2; exit 1; }

[ "$(id -u)" -eq 0 ] || fail "run me as root: sudo bash $0"

# ----- 1. System preparation -------------------------------------------------
say "1/8 System update + Java 17 (Amazon Corretto)"
yum update -y
yum install -y java-17-amazon-corretto-devel wget tar gzip   # -devel => javac (Maven compiles)
java -version  || fail "Java did not install"
javac -version || fail "JDK (javac) missing"

# ----- 2. Environment variables — for ALL users (Challenge 5, hard solution) -
say "2/8 JAVA_HOME / M2_HOME in /etc/profile.d (every login shell gets them)"
JAVA_HOME="$(dirname "$(dirname "$(readlink -f "$(command -v java)")")")"
cat > /etc/profile.d/maven.sh <<EOF
export JAVA_HOME=${JAVA_HOME}
export M2_HOME=/opt/maven
export M2=/opt/maven/bin
export PATH=\${M2}:\${PATH}
EOF
chmod 644 /etc/profile.d/maven.sh
# make the vars available inside THIS script too (non-login shell)
source /etc/profile.d/maven.sh

# ----- helper: fetch from Apache CDN, fall back to the permanent archive -----
fetch() { # fetch <url-path-on-dlcdn> <url-on-archive> <outfile>
    wget -q "https://dlcdn.apache.org/$1" -O "$3" || \
    wget -q "https://archive.apache.org/dist/$2" -O "$3" || \
    fail "could not download $3"
}

# ----- 3. Install Maven ------------------------------------------------------
say "3/8 Maven ${MAVEN_VERSION} -> /opt/maven"
fetch "maven/maven-3/${MAVEN_VERSION}/binaries/apache-maven-${MAVEN_VERSION}-bin.tar.gz" \
      "maven/maven-3/${MAVEN_VERSION}/binaries/apache-maven-${MAVEN_VERSION}-bin.tar.gz" \
      /tmp/maven.tar.gz
tar -xzf /tmp/maven.tar.gz -C /opt
ln -sfn "/opt/apache-maven-${MAVEN_VERSION}" /opt/maven
mvn -version || fail "Maven not working"

# ----- 4. Install Tomcat 9 ---------------------------------------------------
say "4/8 Tomcat ${TOMCAT_VERSION} -> /opt/tomcat, listening on port 80"
fetch "tomcat/tomcat-9/v${TOMCAT_VERSION}/bin/apache-tomcat-${TOMCAT_VERSION}.tar.gz" \
      "tomcat/tomcat-9/v${TOMCAT_VERSION}/bin/apache-tomcat-${TOMCAT_VERSION}.tar.gz" \
      /tmp/tomcat.tar.gz
tar -xzf /tmp/tomcat.tar.gz -C /opt
ln -sfn "/opt/apache-tomcat-${TOMCAT_VERSION}" /opt/tomcat

# Challenge 2: serve on port 80 instead of 8080
sed -i 's/port="8080"/port="80"/' /opt/tomcat/conf/server.xml
grep -q 'port="80"' /opt/tomcat/conf/server.xml || fail "port edit failed"

# convenience shortcuts from the tutorial
ln -sfn /opt/tomcat/bin/startup.sh  /usr/local/bin/tomcatup
ln -sfn /opt/tomcat/bin/shutdown.sh /usr/local/bin/tomcatdown

# ----- 5. Tomcat as a service (Challenge 4, systemd = the robust solution) ---
say "5/8 systemd unit so Tomcat survives reboots"
cat > /etc/systemd/system/tomcat.service <<EOF
[Unit]
Description=Apache Tomcat 9
After=network.target

[Service]
Type=forking
Environment=JAVA_HOME=${JAVA_HOME}
Environment=CATALINA_HOME=/opt/tomcat
ExecStart=/opt/tomcat/bin/startup.sh
ExecStop=/opt/tomcat/bin/shutdown.sh
Restart=on-failure
User=root

[Install]
WantedBy=multi-user.target
EOF
systemctl daemon-reload
systemctl enable --now tomcat
systemctl is-active --quiet tomcat || fail "Tomcat service failed to start"

# ----- 6. Generate the Maven web application (the tutorial's one-liner) ------
say "6/8 Generate ${APP_NAME} from maven-archetype-webapp"
cd "$WORKDIR"
rm -rf "$APP_NAME"
mvn -q archetype:generate -DgroupId="$APP_GROUP_ID" -DartifactId="$APP_NAME" \
    -DarchetypeArtifactId=maven-archetype-webapp -DinteractiveMode=false

# Challenge 1: replace index.jsp with dynamic content
cat > "$WORKDIR/$APP_NAME/src/main/webapp/index.jsp" <<'EOF'
<html>
<head><title>Automated Setup</title></head>
<body>
  <h1>Hello, World!</h1>
  <h3>DevOps Class at RMIT — deployed by one bash script!</h3>
  <p>The current server date and time is: <%= new java.util.Date() %></p>
</body>
</html>
EOF

# ----- 7. Build and deploy (Challenge 3, scripted) ----------------------------
say "7/8 mvn package + deploy WAR to Tomcat"
cd "$WORKDIR/$APP_NAME"
mvn -q clean package
[ -f "target/${APP_NAME}.war" ] || fail "build produced no WAR"

rm -rf "/opt/tomcat/webapps/${APP_NAME}" "/opt/tomcat/webapps/${APP_NAME}.war"
cp "target/${APP_NAME}.war" /opt/tomcat/webapps/
systemctl restart tomcat

# ----- 8. Verify end-to-end (error checking, as the guidance asks) -----------
say "8/8 Wait for the app to answer on port 80"
for i in $(seq 1 30); do
    if curl -sf -o /dev/null "http://localhost:80/${APP_NAME}/"; then
        break
    fi
    [ "$i" -eq 30 ] && fail "app never came up — check ${LOG_FILE} and /opt/tomcat/logs"
    sleep 2
done

# public IP via instance metadata (IMDSv2)
TOKEN=$(curl -sf -X PUT "http://169.254.169.254/latest/api/token" \
        -H "X-aws-ec2-metadata-token-ttl-seconds: 60" || true)
PUBLIC_IP=$(curl -sf -H "X-aws-ec2-metadata-token: $TOKEN" \
        "http://169.254.169.254/latest/meta-data/public-ipv4" || echo "<ec2-public-ip>")

say "DONE — open:  http://${PUBLIC_IP}/${APP_NAME}/"
echo "(Security group must allow inbound TCP 80. Full log: ${LOG_FILE})"

Tip: re-running the script is safe — symlinks use ln -sfn, the old deployment is removed before the new WAR is copied, and the version pins mean you always know what is installed.

🧭 Why each part is there

Java first, and the -devel package

Everything except the webapp itself runs on the JVM, so Java installs before anything else. The plain Corretto package is only a runtime — Maven needs javac, which lives in the -devel variant.

yum install -y java-17-amazon-corretto-devel
javac -version || fail "JDK (javac) missing"

Remember: JRE runs bytecode, JDK compiles source. A Tomcat-only box can live on the JRE; a build box cannot.

/etc/profile.d — Challenge 5's real fix

Writing JAVA_HOME, M2_HOME, and PATH into /etc/profile.d/maven.sh makes mvn work for every user and login shell — ec2-user, sudo su, and sudo su - alike — instead of patching one user's .bash_profile.

cat > /etc/profile.d/maven.sh <<EOF
export JAVA_HOME=...
export PATH=\${M2}:\${PATH}
EOF
source /etc/profile.d/maven.sh  # scripts are non-login shells

Remember: the script must source the file itself — a script is a non-login shell and never reads profile files on its own.

/opt, symlinks, and the archive fallback

Tarballs unpack into versioned directories under /opt; the stable /opt/maven and /opt/tomcat symlinks mean nothing else ever hard-codes a version. Downloads try the CDN, then fall back to the permanent archive.

wget https://dlcdn.apache.org/...        \
  || wget https://archive.apache.org/... \
  || fail "could not download"

Use when: a pinned version vanishes from dlcdn — Apache deletes superseded releases there, which is the #1 way setup scripts rot.

Port 80 in one sed (Challenge 2)

The end goal URL has no port, so the HTTP Connector in server.xml moves from 8080 to 80 — and the edit is verified immediately, because a silent sed miss would only surface much later as a connection error.

sed -i 's/port="8080"/port="80"/' /opt/tomcat/conf/server.xml
grep -q 'port="80"' ... || fail "port edit failed"

Remember: ports below 1024 are privileged — binding 80 works here because Tomcat runs as root in this lab setup.

systemd, not cron @reboot (Challenge 4)

The unit file gives Tomcat journald logging, Restart=on-failure if it crashes, and clean systemctl control — the things the cron shortcut cannot do.

[Service]
Type=forking          # startup.sh spawns and exits
ExecStart=/opt/tomcat/bin/startup.sh
Restart=on-failure

Remember: Type=forking because startup.sh launches Tomcat and returns — systemd would otherwise think the service died.

Error checking, logging, verification

set -euo pipefail stops the script on the first failure, every critical step has an explicit check, all output tees to a log file, and the final loop polls the real URL instead of assuming success.

set -euo pipefail
exec > >(tee -a "$LOG_FILE") 2>&1
curl -sf http://localhost:80/helloWorld/ || retry...

Use when: the marker runs your script on a fresh instance — "it printed DONE and the URL answered" beats "it probably worked".

Note: deployment copies the WAR straight into webapps/, so the Tomcat manager user and IP-restriction steps are skipped on purpose — the lab's own note says a minimal server does not need them.

🧪 Prove it, then drill it

The acceptance test

Run the whole loop once, end to end, exactly the way it would be marked.

1. Launch a fresh AL2023 instance (SG: 22, 80)
2. sudo bash setup.sh          # watch the 8 stages
3. Open http://<public-ip>/helloWorld/
4. sudo reboot → page still answers (systemd)
5. Edit index.jsp, re-run script → change is live

Use when: before submitting — step 4 is the one people forget to test.

What you should be able to explain cold

Every line of the script is a likely question. If any of these is shaky, that is the card to reread above.

- why Java installs first, and why -devel
- why /etc/profile.d beats ~/.bash_profile
- why the script sources the profile itself
- why downloads fall back to archive.apache.org
- why Type=forking in the systemd unit
- what set -euo pipefail does, flag by flag
- why the script polls the URL at the end

Tip: open this page and run /grill-me — then rebuild the script from memory and diff it against this one.

Question: the script prints DONE but the browser times out from your laptop. The app answers on localhost from inside the instance. What is wrong, and which single AWS console screen proves it?
