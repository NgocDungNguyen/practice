🧭RMIT Store: End-to-End CI/CD

This is the master map for Assignment 2 delivery. Jenkins owns the pipeline order and the final result. Ansible owns the middle delivery stage: build both images, push their immutable tags, and deploy those exact tags. The end-to-end test runs only after the deployment is ready.

6 sections7 code blocks~8 min

🗺️ The complete path

One commit through the delivery system

developer pushes code
        |
        v
GitHub webhook starts Jenkins
        |
        v
1. Pull code
   Jenkins checks out the exact commit
        |
        v
2. Unit test
   temporary tests now, real team tests later
        |
        v
3. Ansible: build, push, deploy
   build API + frontend images
   push one immutable tag pair to private Docker Hub
   migrate and deploy the same pair to the target environment
        |
        v
4. E2E test
   exercise the deployed application through its public frontend
        |
        v
5. Result
   Jenkins publishes SUCCESS or FAILURE
   GitHub receives the Jenkins status
   the team receives failure email

Any failed stage stops every later stage and makes the Jenkins result red.
Prometheus and Grafana observe the deployed staging and production hosts.

Jenkins orchestrates the flow. GitHub stores the code and triggers Jenkins. Ansible builds, pushes, and deploys. Docker Hub stores the immutable images. Jenkins runs the post-deployment test and publishes the result.

Order is the gate: failed unit tests prevent Ansible from running. A failed Ansible task prevents E2E. A failed E2E test makes the final Jenkins result red.

🔧 The Jenkins stage order

Build this flow

Pull code
  -> Unit test
  -> Ansible: build, push, deploy
  -> E2E test
  -> Result

The unit and E2E commands are temporary placeholders for now. Keep them in separate stages so the testing teammate can replace each command without changing the delivery order.

What each gate proves

Unit test fails     -> no image build, push, or deployment
Ansible fails       -> no E2E test
E2E test fails      -> deployment happened, result is FAILURE
Every stage passes  -> result is SUCCESS

Do not combine the two tests. Unit tests run against the checked-out code before delivery. E2E tests run against the deployed application after delivery.

Next page: follow Jenkins Pipelines: Required flow, then use the Ansible and Swarm runbook for the build, push, and deploy playbook.

📦 The Jenkins to Ansible contract

Jenkins supplies

GIT_COMMIT=full source commit
IMAGE_TAG=immutable commit-based tag
TARGET_ENVIRONMENT=staging | production
WORKSPACE=checked-out source tree

Jenkins creates the tag from the checked-out commit and starts the Ansible stage only after unit tests pass.

Ansible completes

build API_IMAGE and FRONTEND_IMAGE from WORKSPACE
push both images with IMAGE_TAG
run the target database migration
deploy both images with the same IMAGE_TAG
wait until GIT_COMMIT is live

Ansible owns image build, registry push, and deployment. It returns a nonzero exit code if any task fails, which stops the Jenkins pipeline before E2E.

Rules that keep the handoff honest

  • Never deploy latest.
  • Run unit tests before the Ansible build starts.
  • Build on ansible-server, not on a Swarm node.
  • Never mix an API tag from one build with a frontend tag from another.
  • Do not overwrite a published release tag.
  • Run E2E only after Ansible confirms the expected commit is live.
  • Keep secrets out of the manifest, image, repository, and console log.

Artifact rule: Ansible builds each immutable tag once, pushes the pair, and deploys that same pair. A rerun may reuse the pair only after it verifies that both tags already exist.

🚦 Pull request and production paths

Pull request path

PR update
  -> Jenkins pulls the PR commit and runs unit tests
  -> Ansible builds, pushes, and deploys the exact PR tag to shared staging
  -> Jenkins runs E2E against staging
  -> Jenkins posts green or red status
  -> GitHub requires green status + one approval

Staging is shared. Check /api/version/ before manual testing because another PR may replace it.

Protected main path

human merges approved PR
  -> GitHub creates protected main push
  -> Jenkins pulls the merged commit and runs unit tests
  -> Ansible builds, pushes, and deploys the exact tag to production
  -> Jenkins runs the deployed-environment E2E checks
  -> Jenkins records the result

A failed production E2E check leaves the pipeline red and sends email. The operator decides whether to run the printed rollback command with the previous immutable tag.

Approval boundary: Jenkins reports the result. GitHub branch protection blocks the merge. A human approves and merges. Jenkins does not approve its own release.

📚 Runbooks and ownership

1 · Manual deployment baseline

RMIT Store: Manual Deploy proves the application path before automation. It covers local, EC2, RDS, S3, Docker, and Compose.

2 · Jenkins CI and orchestration

RMIT Store: Jenkins Pipelines installs the persistent Jenkins controller, connects GitHub, runs temporary unit tests, calls the Ansible build/push/deploy stage, runs temporary E2E tests, and records the result.

3 · Ansible and Docker Swarm

RMIT Store: Ansible and Docker Swarm prepares staging and production, builds and pushes immutable images, manages environment configuration, migrates the database, and deploys the exact tags.

4 · Failure notification

RMIT Store: Automated Alerting provides the Jenkins email configuration and reusable notify.groovy module.

5 · Runtime visibility

RMIT Store: Monitoring and Grafana adds health probes, host metrics, dashboards, and runtime alerts after the application environments exist.

Use this page as the index. Each detailed runbook owns its commands. When a command changes, update it in one place and keep this page focused on sequence and contracts.

✅ What complete means

Jenkins evidence

  • GitHub webhook delivery returns HTTP 200.
  • A deliberate failed unit test prevents the Ansible stage.
  • A passing unit test allows the Ansible stage to start.
  • Jenkins shows separate Ansible and E2E stages.
  • Jenkins records the final result and sends failure email.

CD evidence

  • Ansible builds and pushes both images with one immutable tag.
  • Ansible deploys the same tag it just pushed.
  • Staging and production use separate inventories, vaults, RDS data, and S3 buckets.
  • Migrations finish before the API service update.
  • E2E starts only after health and version checks prove the expected commit is live.

Operations evidence

  • Prometheus scrapes the application hosts and Jenkins.
  • Grafana shows the health and host dashboards.
  • A controlled failure sends the correct alert.
  • The team can identify and manually redeploy the previous immutable tag.

Finish line: one Jenkins run shows the whole order: pull code, unit test, Ansible build/push/deploy, E2E test, and final result.
