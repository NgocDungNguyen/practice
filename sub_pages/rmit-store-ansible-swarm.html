🐝RMIT Store: Ansible + Docker Swarm

This is page 1 of 2 for the teammate who owns app/ansible/. It covers the AWS setup, server setup, two Docker Swarms, and a manual deployment proof. Jenkins comes on page 2. You will keep staging and production apart. Each environment has one frontend manager and one backend worker. nginx is the only public app door. It listens on port 80 and sends API requests to the private api:8000 service over a Swarm overlay network.

10 sections53 code blocks~52 min

🎯 Overview — two small Swarms, one safe route

0.1 · The six EC2 instances and the five Elastic IPs

CONTROL BOXES, page 2                                                          Elastic IP
jenkins-server         t3.small    builds and pushes images                    yes
ansible-server         t3.small    runs every deployment                       no (private IP is enough)

STAGING SWARM, one node
staging                t3.small    manager   labels runs_frontend + runs_backend   public :80   yes

PRODUCTION SWARM, two nodes
production-frontend    t3.small    manager   label runs_frontend    public :80                  yes
production-backend     t3.small    worker    label runs_backend     no public :8000             yes

MONITORING, separate page
monitoring-server      t3.small    Prometheus + Grafana, scrapes :9100 on the three app boxes  yes

All six: Amazon Linux 2023, x86_64, same VPC. Learner Lab allows 5 Elastic IPs; ansible-server goes without.
Existing production frontend and backend boxes may be reused.

Two Swarms means two trust boundaries. A staging command cannot update a production service. Staging is a one-node Swarm: the same stack file, but both services land on the single node. Production keeps the manager + worker split.

Build and deploy sit on separate boxes. jenkins-server runs Docker and pushes images. ansible-server holds the SSH deploy key and the vault password and is the only box allowed to SSH into the three app hosts. The box with a root-equivalent Docker socket therefore has no path into production.

0.2 · Request path

browser
  |
  | HTTP :80
  v
frontend EC2 security group
  |
  v
nginx service on manager
  |-- /, /shop, assets  -> Vue files
  |
  |-- /api
  |-- /admin
  |-- /healthz
  |-- /readyz
          |
          | overlay network: rmit_store_app
          v
       api:8000 service on backend worker
          |
          |-- PostgreSQL :5432 -> RDS
          `-- product media     -> environment S3 bucket

The browser never calls port 8000. client/public/config.js stays API_BASE_URL: '/api'. This keeps one browser origin and removes the need for a public backend port.

0.3 · Who does what

jenkins-server, next page:
  test -> build -> push exact immutable tags to private Docker Hub

ansible-server, this page plus next page:
  install Docker -> form Swarm -> log in -> pull -> migrate -> deploy exact tag
  Jenkins runs this box as a build agent labelled "ansible"

Docker Swarm:
  place frontend where runs_frontend=true
  place API where runs_backend=true   (staging: same node; production: the worker)
  restart failed tasks and roll service updates

AWS console, once:
  EC2, security groups, IAM profile, RDS database/user, S3 bucket

Ansible does not build images. docker stack deploy does not build images either. It also ignores Compose depends_on. The migration gate must therefore be an explicit Ansible task before the API service update.

0.4 · Build once per commit, configure at run time

private Docker Hub, one exact pair per commit:
  DOCKERHUB_USER/rmit-store-api:IMAGE_TAG
  DOCKERHUB_USER/rmit-store-frontend:IMAGE_TAG

every image pair is environment-neutral
  |-- staging config comes from staging Ansible vars and vault
  `-- production config comes from production Ansible vars and vault

manual proof: one tag may run in both environments
Jenkins flow: merged main gets a new immutable production tag

/api/version/ must report:
  APP_VERSION = IMAGE_TAG
  GIT_COMMIT  = the commit used to build IMAGE_TAG

Never use latest. An exact tag tells you what is running and gives Jenkins a stable input for a later rollback feature.

Checkpoint: draw two boxes around the two Swarms. Staging holds one node that runs both services. Production holds one frontend manager and one backend worker. Only frontend port 80 is public. jenkins-server and ansible-server both sit outside the clusters and come next.

☁️ Step 1 — Create the EC2 boxes and exact network rules

1.1 · Launch settings

Where: AWS console → EC2 → Instances → Launch instances. This page keeps AWS provisioning manual. It does not add CloudFormation.

Name                    Type         AMI
----------------------  -----------  --------------------------
jenkins-server          t3.small     Amazon Linux 2023, x86_64
ansible-server          t3.small     Amazon Linux 2023, x86_64
staging                 t3.small     Amazon Linux 2023, x86_64   (api + frontend on one node)
production-frontend     t3.small     Amazon Linux 2023, x86_64
production-backend      t3.small     Amazon Linux 2023, x86_64
monitoring-server       t3.small     Amazon Linux 2023, x86_64   (see the Monitoring page)

Network:       same VPC as the existing RDS instance
Key pair:      the team deployment key pair
Storage:       16 GiB gp3 for each app box and ansible-server
               30 GiB gp3 for jenkins-server, it stores images
Public IPv4:   enabled for this Learner Lab design
Backend IAM:    LabInstanceProfile or LabRole on staging and production-backend (they run the API)
Control IAM:    none needed; deployment uses static inventory

Reuse the two current production boxes if they match. Do not rebuild a working production server just to change its name. Add clear Name and Environment tags.

Record two addresses per app box. Inventory uses the public IP for SSH from a laptop. Swarm uses the private IP for cluster traffic. Allocate the five Elastic IPs to jenkins-server, staging, production-frontend, production-backend and monitoring-server, so the committed inventories never go stale. ansible-server keeps an auto-assigned public IP: Jenkins reaches it by private IP, and you only need its public IP for your own SSH.

1.2 · Staging security group

Create one staging-sg. Add each line as an inbound rule. Keep default outbound all traffic.

staging-sg
  TCP 22     source TEAM_PUBLIC_IP/32       teammate SSH
  TCP 22     source ansible-server-sg       automated deploys later
  TCP 80     source 0.0.0.0/0               public store
  TCP 9100   source MONITORING_IP/32        node_exporter for the Monitoring page

No inbound TCP 8000 rule.
No 2377 / 7946 / 4789 rules: a one-node Swarm talks to itself on loopback.

One node, no cluster ports. The overlay network still exists inside the node, so nginx reaches api:8000 by service name exactly like production. Nothing about the stack file changes between the two environments.

1.3 · Production security groups

Create or update production-frontend-sg and production-backend-sg.

production-frontend-sg
  TCP 22     source TEAM_PUBLIC_IP/32
  TCP 22     source ansible-server-sg
  TCP 80     source 0.0.0.0/0
  TCP 9100   source MONITORING_IP/32          node_exporter
  TCP 2377   source production-backend-sg
  TCP 7946   source production-backend-sg
  UDP 7946   source production-backend-sg
  UDP 4789   source production-backend-sg

production-backend-sg
  TCP 22     source TEAM_PUBLIC_IP/32
  TCP 22     source ansible-server-sg
  TCP 9100   source MONITORING_IP/32          node_exporter
  TCP 7946   source production-frontend-sg
  UDP 7946   source production-frontend-sg
  UDP 4789   source production-frontend-sg

No inbound TCP 8000 rule.

If a reused production box still serves the old split-host design on public port 8000, keep that old rule only while you build the new path. Remove it after Step 8 proves the nginx proxy. The final state has no public 8000.

Port 2377 belongs on the manager only. The worker starts that connection. Ports 7946 and 4789 are needed in both directions. Source MONITORING_IP/32 is the monitoring box's Elastic IP; a security-group source only matches if that box really wears the group, the /32 always does.

1.4 · RDS and control-box rules

rds-sg
  TCP 5432   source staging-sg
  TCP 5432   source production-backend-sg
  Public access: No
  No 0.0.0.0/0 rule

jenkins-server-sg
  TCP 22     source TEAM_PUBLIC_IP/32
  TCP 8080   source TEAM_PUBLIC_IP/32
  TCP 8080   source each current GitHub webhook CIDR
  TCP 8080   source MONITORING_IP/32          Prometheus reads /prometheus

ansible-server-sg
  TCP 22     source TEAM_PUBLIC_IP/32       teammate SSH
  TCP 22     source jenkins-server-sg       Jenkins launches the agent
  no other inbound rule

app box SSH rules
  use one TEAM_PUBLIC_IP/32 rule per teammate if needed
  add ansible-server-sg as a separate source rule

Port 8080 and the Ansible group are listed now so the six-box map is complete. monitoring-sg itself (22 from you, 3000 public) is on the Monitoring page. The next page shows how to get GitHub's current webhook CIDRs and set up Jenkins authentication, the webhook secret, credentials, and the Ansible agent. If the Learner Lab cannot hold every GitHub range, opening 8080 to 0.0.0.0/0 is a recorded temporary fallback, not the preferred final rule.

SSH flows one way only. Jenkins opens port 22 on ansible-server, and ansible-server opens port 22 on the three app boxes. Nothing lets jenkins-server reach an app box directly. RDS still accepts only the two groups that run the API, so neither control box can query the database and migrations run on the node that runs the API.

1.5 · Let backend containers use the IAM role

On staging and production-backend (the two boxes that run the API), open Actions → Security → Modify IAM role. Select the Learner Lab instance profile for LabRole. Then open Actions → Instance settings → Modify instance metadata options.

Instance metadata service:    Enabled
IMDSv2:                       Required
Metadata response hop limit:  2

Why hop limit 2: boto3 runs inside the API container. It needs one extra network hop to read temporary role credentials. Do not put AWS access keys in a vault or environment file.

Checkpoint: the three app boxes are running in one VPC. Frontends expose 80. No box exposes 8000. The production pair has only 2377, 7946, and 4789 between the two of them; staging has no cluster ports at all. Every app box has 9100 from MONITORING_IP/32. RDS 5432 accepts only staging-sg and production-backend-sg. App-box SSH now names ansible-server-sg, not jenkins-server-sg.

🗄️ Step 2 — Split RDS and S3 by environment

2.1 · Keep the production database

Existing RDS PostgreSQL instance
  production database: rmit_store
  production login:    RMIT_PRODUCTION_APP_USER

Add on the same RDS instance
  staging database:    rmit_store_staging
  staging login:       rmit_staging_app

The production and staging login names and passwords must differ. Do not let staging use the RDS master user. Do not give either app user CREATEDB, CREATEROLE, or superuser rights.

2.2 · Create the staging database and login once

Where: SSH to staging. Install only the PostgreSQL client. Connect with the RDS master login for this one setup step.

sudo dnf install -y postgresql16

psql \
  -h RDS_ENDPOINT \
  -U RDS_MASTER_USER \
  -d postgres \
  -W

At the postgres=> prompt, replace the placeholder password. Keep the quotes.

CREATE ROLE rmit_staging_app
  LOGIN
  PASSWORD 'STAGING_DB_PASSWORD'
  NOSUPERUSER
  NOCREATEDB
  NOCREATEROLE;

CREATE DATABASE rmit_store_staging
  OWNER rmit_staging_app;

REVOKE ALL ON DATABASE rmit_store_staging FROM PUBLIC;
GRANT CONNECT, TEMPORARY ON DATABASE rmit_store_staging TO rmit_staging_app;
\q

The app user owns only its database. Django migrations can create and change tables there. It cannot create another database or manage RDS roles.

2.3 · Check the production login is not the RDS master

Keep the existing rmit_store data. Check the login the app uses now.

# on production-backend
psql -h RDS_ENDPOINT -U RMIT_PRODUCTION_APP_USER -d rmit_store -W \
  -c "select current_user, current_database();"

# the result must be the dedicated production app user,
# not RDS_MASTER_USER

If production still uses the RDS master login, stop before changing ownership. Take an RDS snapshot. Create a login with no CREATEDB, CREATEROLE, or superuser rights. Then transfer ownership of the Django database objects during a maintenance window. Existing table owners differ between installations, so a blind GRANT block is not safe here. Test that change in staging first.

Django migrations need object ownership. Read-only or table-data grants are not enough for schema changes. The final production vault must contain a dedicated app URL, never the RDS master URL.

2.4 · Test both app logins from the right boxes

# on staging
psql -h RDS_ENDPOINT -U rmit_staging_app -d rmit_store_staging -W \
  -c "select current_user, current_database();"

# on production-backend
psql -h RDS_ENDPOINT -U RMIT_PRODUCTION_APP_USER -d rmit_store -W \
  -c "select current_user, current_database();"

Each command should print the matching user and database. A timeout points to the RDS security group. password authentication failed points to the login or password.

Do not test with the master user. A successful master login does not prove the least-privilege app login works.

2.5 · Create a separate staging S3 bucket

Where: AWS console → S3 → Create bucket.

staging bucket:     RMIT_STORE_STAGING_BUCKET
production bucket: RMIT_STORE_PRODUCTION_BUCKET   # keep the existing bucket
region:             AWS_REGION                     # same region as the app
versioning:         enable if Learner Lab allows it

Public read:
  copy the production media policy only if the current app needs public object URLs
Write and delete:
  backend instances use LabRole, never access keys

Bucket names are global. Pick a team-specific staging name. Do not reuse the production bucket. A staging seed or upload must never change production media.

Check the role on each backend: aws sts get-caller-identity should show the lab role. Then aws s3 ls s3://RMIT_STORE_STAGING_BUCKET should work on staging.

Checkpoint: staging has its own database, app login, password, and S3 bucket. Production keeps separate values. Both backend boxes can reach only their intended data with an app login and temporary IAM role credentials.

3.3 · Complete ansible/inventories/staging.ini

[swarm_managers]

[swarm_nodes:children]
swarm_managers
swarm_workers

Use public IPs for ansible_host. Use private IPs for swarm_advertise_addr. ansible-server sits in the same VPC, so it can reach either address and the one committed inventory works from a laptop and from the agent.

3.4 · Complete ansible/inventories/production.ini

[swarm_managers]
production-frontend ansible_host=PRODUCTION_FRONTEND_IP swarm_advertise_addr=PRODUCTION_FRONTEND_PRIVATE_IP

[swarm_workers]

Both inventory files use the same group names, so the same roles and plays run against either. The only difference is that staging's [swarm_workers] is empty. The -i argument chooses one cluster at a time.

-i overrides ansible.cfg. This matters because the existing config still points at inventory.ini.

3.6 · Separate encrypted vault files

Create the files with ansible-vault create. Paste only the matching shape into each editor. Replace every placeholder there, not in this guide.

# ansible/group_vars/vault-staging.yml, encrypted after save
---
vault_django_secret_key: STAGING_DJANGO_SECRET
vault_database_url: postgres://rmit_staging_app:URL_ENCODED_STAGING_DB_PASSWORD@RDS_ENDPOINT:5432/rmit_store_staging
vault_dockerhub_token: STAGING_OR_SHARED_READ_ONLY_DOCKERHUB_TOKEN

# ansible/group_vars/vault-production.yml, encrypted after save
---
vault_django_secret_key: DIFFERENT_PRODUCTION_DJANGO_SECRET
vault_database_url: postgres://RMIT_PRODUCTION_APP_USER:URL_ENCODED_PRODUCTION_DB_PASSWORD@RDS_ENDPOINT:5432/rmit_store
vault_dockerhub_token: PRODUCTION_OR_SHARED_READ_ONLY_DOCKERHUB_TOKEN
cd app
ansible-vault create ansible/group_vars/vault-staging.yml
ansible-vault create ansible/group_vars/vault-production.yml

head -1 ansible/group_vars/vault-staging.yml
head -1 ansible/group_vars/vault-production.yml

Checkpoint: two inventory files select one Swarm each. Two non-secret files name the correct S3 bucket and frontend. Two real vault files start with $ANSIBLE_VAULT. Old roles and site.yml still exist.

🐳 Step 4 — Build the manager and worker roles

4.1 · Complete ansible/roles/swarm_manager/tasks/main.yml

---
- name: Install Python tools for Docker modules
  ansible.builtin.dnf:
    name: python3-pip
    state: present

- name: Install Docker SDK for Python
  ansible.builtin.pip:
    name: docker
    state: present

- name: Create or keep the single-manager Swarm
  community.docker.docker_swarm:
    state: present
    advertise_addr: "{{ swarm_advertise_addr }}"
  register: swarm_manager_result
  no_log: true

- name: Label the manager for frontend placement
  community.docker.docker_node:
    hostname: "{{ ansible_hostname }}"
    labels:
      runs_frontend: "true"
    labels_state: merge

- name: Also label the manager for backend placement when there is no worker
  community.docker.docker_node:
    hostname: "{{ ansible_hostname }}"
    labels:
      runs_backend: "true"
    labels_state: merge
  when: groups['swarm_workers'] | default([]) | length == 0

- name: Keep the worker join token in memory
  ansible.builtin.set_fact:
    swarm_worker_join_token: "{{ swarm_manager_result.swarm_facts.JoinTokens.Worker }}"
  no_log: true

community.docker.docker_swarm is idempotent. It creates a Swarm only when the host is not already a manager. The token stays in Ansible memory and is hidden from output. Two boolean labels instead of one app_role value let a single node carry both roles: staging gets both labels, production splits them.

One manager is deliberate but not highly available. If the frontend manager dies, Swarm control and the public site stop. Record this in the report.

4.2 · Complete ansible/roles/swarm_worker/tasks/main.yml

---
- name: Install Python tools for Docker modules
  ansible.builtin.dnf:
    name: python3-pip
    state: present

- name: Install Docker SDK for Python
  ansible.builtin.pip:
    name: docker
    state: present

- name: Join or keep the worker in this Swarm
  community.docker.docker_swarm:
    state: join
    advertise_addr: "{{ swarm_advertise_addr }}"
    join_token: "{{ hostvars[groups['swarm_managers'][0]].swarm_worker_join_token }}"
    remote_addrs:
      - "{{ hostvars[groups['swarm_managers'][0]].swarm_advertise_addr }}:2377"
  no_log: true

- name: Label the worker for backend placement
  community.docker.docker_node:
    hostname: "{{ ansible_hostname }}"
    labels:
      runs_backend: "true"
    labels_state: merge
  delegate_to: "{{ groups['swarm_managers'][0] }}"

If a host already belongs to the wrong Swarm, this role should fail. Do not make it run docker swarm leave --force by itself. Confirm the host and environment first, then leave the wrong cluster by hand.

The worker connects to the manager's private IP. That is why port 2377 accepts only the matching backend security group.

4.3 · Required collection file

Create a new ansible/requirements.yml. The known baseline does not have this file. Its complete content is:

---
collections:
  - name: community.docker
    version: ">=3.10.0,<5.0.0"
cd app/ansible
ansible-galaxy collection install -r requirements.yml
ansible-galaxy collection list | grep community.docker

Run this on the Ansible control machine. The roles install the Python Docker SDK on EC2. The collection itself runs on your laptop now and inside the ansible-server virtual environment later, so page 2 installs the same requirements.yml there.

4.4 · Why these roles can be run twice

first run:
  Docker SDK installed
  manager creates Swarm
  worker joins
  labels added

second run:
  packages present
  same Swarm kept
  same membership kept
  same labels kept

join token:
  no_log hides it
  never save it in git, inventory, vault, or a screenshot

Module state drives the result. There is no hand-written parsing of docker swarm init output, so a change in its human text does not break the play.

Checkpoint: the manager role creates one manager, labels it runs_frontend (and runs_backend too when the inventory has no worker), and keeps the join token hidden. The worker role joins one private manager address and labels itself runs_backend. A second run should not recreate the Swarm.

🧱 Step 5 — Define the stack, nginx proxy, and migration rule

5.1 · Change the API entrypoint behavior safely

The current app/entrypoint.sh runs python manage.py migrate before gunicorn. With two API replicas, both replicas would run migrations again during each update.

current image entrypoint:
  migrate -> gunicorn

safe Swarm path in this guide:
  Ansible one-off container on backend -> migrate once
  Swarm API service entrypoint override -> gunicorn only

later clean-up:
  edit app/entrypoint.sh so it starts gunicorn only
  keep migration only in ansible/roles/swarm_deploy/tasks/main.yml

The stack below overrides the image entrypoint with gunicorn. The one-off migration task uses --entrypoint python. If migration exits nonzero, Ansible stops before docker stack deploy.

This is the safe practical bridge. It works with the current image and prevents every replica from migrating. The later entrypoint clean-up makes that policy easier to see.

5.2 · Complete proposed root app/nginx.conf

Jenkins will bake this file into the frontend image. Docker DNS resolves the service name api on the overlay network.

server {
    listen 80;
    server_name _;
    root /usr/share/nginx/html;
    index index.html;
    client_max_body_size 10M;

    resolver 127.0.0.11 valid=10s ipv6=off;
    set $api_upstream http://api:8000;

    location / {
        try_files $uri $uri/ /index.html;
    }

    location = /config.js {
        add_header Cache-Control "no-store";
    }

    location /assets/ {
        add_header Cache-Control "public, max-age=31536000, immutable";
    }

    location ~ ^/(api|admin|static|healthz|readyz)(/|$) {
        proxy_pass $api_upstream;
        proxy_set_header Host              $host;
        proxy_set_header X-Forwarded-Host  $host;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_redirect off;
    }
}

/api/version/ matches the /api route. nginx forwards the original path. The resolver lets nginx recover if the API task address changes.

5.3 · Keep client/public/config.js on one origin

window.__APP_CONFIG__ = {
  API_BASE_URL: '/api'
}

No staging IP and no production IP belongs in the frontend image. The browser always asks the same host for /api. nginx chooses the private service.

Same image in both environments. Do not mount a different config.js for each Swarm. The relative path is already the correct runtime setting.

5.4 · Complete ansible/roles/swarm_deploy/templates/api.env.j2

5.6 · Secret limit to state in the report

Ansible Vault encrypts secrets in git. The rendered migration env file is mode 0600. Swarm service environment values are still visible to a Swarm manager through service inspection.

protected:
  vault files in git
  token output in Ansible logs
  migration env file permissions

not fully protected:
  service environment from a Swarm manager

future hardening:
  add Docker secret files
  teach the app to read SECRET_KEY_FILE and DATABASE_URL_FILE

Do not claim Docker Secrets are implemented. The current app reads normal environment variables. Vault is still a clear improvement, but manager access remains privileged.

Checkpoint: nginx forwards API, admin, static, health, and readiness paths to api:8000. The stack publishes only frontend port 80. It pulls two exact tags, constrains both services by node label, and overrides the API entrypoint so replicas do not migrate.

  community.docker.docker_login:

  no_log: true

- name: Deploy exact API and frontend tags

      - docker
      - stack
      - deploy

      - --prune
      - --compose-file

  environment:

    stack_template.changed or
    api_env_template.changed or
    (dockerhub_user + '/rmit-store-api:' + image_tag) not in stack_before.stdout or
    (dockerhub_user + '/rmit-store-frontend:' + image_tag) not in stack_before.stdout
  failed_when: stack_deploy.rc != 0
  no_log: true

  ansible.builtin.uri:
    url: "{{ frontend_origin }}/readyz/"
    method: GET
    status_code: 200
    return_content: true
  register: rollout_ready
  until: (rollout_ready.status | default(0)) == 200
  retries: 30
  delay: 10
  delegate_to: localhost
  become: false
  changed_when: false

- name: Wait for the deployed commit through the public frontend
  ansible.builtin.uri:
    url: "{{ frontend_origin }}/api/version/"
    method: GET
    status_code: 200
    return_content: true
  register: rollout_version
  until:

    - git_commit in (rollout_version.content | default('')) or
      git_commit[0:8] in (rollout_version.content | default(''))
  retries: 30
  delay: 10
  delegate_to: localhost
  become: false
  changed_when: false

- name: Assert the public version is the requested commit
  ansible.builtin.assert:
    that:
      - git_commit in rollout_version.content or
        git_commit[0:8] in rollout_version.content
    fail_msg: "/api/version/ did not report the requested git_commit."
  delegate_to: localhost
  become: false

- name: Show deployed services without secrets
  ansible.builtin.command:
    cmd: docker stack services {{ stack_name }}
  register: stack_services
  changed_when: false

- name: Print deployed service table
  ansible.builtin.debug:
    var: stack_services.stdout_lines

The migration runs on backend_node: the worker in production, the single manager in staging. Only those security groups can reach RDS. The manager logs in separately so --with-registry-auth can pass private registry auth to Swarm tasks.

The two uri tasks run from the Ansible control node, your laptop now and ansible-server once page 2 is wired, not from an EC2 target. They wait up to five minutes for readiness and the requested commit through nginx. The role returns only after the public rollout is ready and /api/version/ contains the full git_commit or its first eight characters.

Failure stops the play. A nonzero migration result prevents the stack command from running. A rollout or version timeout also fails the role. Output text can differ by Docker version, so proof comes from service state and public HTTP checks.

6.4 · Schema safety limit

The migration-first order stops a bad migration from starting new API tasks. It does not make every schema change safe while the old API is still serving.

safe future pattern:
  release A: add new nullable column or new table
  release B: write both old and new shape
  release C: stop reading old shape
  later:     remove old column

risky in one release:
  rename or drop a column while old API tasks still use it

Backward-compatible migrations are future work. State this limit. Do not claim zero-downtime schema migration until the team tests an expand-and-contract process.

Checkpoint: migration runs once on the backend worker with the new API image. A failure blocks service update. After deployment, the control runner waits for public readiness and the requested commit before the role returns. No task output reveals a token, database URL, or Django key.

9.5 · Contract for the Jenkins page

Jenkins runs the playbook on ansible-server,
its build agent labelled "ansible", and supplies:
  ansible/inventories/staging.ini or production.ini
  target_environment
  image_tag
  git_commit
  app_version
  SSH private key file
  Ansible vault password file

  ansible/group_vars/vault-staging.yml
  ansible/group_vars/vault-production.yml

PR pipeline:
  test the pull request
  build and push an immutable PR commit tag
  call staging.ini + target_environment=staging

Production pipeline after approved merge:
  check out the merged main commit
  build and push a new immutable merged-main tag
  call production.ini + target_environment=production

Both call:
  ansible/site-swarm.yml
  -e image_tag=EXACT_TAG
  -e git_commit=FULL_COMMIT
  -e app_version=RELEASE_VERSION

Inventory:
  static staging.ini and production.ini
  no AWS inventory discovery
  no control-box EC2 IAM role needed for inventory

Boundary:
  jenkins-server never SSHes into an app box
  ansible-server never builds or pushes an image

The PR and merged main builds may have different tags and commits. Both images remain environment-neutral. Staging and production database, bucket, host, and secret values come from Ansible, never from an image build.
