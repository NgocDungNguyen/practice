📈RMIT Store: Monitoring & Grafana

Core requirement "monitoring and alerting with useful dashboards" — built as a third small EC2 box running Prometheus and Grafana in Docker Compose. It probes the API's /healthz/ and /readyz/, the website's front page, reads CPU / RAM / disk from both app servers, and later Jenkins too. Dashboards and alert rules are files in the repo, not clicks. Alerts email the same team Gmail the Jenkins alerting module uses. You build it by hand first, prove it, then hand the Ansible owner two tiny roles.

9 sections46 code blocks~62 min

🎯 What you are building, and how the pieces talk

The requirement, in one line

Section 2 of the requirements: monitoring and alerting. Prometheus / Grafana / CloudWatch are all acceptable. The app already exposes /healthz/ (is the process alive) and /readyz/ (can it reach the database and S3). You must alert on failed checks, error rates and resource use. The rubric adds: useful dashboards.

monitoring (new t3.small)        stg-server (api + web)     prd-api-server        prd-frontend-server
-------------------------        ----------------------     ---------------       -------------------
prometheus :9090  pulls  ────►   node_exporter :9100        node_exporter :9100   node_exporter :9100
blackbox   :9115  probes ────►   api :8000/healthz/         api :8000/healthz/    web :80/
                                 api :8000/readyz/          api :8000/readyz/
                                 web :80/
grafana    :3000  reads prometheus, draws dashboards, fires alerts ──► team Gmail

                         ────►   jenkins :8080/prometheus   (Step 7)

5 Elastic IPs total: jenkins, prd-api, prd-frontend, monitoring, stg (one box runs both api and web).
ansible-master has none and is not monitored; it only makes outgoing SSH calls.

Pull, not push. Prometheus scrapes: every 15 seconds it asks each target "give me your numbers". Nothing on the app boxes knows Grafana exists. That is why the monitoring box needs to reach the others, and why the security-group rules in Step 1 matter.

Four words you will see a lot

Prometheus is the database of numbers over time. Exporter is any small program that turns something into numbers Prometheus can read: node_exporter reads the Linux host (CPU, RAM, disk), blackbox_exporter does an HTTP request to a URL and reports "did it answer 200, and how fast". Grafana draws the numbers and, since version 9, also evaluates alert rules and sends email, so no separate Alertmanager is needed. Provisioning is Grafana's word for "read datasources, dashboards and alert rules from files at boot".

metric          example                                      who produces it
--------------  -------------------------------------------  ---------------------
probe_success   probe_success{probe="api-healthz"} 1         blackbox_exporter
probe_duration  probe_duration_seconds{...} 0.043             blackbox_exporter
node_cpu_...    node_cpu_seconds_total{mode="idle"} 91234     node_exporter
node_memory_..  node_memory_MemAvailable_bytes 1.2e9          node_exporter
up              up{job="jenkins"} 1                          Prometheus itself (did the scrape work)

Every metric is a name plus labels. probe_success{probe="api-healthz"} reads as "the probe_success number for the probe we labelled api-healthz". Alert rules and dashboard panels are just questions about these.

What goes in the repo

All of it lives under a new monitoring/ folder at the repo root, next to server/, client/ and jenkins/. Plus two Ansible roles for the teammate who owns ansible/.

monitoring/

├── .env.example  # names of the secrets; real .env is gitignored
├── README.md  # hand-off for the Ansible owner (Step 6)
├── prometheus/
│   └── prometheus.yml  # what to scrape (edit the IPs)
├── blackbox/

└── grafana/
    ├── provisioning/
    │   ├── datasources/prometheus.yml

    │   └── alerting/

    │       ├── policies.yml  # everything goes to that email

Security groups: every door you must open, all boxes

One table to check against the AWS console. Only the new rules are listed; the ones you already have (22, 80, 8000, 5432) stay as they are. Source MONITORING_IP/32 means only the monitoring box may knock, not the internet. (Using "source = monitoring-sg" looks tidier, but it only matches if the monitoring instance really wears that group. The /32 always works.)

security group       new inbound rule            source           why
------------------   -------------------------   --------------   -------------------------------------------
monitoring-sg (new)  TCP 22                      My IP              SSH for you
monitoring-sg (new)  TCP 3000                    0.0.0.0/0          Grafana UI (has its own login)
stg box's sg         TCP 9100                    MONITORING_IP/32   node_exporter: CPU / RAM / disk of the stg box
prd-api-sg           TCP 9100                    MONITORING_IP/32   node_exporter of the prd API box
prd-frontend-sg      TCP 9100                    MONITORING_IP/32   node_exporter of the prd FE box
jenkins-sg           TCP 8080                    MONITORING_IP/32   Jenkins /prometheus metrics (Step 7, later)

NOT needed:  9090 (Prometheus) and 9115 (blackbox) stay closed; Grafana talks to them inside Docker.
             8000 (API) and 80 (FE) are already open to the world, so the health probes need nothing new.

How to add one: EC2 → Security Groups → pick the group → Edit inbound rules → Add rule → Type "Custom TCP", Port, Source "Custom", type MONITORING_IP/32 (no trailing dot) and press Enter, remove any 0.0.0.0/0 chip → Save. Details in Step 1.

The decisions already made, so you do not re-decide them at 1 am. Prometheus + Grafana, not CloudWatch (better dashboards, and Learner Lab IAM is limited). A third box, so monitoring survives an API outage. Separate compose file and its own Ansible role, so the app deploy is untouched. Grafana's built-in alerting, no Alertmanager. Minimum scope first: health probes, host metrics, one dashboard, six alerts. cAdvisor and error-rate metrics are "future work" in the report.

☁️ Step 1 — AWS console: the box and the doors

1.1 · Security group monitoring-sg

Where: AWS console → EC2 → Security Groups → Create security group.

Name          monitoring-sg
Description   Prometheus + Grafana box
VPC           the default one (same as your app boxes)

Inbound rules
  SSH          TCP 22     Source: My IP
  Custom TCP   TCP 3000   Source: Anywhere-IPv4 (0.0.0.0/0)  # Grafana UI, has its own login

Outbound       leave the default (all traffic)

Why 3000 to the world: Grafana has a login page, anonymous access will be off, and you want teammates and the marker to open it. Prometheus (9090) is not opened: Grafana reaches it inside Docker.

1.2 · Open the exporter port on the three app boxes

Where: EC2 → Instances → click the box → Security tab → click its security group → Edit inbound rules → Add rule. Do it for stg, prd-api and prd-frontend. Go through the Instances tab so you edit the group the box actually wears.

stg box's sg     add:  Custom TCP  9100   Source: Custom  MONITORING_IP/32
prd-api-sg       add:  Custom TCP  9100   Source: Custom  MONITORING_IP/32
prd-frontend-sg  add:  Custom TCP  9100   Source: Custom  MONITORING_IP/32

later, when Jenkins has its box (Step 7):
jenkins-sg       add:  Custom TCP  8080   Source: Custom  MONITORING_IP/32

/32 means "this one address only". Nobody on the internet can read your host metrics. Type it with no trailing dot, press Enter so it becomes a chip, and remove any 0.0.0.0/0 chip the console added. Ports 8000 and 80 are already public, so the blackbox probes need nothing new.

1.3 · Launch monitoring-server

Where: EC2 → Instances → Launch instances. Same recipe as the api-server in Plan C of the manual-deploy page.

Name              monitoring-server
AMI               Amazon Linux 2023 (x86_64)
Instance type     t3.small  # 2 GB RAM. t3.micro (1 GB) will swap with Prometheus + Grafana
Key pair          your existing .pem  (the one for your app boxes)
Network           Select existing security group -> monitoring-sg
Storage           16 GiB gp3  # Prometheus keeps 15 days of data by default
IAM role          none needed

Optional but wise: allocate an Elastic IP and associate it, exactly like C4 on the manual-deploy page. Otherwise the public IP changes every time the Learner Lab restarts and your Grafana link goes stale.

Write down four addresses now: the monitoring box (MONITORING_IP), the staging box (STG_IP), and the two prod boxes (PRD_API_IP, PRD_FE_IP). You will paste them into files in Step 2. They are Elastic IPs, so they are safe to commit.

1.4 · Docker on the new box

Where: your laptop terminal, then the monitoring box. Same as Step E of the manual-deploy page, and the same as the docker_engine Ansible role.

# laptop
ssh -i ~/Downloads/your-key.pem ec2-user@MONITORING_IP

# monitoring-server
sudo dnf update -y  # refresh + upgrade packages (dnf = the package manager on AL2023)
sudo dnf install -y docker git  # install Docker engine and git
sudo systemctl enable --now docker  # start Docker now AND on every boot
sudo usermod -aG docker ec2-user  # let ec2-user run docker without sudo (-aG = append to group)
sudo mkdir -p /usr/local/lib/docker/cli-plugins  # the folder where docker looks for "docker compose" etc.
sudo curl -SL https://github.com/docker/compose/releases/latest/download/docker-compose-linux-x86_64 \
     -o /usr/local/lib/docker/cli-plugins/docker-compose  # download the compose plugin binary there
sudo chmod +x /usr/local/lib/docker/cli-plugins/docker-compose  # make it runnable
exit  # log out and back in so the docker group applies

# laptop, again
ssh -i ~/Downloads/your-key.pem ec2-user@MONITORING_IP
docker compose version  # prints a version: good

Amazon Linux 2023 has no docker-compose-plugin package, hence the manual download into the CLI plugins folder. usermod -aG docker only takes effect after a fresh login, so the exit is not optional.

Checkpoint: you can SSH into monitoring-server, docker compose version works, and the three security groups have the rules above. Nothing else is installed yet.

2.2 · monitoring/docker-compose.yml

Three services on one private Docker network. Only Grafana publishes a port to the host. Versions are pinned so it builds the same next month.

# monitoring/docker-compose.yml
# Prometheus + blackbox_exporter + Grafana for the RMIT Store.
# Secrets come from ./.env (gitignored) - see .env.example.

services:  # each entry below = one container
  prometheus:
    image: prom/prometheus:v2.55.1  # which image to run; pinned so it never changes under you
    container_name: prometheus  # fixed name, so "docker logs prometheus" works
    restart: unless-stopped  # come back after a reboot / Learner Lab restart
    command:  # flags passed to the prometheus binary
      - --config.file=/etc/prometheus/prometheus.yml  # where the config is INSIDE the container
      - --storage.tsdb.retention.time=15d  # keep 15 days of numbers, then delete old ones
    volumes:  # host path : container path
      - ./prometheus/prometheus.yml:/etc/prometheus/prometheus.yml:ro  # our config, read-only
      - prometheus_data:/prometheus  # named volume: the data survives "compose down"
  # no ports: Grafana reaches it on the compose network as http://prometheus:9090

  blackbox:
    image: prom/blackbox-exporter:v0.25.0  # the "go poke a URL and report 200/not-200" tool
    container_name: blackbox
    restart: unless-stopped
    volumes:
      - ./blackbox/blackbox.yml:/etc/blackbox_exporter/config.yml:ro  # its one config file (the http_2xx module)
  # no ports: only Prometheus talks to it

  grafana:
    image: grafana/grafana:11.3.0
    container_name: grafana
    restart: unless-stopped
    ports:
      - "3000:3000"  # host port 3000 -> container port 3000; the ONLY door open to the outside
    environment:  # Grafana reads all GF_* variables as settings
      GF_SERVER_ROOT_URL: "http://${MONITORING_HOST}:3000"  # public URL; used for links inside alert emails
      GF_SECURITY_ADMIN_USER: admin  # login name of the one admin account
      GF_SECURITY_ADMIN_PASSWORD: "${GRAFANA_ADMIN_PASSWORD}" # its password, from .env
      GF_AUTH_ANONYMOUS_ENABLED: "false"  # no peeking without logging in
      GF_USERS_ALLOW_SIGN_UP: "false"  # nobody can make themselves an account
  # email - same Gmail account and app password as jenkins/casc/alerting.yaml
      GF_SMTP_ENABLED: "true"  # turn the mailer on
      GF_SMTP_HOST: "smtp.gmail.com:587"  # Gmail's mail server, STARTTLS port
      GF_SMTP_USER: "${GMAIL_USER}"  # login = the team Gmail address
      GF_SMTP_PASSWORD: "${GMAIL_APP_PASSWORD}"  # the 16-char app password, from .env
      GF_SMTP_FROM_ADDRESS: "${GMAIL_USER}"  # "From:" on the emails
      GF_SMTP_FROM_NAME: "RMIT Store Monitoring"  # display name next to the From address
  # read by provisioning/alerting/contact-points.yml
      ALERT_EMAILS: "${ALERT_EMAILS}"  # who gets the alerts (not a GF_ setting, our own)
    volumes:
      - ./grafana/provisioning:/etc/grafana/provisioning:ro  # datasource + dashboards list + alert rules (files -> Grafana at boot)
      - ./grafana/dashboards:/var/lib/grafana/dashboards:ro  # the dashboard JSON files themselves
      - grafana_data:/var/lib/grafana  # Grafana's own database (login sessions etc.)
    depends_on:
      - prometheus  # start prometheus first

volumes:  # declare the named volumes used above
  prometheus_data:
  grafana_data:

Port 587 with STARTTLS is what Grafana's mailer likes best. Jenkins used 465 with SSL. Same Gmail account, same app password, different door. ${NAME} values come from .env in the same folder; Compose fills them in.

2.4 · monitoring/prometheus/prometheus.yml

Three jobs now, a fourth waiting for Jenkins. Every target carries two labels: env (stg or prod) and either host or probe. The alert rules and dashboard match on probe, so one rule covers both envs and the email says which one broke.

# monitoring/prometheus/prometheus.yml
# Replace STG_IP, PRD_API_IP and PRD_FE_IP with the Elastic IPs of your boxes
# (they do not change, so real IPs in git are fine; the Ansible role templates them anyway).

global:
  scrape_interval: 15s  # how often to go and collect numbers from every target
  evaluation_interval: 15s  # how often to re-check rules (Grafana does our alerting, so this barely matters)

scrape_configs:  # one "job" = one kind of thing to collect from
  # Prometheus watching itself - cheap, and proves scraping works at all
  - job_name: prometheus
    static_configs:  # "static" = a fixed list of addresses, no discovery magic
      - targets: ["localhost:9090"]  # itself

  # Host metrics: CPU, RAM, disk, network on each app box
  - job_name: node
    static_configs:
      - targets: ["STG_IP:9100"]  # node_exporter on the staging box (api + web together)
        labels: { host: stg-server, env: stg }  # sticks host="stg-server" env="stg" onto every number from it
      - targets: ["PRD_API_IP:9100"]  # node_exporter on the prod api box
        labels: { host: api-server, env: prod }
      - targets: ["PRD_FE_IP:9100"]  # node_exporter on the prod frontend box
        labels: { host: frontend-server, env: prod }

  # HTTP probes through blackbox_exporter. Prometheus asks blackbox
  # "probe this URL", blackbox does the request and reports probe_success 0/1.
  - job_name: blackbox_http
    metrics_path: /probe  # blackbox answers on /probe, not the usual /metrics
    params:
      module: [http_2xx]  # which check to run (defined in blackbox.yml)
    static_configs:  # the "targets" here are URLs to probe, not exporters to scrape
      - targets: ["http://STG_IP:8000/healthz/"]
        labels: { probe: api-healthz, env: stg }  # probe = the name the dashboard + alert rules match on
      - targets: ["http://STG_IP:8000/readyz/"]
        labels: { probe: api-readyz, env: stg }
      - targets: ["http://STG_IP/"]
        labels: { probe: website, env: stg }
      - targets: ["http://PRD_API_IP:8000/healthz/"]
        labels: { probe: api-healthz, env: prod }  # same probe name, different env
      - targets: ["http://PRD_API_IP:8000/readyz/"]
        labels: { probe: api-readyz, env: prod }
      - targets: ["http://PRD_FE_IP/"]
        labels: { probe: website, env: prod }
    relabel_configs:  # rewrite rules that run before the scrape
  # the target URL becomes the ?target= parameter ...
      - source_labels: [__address__]  # take the URL from the targets list above
        target_label: __param_target  # put it into ?target=URL
  # ... and stays visible as the instance label ...
      - source_labels: [__param_target]
        target_label: instance  # so you can still see which URL a number belongs to
  # ... while the actual scrape goes to the blackbox container
      - target_label: __address__
        replacement: blackbox:9115  # the real address Prometheus connects to

  # Jenkins, once it has its own EC2 box with the "prometheus" plugin (Step 7).
  # Uncomment and set JENKINS_IP.
  # - job_name: jenkins
  #   metrics_path: /prometheus  # the Jenkins plugin publishes here, not /metrics
  #   static_configs:
  #     - targets: ["JENKINS_IP:8080"]

The relabel block is the only clever part. Without it Prometheus would try to scrape http://STG_IP:8000/healthz/ directly and get HTML, not metrics. With it, Prometheus calls blackbox:9115/probe?module=http_2xx&target=http://STG_IP:8000/healthz/ and blackbox does the real request. Django gotcha: if a probe returns 0 but curl shows a 400 Bad Request page, the box IP is missing from ALLOWED_HOSTS in the API's server/.env. Add it and recreate the api container.

2.5 · monitoring/blackbox/blackbox.yml

# monitoring/blackbox/blackbox.yml
modules:  # a "module" = one recipe for checking a target
  http_2xx:  # the name prometheus.yml asks for (module: [http_2xx])
    prober: http  # do an HTTP request (other probers: tcp, icmp/ping, dns)
    timeout: 5s  # no answer in 5 s = failed probe
    http:
      preferred_ip_protocol: ip4  # use IPv4; the EC2 boxes have no public IPv6
      follow_redirects: true  # a 301/302 to another page still counts, follow it
  # valid_status_codes defaults to 2xx, so /readyz/ answering 503 = probe_success 0

This is why /readyz/ is a real check: the Django view returns 503 when the database or S3 is unreachable. A 503 is not 2xx, so the probe fails, so the alert fires. The app's own readiness logic drives the monitoring for free.

2.6 · Grafana datasource and dashboard provider

# monitoring/grafana/provisioning/datasources/prometheus.yml
apiVersion: 1  # provisioning file format version; always 1
datasources:  # where Grafana gets numbers from
  - name: Prometheus  # the name shown in the UI
    uid: prometheus  # alert rules and dashboards refer to this uid
    type: prometheus  # the plugin to talk with (Grafana also speaks Loki, MySQL, ...)
    access: proxy  # Grafana's server fetches the data, not your browser
    url: http://prometheus:9090  # the prometheus container, by compose service name
    isDefault: true  # new panels use it without asking
    editable: false  # grey out "edit" in the UI: the file is the truth
# monitoring/grafana/provisioning/dashboards/dashboards.yml
apiVersion: 1
providers:  # a "provider" = one place Grafana loads dashboards from
  - name: rmit-store  # any name
    folder: RMIT Store  # the folder they appear in, in the Dashboards menu
    type: file  # load from files on disk
    disableDeletion: false  # if a JSON file disappears, remove the dashboard too
    updateIntervalSeconds: 30  # re-read the folder every 30 s (edit a file, see it live)
    allowUiUpdates: false  # the file is the truth; edit in the UI, export, commit
    options:
      path: /var/lib/grafana/dashboards  # the folder mounted in docker-compose.yml

uid: prometheus is a name you choose. Every "datasource": {"uid": "prometheus"} in the dashboard JSON and every datasourceUid: prometheus in the rules points back here. Change one, change all.

Checkpoint: six files exist under monitoring/, none of them contains a password, and git status does not list monitoring/.env (because you have not created it, and it is ignored anyway). Dashboards and alert rules are next.

3.3 · Contact point and policy

# monitoring/grafana/provisioning/alerting/contact-points.yml
apiVersion: 1
contactPoints:  # a "contact point" = one way to reach a human
  - orgId: 1  # Grafana organisation; a fresh install has exactly one, id 1
    name: team-email  # the name policies.yml points at
    receivers:  # one contact point can have several channels; we have one
      - uid: team-email  # stable id, so re-provisioning updates instead of duplicating
        type: email  # send an email (others: slack, webhook, ...)
        settings:
          addresses: "${ALERT_EMAILS}"  # env var from docker-compose.yml, comma-separated
          singleEmail: true  # one email to all addresses, not one per address
# monitoring/grafana/provisioning/alerting/policies.yml
apiVersion: 1
policies:  # the routing tree: which alert goes to which contact point
  - orgId: 1
    receiver: team-email  # the root rule: everything goes here (no sub-routes needed)
    group_by: [grafana_folder, alertname]  # alerts with the same name are bundled into one email
    group_wait: 30s  # wait 30 s to batch alerts that fire together
    group_interval: 5m  # if more alerts join an existing group, wait 5 min before the next email
    repeat_interval: 4h  # re-send a still-firing alert every 4 h, not every minute

Grafana expands ${ALERT_EMAILS} from the container environment when it reads provisioning files. That is how the address list stays out of git while the rule files stay in.

3.4 · monitoring/grafana/provisioning/alerting/rules.yml — six alerts

Each rule is two steps: query A asks Prometheus for a number, expression C compares it to a threshold. for: is how long it must stay bad before anyone is emailed.

# monitoring/grafana/provisioning/alerting/rules.yml
apiVersion: 1
groups:  # rules live in groups; a group shares one check interval
  - orgId: 1
    name: rmit-store  # group name
    folder: RMIT Store  # folder in the Alerting UI (created if missing)
    interval: 1m  # evaluate every rule in this group once a minute
    rules:

  # ---- rule 1, fully explained; the other five have the same shape ----
      - uid: api-healthz-down  # stable id; change the title freely, never the uid
        title: API healthz down  # what the email subject says
        condition: C  # which step below decides fire / not fire
        for: 1m  # must be bad for 1 whole minute before it fires (kills flaps)
        noDataState: Alerting  # if the probe itself vanishes, that is also bad
        execErrState: Error  # if the query itself breaks, show "Error" rather than fire
        labels: { severity: critical, service: api }  # tags; policies could route on these
        annotations:
          summary: "The API is not answering /healthz/ (process down or port 8000 unreachable)."  # body text of the email
        data:  # the steps, run in order
          - refId: A  # step A: ask Prometheus for a number
            relativeTimeRange: { from: 300, to: 0 }  # look at the last 300 s (5 min)
            datasourceUid: prometheus  # the datasource uid from datasources/prometheus.yml
            model: { refId: A, instant: true, expr: 'probe_success{probe="api-healthz"}' }  # instant = one latest value, not a graph
          - refId: C  # step C: compare
            datasourceUid: __expr__  # magic uid meaning "Grafana's own math, no datasource"
            model: { refId: C, type: threshold, expression: A,  # take A's value ...
                     conditions: [ { evaluator: { type: lt, params: [1] } } ] }  # ... fire if it is less than 1 (i.e. 0 = down)

      - uid: api-readyz-failing
        title: API readyz failing (database or S3)
        condition: C
        for: 2m
        noDataState: Alerting
        execErrState: Error
        labels: { severity: critical, service: api }
        annotations:
          summary: "The API is up but /readyz/ returns 503: check RDS and the S3 bucket."
        data:
          - refId: A
            relativeTimeRange: { from: 300, to: 0 }
            datasourceUid: prometheus
            model: { refId: A, instant: true, expr: 'probe_success{probe="api-readyz"}' }
          - refId: C
            datasourceUid: __expr__
            model: { refId: C, type: threshold, expression: A,
                     conditions: [ { evaluator: { type: lt, params: [1] } } ] }

      - uid: website-down
        title: Website down
        condition: C
        for: 1m
        noDataState: Alerting
        execErrState: Error
        labels: { severity: critical, service: frontend }
        annotations:
          summary: "The frontend is not serving its home page on port 80."
        data:
          - refId: A
            relativeTimeRange: { from: 300, to: 0 }
            datasourceUid: prometheus
            model: { refId: A, instant: true, expr: 'probe_success{probe="website"}' }
          - refId: C
            datasourceUid: __expr__
            model: { refId: C, type: threshold, expression: A,
                     conditions: [ { evaluator: { type: lt, params: [1] } } ] }

      - uid: host-cpu-high
        title: Host CPU above 80% for 5 minutes
        condition: C
        for: 5m
        noDataState: OK
        execErrState: Error
        labels: { severity: warning }
        annotations:
          summary: "{{ $labels.host }} CPU is above 80%."
        data:
          - refId: A
            relativeTimeRange: { from: 600, to: 0 }
            datasourceUid: prometheus
            model: { refId: A, instant: true,
                     expr: '100 * (1 - avg by (host) (rate(node_cpu_seconds_total{mode="idle"}[5m])))' }
          - refId: C
            datasourceUid: __expr__
            model: { refId: C, type: threshold, expression: A,
                     conditions: [ { evaluator: { type: gt, params: [80] } } ] }

      - uid: host-disk-high
        title: Host root disk above 85%
        condition: C
        for: 5m
        noDataState: OK
        execErrState: Error
        labels: { severity: warning }
        annotations:
          summary: "{{ $labels.host }} root filesystem is above 85% full."
        data:
          - refId: A
            relativeTimeRange: { from: 600, to: 0 }
            datasourceUid: prometheus
            model: { refId: A, instant: true,
                     expr: '100 * (1 - node_filesystem_avail_bytes{mountpoint="/",fstype!="tmpfs"} / node_filesystem_size_bytes{mountpoint="/",fstype!="tmpfs"})' }
          - refId: C
            datasourceUid: __expr__
            model: { refId: C, type: threshold, expression: A,
                     conditions: [ { evaluator: { type: gt, params: [85] } } ] }

      - uid: jenkins-down
        title: Jenkins down
        condition: C
        for: 2m
        noDataState: OK  # OK, not Alerting: stays quiet until the jenkins job exists
        execErrState: Error
        labels: { severity: warning, service: cicd }
        annotations:
          summary: "Prometheus cannot scrape Jenkins on port 8080."
        data:
          - refId: A
            relativeTimeRange: { from: 300, to: 0 }
            datasourceUid: prometheus
            model: { refId: A, instant: true, expr: 'up{job="jenkins"}' }
          - refId: C
            datasourceUid: __expr__
            model: { refId: C, type: threshold, expression: A,
                     conditions: [ { evaluator: { type: lt, params: [1] } } ] }

noDataState is the subtle one. For the health probes, "no data" means blackbox or Prometheus died, so we alert. For hosts and Jenkins, "no data" means "not set up yet", so we stay quiet. Getting this wrong means either a silent outage or an inbox full of noise.

5.3 · Optional: prove the readiness check on its own

Stopping api proves liveness. To show /readyz/ catching a dependency failure while the process is fine, temporarily break the database address.

This distinction is worth a sentence in the report: liveness says "restart me", readiness says "do not send me traffic, my database is gone". Two probes, two different alerts, two different responses.

🤖 Step 6 — Hand it to the Ansible owner as two roles

6.1 · Role node_exporter (runs on every app box)

Same style as the existing roles: FQCN modules, ansible.builtin.command for docker, one tasks/main.yml. Idempotent: it checks before it runs.

# ansible/roles/node_exporter/tasks/main.yml
---
# Host metrics for Prometheus (CPU, RAM, disk). Listens on 9100 - open that
# port only to MONITORING_IP/32. Same docker run as the monitoring guide, Step 4.1.
# The stg host is in both app_servers and frontend_servers, so this role runs
# twice on it - the check below makes the second run a no-op.

- name: Check whether node_exporter is already running  # task 1: look
  ansible.builtin.command:  # run a shell command on the box
    cmd: docker ps -q --filter name=^node_exporter$  # prints the container id if it exists, else nothing
  register: node_exporter_ps  # save the output under this name
  changed_when: false  # looking never counts as a change

- name: Run node_exporter  # task 2: act
  ansible.builtin.command:
    cmd: >  # ">" folds the next lines into one command
      docker run -d --name node_exporter --restart unless-stopped
      --net host --pid host
      -v /:/host:ro,rslave
      prom/node-exporter:{{ node_exporter_version }} --path.rootfs=/host  # version from group_vars/all.yml
  when: node_exporter_ps.stdout == ""  # only if task 1 found nothing

changed_when: false on the check keeps the play's summary honest: looking is not changing. The when: makes a second run a no-op.

    group: ec2-user
    mode: "0644"  # files: owner read/write, others read
    directory_mode: "0755"  # folders: also enterable

- name: Render prometheus.yml with the real host addresses
  ansible.builtin.template:  # like copy, but fills in {{ variables }} first
    src: prometheus.yml.j2  # from roles/monitoring/templates/
    dest: "{{ monitoring_dest }}/prometheus/prometheus.yml"  # overwrites the placeholder copy from the task above
    owner: ec2-user
    group: ec2-user
    mode: "0644"

- name: Render .env with secrets from the vault
  ansible.builtin.template:
    src: env.j2
    dest: "{{ monitoring_dest }}/.env"
    owner: ec2-user
    group: ec2-user
    mode: "0600"  # owner only: it holds passwords

- name: Bring up the monitoring stack
  ansible.builtin.command:
    cmd: docker compose up -d  # same command you ran by hand in Step 4.3
    chdir: "{{ monitoring_dest }}"  # cd there first, so compose finds the yml + .env
  register: compose_up
  changed_when: "'Started' in compose_up.stderr or 'Created' in compose_up.stderr"  # "changed" only if a container actually (re)started
# ansible/roles/monitoring/templates/env.j2  -> becomes monitoring/.env on the box
# (comments on their own lines: a "# ..." after a value can end up INSIDE the value in a .env file)
# from inventory: ansible_host of the monitoring box
MONITORING_HOST={{ monitoring_server_ip }}
# from the encrypted vault.yml
GRAFANA_ADMIN_PASSWORD={{ vault_grafana_admin_password }}
GMAIL_USER={{ vault_gmail_user }}
GMAIL_APP_PASSWORD={{ vault_gmail_app_password }}
# plain var in group_vars/all.yml (addresses are not secret)
ALERT_EMAILS={{ alert_emails }}

prometheus.yml.j2 is the file from 2.4 with four swaps: STG_IP → {{ stg_server_ip }}, PRD_API_IP → {{ prd_api_ip }}, PRD_FE_IP → {{ prd_fe_ip }}, and the Jenkins job wrapped in {% if jenkins_host %} ... {% endif %} with {{ jenkins_host }}:8080 as the target. Copy, swap, save as ansible/roles/monitoring/templates/prometheus.yml.j2.

🔧 Step 7 — Watch Jenkins too (when it has its box)

7.1 · One plugin line

Where: laptop, jenkins/local/Dockerfile from the alerting module. The prometheus plugin publishes Jenkins' own numbers at /prometheus.

RUN jenkins-plugin-cli --plugins \
    configuration-as-code \
    email-ext \
    workflow-aggregator \
    git \
    pipeline-stage-view \
    prometheus  # <- add this line
# jenkins/casc/alerting.yaml  (optional, append under `unclassified:`)
  prometheusConfiguration:
    path: prometheus  # endpoint = http://JENKINS:8080/prometheus
    collectingMetricsPeriodInSeconds: 60
    useAuthenticatedEndpoint: false  # Prometheus scrapes without a login; port 8080 is only open to MONITORING_IP/32

On the real Jenkins box (whoever runs it): Manage Jenkins → Plugins → install "Prometheus metrics", restart. Then curl -s localhost:8080/prometheus | head should print metric lines. Add a note to jenkins/README.md so the pipeline owner knows why the plugin is there.

7.2 · Point Prometheus at it

# by hand, on monitoring-server:
#   uncomment the jenkins job in ~/monitoring/prometheus/prometheus.yml, set JENKINS_IP
docker compose restart prometheus
docker compose exec grafana curl -s http://prometheus:9090/api/v1/targets | python3 -m json.tool | grep -A3 jenkins  # "health": "up"

# with Ansible: set jenkins_host in group_vars/all.yml, re-run site.yml
# and in the AWS console: jenkins-sg  add  Custom TCP 8080  Source: MONITORING_IP/32

Then the dashboard's Jenkins row fills in and the "Jenkins down" rule starts guarding it. Stop the Jenkins service for two minutes to prove that one too, if the report wants a CI/CD alert screenshot.

7.3 · Why not Ansible metrics?

Ansible is a tool that runs and exits; there is no process to scrape. Its "health" is the exit status of the playbook, which lives in the Jenkins job that runs it. So Jenkins metrics are the Ansible metrics: a failed deploy job counts in failed_build_count, and the Jenkins alerting module already emails on it.

Report sentence: "Pipeline health (including Ansible deploys) is observed through Jenkins build metrics; runtime health through blackbox probes and node_exporter."

Checkpoint: up{job="jenkins"} is 1 in Prometheus, the Jenkins tiles show numbers, and the prometheus plugin line is committed in jenkins/local/Dockerfile.

8.3 · Cleaning up and Learner Lab restarts

# when the lab session restarts, all three boxes come back with the same containers
#   (restart: unless-stopped) - but public IPs change unless you used Elastic IPs.
# if an IP changed (should not, with Elastic IPs): fix it in ~/monitoring/prometheus/prometheus.yml and
docker compose restart prometheus
# Grafana data (login, nothing else of value) is in the grafana_data volume; provisioning re-reads files at boot.

# to remove everything from the monitoring box:
cd ~/monitoring && docker compose down -v

Because everything is provisioned from files, down -v then up -d gives you an identical Grafana in about a minute. That is the sentence that justifies "as code" in the report.

The whole point: monitoring is graded on whether you can see the system's state and get told when it breaks, with enough context to act. Three tiles, two graphs, one email that says what and where, arriving before anyone goes looking, is the entire deliverable.
