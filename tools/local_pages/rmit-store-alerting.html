🚨 RMIT Store: Automated Alerting

Core requirement 8 — email the team when a build, test or deployment fails — built as a small, drop-in module for whoever owns the Jenkins pipeline. You write one Groovy file and one YAML file, prove them on a throwaway Jenkins on your laptop, then hand the pipeline teammate three lines to paste. No Jenkins server, no pipeline stages, no Slack: just the alerting.

🎯 What you are building, and where it plugs in

The requirement, in one line

Core requirement 8: implement email notifications to the team for build, test, and deployment failures. Requirement 4 adds: if testing fails, notify the team and do not update production. Both are the same mechanism — when a pipeline stage goes red, an email goes out.

Jenkins pipeline (teammate's job)      Alerting module (your job)
------------------------------------   -----------------------------------------
stage Build   ─┐                       jenkins/notify.groovy    the code that sends
stage Test    ─┼─ any stage fails ──►  jenkins/casc/*.yaml      what Jenkins needs (SMTP, creds)
stage Deploy  ─┘                       3 lines in the Jenkinsfile to call it

You do not build Jenkins or the pipeline. You build a small piece that any Jenkinsfile can call, and you prove it works on a throwaway Jenkins on your laptop.

Why a post block

A declarative Jenkinsfile has stages { ... }, then an optional post { ... } that runs after the stages no matter what happened. post { always { ... } } is the one place that sees every outcome: success, failure, aborted. That is where the alert hook goes.

pipeline {
    agent any
    stages {
        stage('Build')  { steps { ... } }
        stage('Test')   { steps { ... } }   // if this fails, Deploy never runs
        stage('Deploy') { steps { ... } }
    }
    post {
        always { script { load('jenkins/notify.groovy').notifyTeam() } }
    }
}

Groovy is the language Jenkinsfiles are written in. It looks like Java with less ceremony. load reads a .groovy file from the checked-out repo and hands back its methods.

What goes in the repo

All of it lives under a new jenkins/ folder at the repo root (the folder holding server/ and client/). Nothing here touches the app code.

jenkins/
├── notify.groovy              # the module: sends the email
├── Jenkinsfile.alert-test     # fake pipeline that fails on purpose (testing only)
├── casc/
│   ├── alerting.yaml          # Jenkins config: SMTP, credential, ALERT_EMAILS  -> hand to teammate
│   └── local.yaml             # laptop-only: admin login + URL                  -> never hand over
└── local/
    └── Dockerfile             # throwaway Jenkins image for your laptop

Secrets never go in git. The Gmail app password is passed as an environment variable and referenced from the YAML as ${GMAIL_APP_PASSWORD}.

The three ideas that make this work. (1) post { always } runs after every build, so one hook catches build, test and deploy failures. (2) Jenkins Configuration as Code (JCasC, a plugin that reads YAML at boot) means the SMTP setup is a file in the repo, not clicks in a UI. (3) A failing Test stage stops the pipeline before Deploy, so "notify and do not update production" comes for free.

🐳 Step 2 — A throwaway Jenkins on your laptop

2.1 · The image

Where: repo root. Make jenkins/local/Dockerfile.

Start from the official Jenkins LTS image, disable the setup wizard, and pre-install the five plugins we need. CASC_JENKINS_CONFIG tells the Configuration as Code plugin which folder to read at boot.

# jenkins/local/Dockerfile
# A throwaway Jenkins for testing the alerting module on a laptop.
FROM jenkins/jenkins:lts-jdk17

# skip the "unlock Jenkins" wizard; JCasC configures everything instead
ENV JAVA_OPTS="-Djenkins.install.runSetupWizard=false"
ENV CASC_JENKINS_CONFIG=/var/jenkins_home/casc

RUN jenkins-plugin-cli --plugins \
    configuration-as-code \
    email-ext \
    workflow-aggregator \
    git \
    pipeline-stage-view

Plugins: configuration-as-code reads the YAML, email-ext sends rich email, workflow-aggregator is the Pipeline suite, git clones, pipeline-stage-view draws the stage boxes you will screenshot for the report.

2.2 · Laptop-only config

Where: jenkins/casc/local.yaml.

With the wizard off, Jenkins would boot with no login at all. This file gives it one admin user (password from an env var) and tells it its own URL, which the email needs for the console link.

# jenkins/casc/local.yaml
# LAPTOP ONLY. Gives the throwaway Jenkins a login and a URL.
# Do NOT hand this file to the Jenkins teammate - it would overwrite their users.

jenkins:
  securityRealm:
    local:
      allowsSignup: false
      users:
        - id: admin
          password: "${JENKINS_ADMIN_PASSWORD}"
  authorizationStrategy: loggedInUsersCanDoAnything

unclassified:

Important: this file is for your laptop only. Handing it to the Jenkins teammate would replace their users with yours.

✉️ Step 3 — Write the module: notify.groovy

3.1 · The whole file

Where: jenkins/notify.groovy. Read it top to bottom before pasting; every decision from the design is in here.

// jenkins/notify.groovy
// Email the team when a build / test / deploy stage fails, and once more when
// main goes back to green. Nothing is sent for a normal green build.
//
// Use from a Jenkinsfile:
//   post { always { script { load('jenkins/notify.groovy').notifyTeam() } } }

def notifyTeam() {
    def result   = currentBuild.currentResult ?: 'SUCCESS'
    def previous = currentBuild.previousBuild?.result
    def branch   = (env.BRANCH_NAME ?: env.GIT_BRANCH ?: gitOut('rev-parse --abbrev-ref HEAD')).replace('origin/', '')
    def commit   = (env.GIT_COMMIT ?: gitOut('rev-parse HEAD')).take(8)
    def author   = gitOut('log -1 --pretty=%an')
    def message  = gitOut('log -1 --pretty=%s')
    def stage    = env.FAILED_STAGE ?: 'see the log tail below'
    def onMain   = branch in ['main', 'master']

    def failed = (result != 'SUCCESS')
    def fixed  = !failed && onMain && previous != null && previous != 'SUCCESS'
    if (!failed && !fixed) {
        echo "notifyTeam: ${result} on ${branch} - nothing to send"
        return
    }

    def to = env.ALERT_EMAILS
    if (!to) {
        echo 'notifyTeam: ALERT_EMAILS is not set on this Jenkins - no email sent'
        return
    }

    def tag    = failed ? "FAILED (${result})" : 'FIXED'
    def colour = failed ? '#c62828' : '#2e7d32'

    // Groovy fills in ${...} here...
    def head = """
<h2 style="color:${colour}">${tag}: ${env.JOB_NAME} #${env.BUILD_NUMBER}</h2>
<table cellpadding="4">
  <tr><td><b>Stage</b></td><td>${failed ? stage : 'all stages green again'}</td></tr>
  <tr><td><b>Branch</b></td><td>${branch}</td></tr>
  <tr><td><b>Commit</b></td><td>${commit} - ${message}</td></tr>
  <tr><td><b>Pushed by</b></td><td>${author}</td></tr>
  <tr><td><b>Console log</b></td><td><a href="${env.BUILD_URL}console">${env.BUILD_URL}console</a></td></tr>
</table>
"""
    // ...but this ${BUILD_LOG} is in single quotes, so Groovy leaves it alone
    // and the Email Extension plugin expands it into the last 50 log lines.
    def tail = failed ? '<h3>Last 50 lines of the log</h3><pre>${BUILD_LOG, maxLines=50, escapeHtml=true}</pre>' : ''

    emailext(
        to:       to,
        subject:  "${tag} - ${env.JOB_NAME} #${env.BUILD_NUMBER} - ${branch}",
        mimeType: 'text/html',
        body:     head + tail
    )
}

// Run a git command in the workspace; return trimmed output, or '' if it fails.
def gitOut(String args) {
    return sh(script: "git ${args} 2>/dev/null || true", returnStdout: true).trim()
}

return this

return this at the end is not optional. It is what lets load(...) hand back an object whose notifyTeam() you can call.

3.2 · How to read it

Follow the flow, it is short:

1. Ask Jenkins what happened      currentBuild.currentResult      SUCCESS / FAILURE / UNSTABLE / ABORTED
2. Ask about the previous build   currentBuild.previousBuild      to detect "was red, now green"
3. Ask git who/what               git log -1, rev-parse           branch, commit, author, message
4. Decide                          failed?  -> send a red email on ANY branch
                                   fixed?   -> send a green email, main only, only if last run was red
                                   else     -> print one line to the console and stop
5. Recipients                      env.ALERT_EMAILS               set by casc/alerting.yaml
6. Send                            emailext(...)                  HTML body + last 50 log lines

Two kinds of ${...}: in the triple-quoted head string Groovy fills them in. In the single-quoted tail string Groovy leaves ${BUILD_LOG, ...} alone so the Email Extension plugin can expand it later. Mixing those up is the most common bug.

3.3 · Naming the stage that broke

Jenkins does not hand a post block the name of the failing stage. The module reads env.FAILED_STAGE if someone set it, else says see the log tail. The log tail always contains the [Pipeline] { (Test) marker, so the answer is in the email either way.

// optional, inside any stage - one line, makes the email say "Stage: Test"
post { failure { script { env.FAILED_STAGE = env.STAGE_NAME } } }

Why optional: it keeps the ask of the Jenkins teammate to three lines. They can add the per-stage line later if they want prettier emails.

Checkpoint: jenkins/notify.groovy exists, ends in return this, and you can explain in one sentence each why the red email goes to every branch but the green one only on main.

🧪 Step 4 — Break it on purpose, watch the email land

4.1 · A fake pipeline

Where: jenkins/Jenkinsfile.alert-test. It pretends to build, fails in Test, and never reaches Deploy — exactly the shape of a real failure.

// jenkins/Jenkinsfile.alert-test
// A fake pipeline whose only job is to exercise notify.groovy.
// Build -> Test (fails on purpose) -> Deploy (never reached).

pipeline {
    agent any

    environment {
        BREAK_THE_TESTS = 'yes'   // flip to 'no' to see the FIXED email
    }

    stages {
        stage('Build') {
            steps { echo 'pretend: docker build both tiers' }
        }
        stage('Test') {
            steps {
                sh '''
                  echo "running the test suite..."
                  if [ "$BREAK_THE_TESTS" = "yes" ]; then
                    echo "FAIL test_cart_total: expected 42.00, got 41.99"
                    exit 1
                  fi
                  echo "all tests passed"
                '''
            }
            // optional: remember which stage broke, so the email can name it
            post { failure { script { env.FAILED_STAGE = env.STAGE_NAME } } }
        }
        stage('Deploy') {
            steps { echo 'pretend: deploy to staging' }
        }
    }

    post {
        always {
            script { load('jenkins/notify.groovy').notifyTeam() }
        }
    }
}

This is a test fixture, not the team pipeline. It stays in the repo so anyone can re-prove alerting in two minutes.

4.2 · Commit, because Jenkins clones

Where: repo root.

Jenkins will git clone /repo, and a clone only sees committed files. Commit on a branch; no push needed for this step.

git checkout -b feature/alerting

Every edit to notify.groovy needs a new commit before rerunning the job. git commit --amend --no-edit keeps the history tidy while you iterate.

4.5 · Fix it, see the green email

Where: jenkins/Jenkinsfile.alert-test. Flip BREAK_THE_TESTS to 'no', commit, Build Now.

No email. That is correct: the FIXED email is main only, and this is a feature branch. To see it, temporarily change the job's Branch Specifier to a branch named main, or edit the onMain line to include your branch, run red then green, then put it back.

6.1 · What they paste into the Jenkinsfile

Three lines at the bottom. Nothing else in their pipeline changes.

// Add to the very end of the Jenkinsfile, after `stages { ... }`:
post {
    always {
        script { load('jenkins/notify.groovy').notifyTeam() }

6.2 · What they put on the Jenkins server (JCasC way)

7.2 · What to put in the report

Design       post{always} hook -> notify.groovy -> Email Extension -> Gmail SMTP -> team inboxes
Why Gmail    zero cost, no AWS SES sandbox verification, app password kept out of git
Why JCasC    SMTP + credential + recipients are a file in the repo, reproducible on any Jenkins
Policy       red email on every branch; green FIXED email on main only; silence otherwise
Evidence     screenshot: stage view red + email; screenshot: FIXED email; the console "Sending email to:" line
Limits       Gmail app-password accounts are not for production scale; swap to SES = change 4 YAML lines

One honest limitation in the report reads better than none. The SES swap line is your "future work".

The whole point: alerting is graded on whether a human gets told, fast, with enough context to act. One email, with the stage, the commit, the author and the log — arriving before anyone goes looking — is the entire deliverable.
