🤖 RMIT Store: Ansible Deploy

Core requirement 7 — Configuration Management (Ansible). You own ansible/. Advanced requirement 1 (Infrastructure as Code) is CloudFormation; that is a different teammate. Jenkins builds and pushes images. You deploy them to the team's shared five EC2 boxes: one Jenkins server plus staging API, staging frontend, production API, and production frontend. Docker Swarm is not your job. Another teammate initializes the cluster and writes the stack logic behind deploy.yml. Your deliverable is inventory, encrypted vars, migrations, and this stable handoff:

ansible-playbook -i ansible/inventory/aws_ec2.yml ansible/deploy.yml -e target=... -e api_image=... -e frontend_image=... (from repo root; dynamic EC2 inventory committed in git).

🗺️ Step 2 — Staging and production inventory

2.1 · Dynamic inventory — committed, non-secret

The team runs one shared five-box set. Inventory is the committed file ansible/inventory/aws_ec2.yml (same path ansible.cfg already points at). It lives in the git checkout Jenkins mounts — no hidden copy on the server.

Extend the SHA 66ea54d baseline: replace the dev filter with staging and production. Group hosts by EC2 tags so deploy.yml can target {{ target }}_api:{{ target }}_frontend.

# ansible/inventory/aws_ec2.yml  (extend the committed file)
plugin: amazon.aws.aws_ec2
regions:
  - us-east-1
filters:
  tag:Environment:
    - staging
    - production
  instance-state-name:
    - running
hostnames:
  - private-ip-address
compose:
  ansible_host: private_ip_address
leading_separator: false
keyed_groups:
  # Environment=staging Role=api  →  staging_api  (NOT _staging_api)
  - key: tags.Environment + '_' + tags.Role
    prefix: ''
    separator: ''
  - key: tags.Environment
    prefix: env

With leading_separator: false, an empty prefix does not add a leading underscore. You should see exactly four groups: staging_api, staging_frontend, production_api, production_frontend.

Tag each of the four app EC2 instances in the AWS console (or CloudFormation):

staging-api box:       Environment=staging   Role=api
staging-frontend box:  Environment=staging   Role=frontend
production-api box:    Environment=production Role=api
production-frontend:   Environment=production Role=frontend

Jenkins passes -e target=staging or production. deploy.yml limits to {{ target }}_api:{{ target }}_frontend — groups produced by the plugin from tags, not hand-edited IPs.

2.2 · How the runner discovers hosts (LabRole + IMDS)

The jenkins-server EC2 instance wears Learner Lab LabRole (or equivalent). That role needs read-only EC2 API access — at minimum ec2:DescribeInstances — so the amazon.aws.aws_ec2 plugin can list tagged instances.

The ephemeral runner uses --network host so boto3 can reach the instance metadata service (IMDS) on the Jenkins EC2 host. No AWS keys in git or Jenkins argv.

Jenkins EC2 prerequisite (one-time): set IMDSv2 and verify hop limit ≥ 2 so containerized processes can assume the instance role. AWS console → EC2 → instance → Actions → Modify instance metadata options:

Metadata response hop limit: 2    # 1 = host only; 2 = reachable from containers on host network

4.1 · Command from repo root

# production (after merge to main):
ansible-playbook -i ansible/inventory/aws_ec2.yml ansible/deploy.yml \
  -e target=production \
  -e api_image=DOCKER_USER/rmit-store-api:a1b2c3d4 \
  -e frontend_image=DOCKER_USER/rmit-store-frontend:a1b2c3d4 \
  --vault-password-file /path/to/vault-pass \
  --private-key /path/to/deploy-key

From app/ansible/: use -i inventory/aws_ec2.yml deploy.yml (same inventory file, shorter paths). Never substitute inventory.ini in Jenkins.

4.2 · Immutable image tags and one staging slot

PR pipeline tag:         pr-<PR_NUMBER>-<8-char-SHA>   e.g. pr-42-a1b2c3d4
Production pipeline tag: <8-char-SHA>                 e.g. a1b2c3d4

Tags are immutable — Jenkins never overwrites an existing tag on Docker Hub. Each build pushes a new tag string.

All open PRs share one staging environment (two boxes). A successful PR deploy replaces whatever was running on staging before. Tags do not stop that — they only preserve old images in the registry for rollback.

lock(resource: 'staging') prevents two PR jobs deploying at the same time. It does not give each PR its own staging copy. Wait for the lock, deploy, release — the next merged PR wins staging again.

4.3 · Private registry auth — shared ownership

Images live in private Docker Hub repos. Jenkins stores the username and token as Secret File credentials (same pattern as SSH key and vault passphrase). Mount them read-only into the runner — never export secret values into the runner environment.

1. Jenkins push stage        — separate push credentials (Jenkins page); console masked
2. Deploy runner mounts      — /run/secrets/dockerhub_user + /run/secrets/dockerhub_token
3. Runner env (paths only)   — DOCKERHUB_USER_FILE / DOCKERHUB_TOKEN_FILE
4. Ansible docker_login      — lookup('file', lookup('env', '..._FILE')) | trim ; no_log: true
5. Migration host            — login + pull api_image before migrate
6. Swarm service update      — --with-registry-auth on workers (Swarm teammate)

Do not duplicate Docker Hub credentials in Ansible vault. Do not pass -e DOCKERHUB_TOKEN=... or export token values into docker run -e.

Not solely the Swarm teammate's problem. If migrate cannot pull the image, the play must fail before any service update runs.

4.4 · What deploy.yml must do

1. assert target in [staging, production]
2. docker_login via DOCKERHUB_*_FILE paths + pull api_image (no_log)
3. run migrations (Step 5) — fail immediately on non-zero exit
4. only if migrate succeeded: Swarm service update with api_image + frontend_image
5. verify /healthz/, /readyz/, /api/version/ (Step 7)

site.yml stays for bootstrap / dev EC2 discovery. deploy.yml is the CI/CD entry point Jenkins calls every pipeline run.

Checkpoint: three -e vars, every command uses -i ansible/inventory/aws_ec2.yml, staging is one shared slot with a lock. Next: migrations.

🗄️ Step 5 — Migrations before backend update

5.1 · Why the API entrypoint is not enough

The API image's entrypoint.sh runs python manage.py migrate --noinput then starts gunicorn. Every container start migrates.

That was fine for manual deploys. For CI/CD you need one explicit migrate before the Swarm service update. If migrate fails, the old API image must keep serving traffic.

A plain docker run {{ api_image }} python manage.py migrate never finishes — the entrypoint ignores your command and starts gunicorn anyway. You must override the entrypoint.

5.2 · Explicit migration task

Run once per deploy against the target environment's database. Use the new API image so migration code matches the code about to go live.

Service updates happen only after this task succeeds (failed_when: rc != 0 stops the play).

# inside deploy.yml, before any Swarm update — pattern; you implement
# DOCKERHUB_USER_FILE and DOCKERHUB_TOKEN_FILE are path-only env vars from Jenkins (Step 6)

- name: Log in to Docker Hub on API host (private pull for migrate)
  community.docker.docker_login:
    username: "{{ lookup('file', lookup('env', 'DOCKERHUB_USER_FILE')) | trim }}"
    password: "{{ lookup('file', lookup('env', 'DOCKERHUB_TOKEN_FILE')) | trim }}"
  delegate_to: "{{ groups[target + '_api'][0] }}"
  no_log: true

- name: Pull API image on migration host
  community.docker.docker_image:
    name: "{{ api_image }}"
    source: pull
  delegate_to: "{{ groups[target + '_api'][0] }}"
  no_log: true

- name: Run database migrations for {{ target }}
  ansible.builtin.command:
    cmd: >
      docker run --rm
      --env-file /path/to/rendered/.env
      --entrypoint python
      {{ api_image }}
      manage.py migrate --noinput
  delegate_to: "{{ groups[target + '_api'][0] }}"
  run_once: true
  register: migrate_result
  changed_when: "'Applying' in migrate_result.stdout"
  failed_when: migrate_result.rc != 0

# subsequent tasks: update API service, then frontend — only reached if migrate succeeded

Login and pull happen before migrate. community.docker is in requirements.yml — the pinned runner image must install it. no_log: true on login and pull. Credentials are read from mounted Secret Files, not vault and not runner env values.

5.3 · Order of operations

pull + login  →  migrate (run_once, entrypoint override)  →  update API service  →  update frontend

A failed migration leaves the previous API container running. Staging uses rmit_store_staging; production uses rmit_store — a bad staging migrate cannot touch production data, but still fail fast on both.

Checkpoint: migrate uses --entrypoint python, run_once: true, fail-fast before service update. Next: Jenkins runner handoff.

🐳 Step 6 — Ephemeral Ansible runner from Jenkins

6.1 · Persistent Jenkins, throwaway runner

Jenkins runs in Docker on the shared jenkins-server (t3.medium). The Jenkins teammate owns the server image (see the Jenkins tutorial page for the Dockerfile under jenkins/server/).

Each deploy stage starts an ephemeral Ansible runner container. It mounts the workspace (including inventory/aws_ec2.yml and committed encrypted vaults), mounts SSH key, vault passphrase, and known_hosts as files, runs ansible-playbook, then exits. Cleanup runs in post { always { ... } }.

Container Jenkins + host Docker socket resolves paths on the host. Use the same absolute bind for Jenkins home on both containers, e.g. /var/jenkins_home:/var/jenkins_home. Then WORKSPACE, withCredentials file paths, and inventory paths match inside the runner.

6.2 · One-time known_hosts on jenkins-server

Run once on the Jenkins EC2 host (SSH as ec2-user). Replace placeholders with the four app private or public IPs your team uses for SSH.

The official Jenkins image runs as UID/GID 1000:1000. Use that numeric owner — not a host jenkins account that may not exist on Amazon Linux.

# on jenkins-server — compare fingerprints with teammates over a trusted channel first
sudo mkdir -p /var/jenkins_home/.ssh
sudo touch /var/jenkins_home/.ssh/known_hosts

for IP in STAGING_API_IP STAGING_FRONTEND_IP PRODUCTION_API_IP PRODUCTION_FRONTEND_IP; do
  ssh-keyscan -H "$IP" | sudo tee -a /var/jenkins_home/.ssh/known_hosts
done

sudo chown 1000:1000 /var/jenkins_home/.ssh/known_hosts
sudo chmod 600 /var/jenkins_home/.ssh/known_hosts

# validate each host is present (repeat per IP):
ssh-keygen -F STAGING_API_IP -f /var/jenkins_home/.ssh/known_hosts && echo "staging-api ok"

Before first use, have a teammate read the fingerprint from a direct SSH session. Match it to what ssh-keyscan stored. Wrong fingerprint = stop and investigate.

Override the branch's host_key_checking = False. Pass ANSIBLE_HOST_KEY_CHECKING=True and StrictHostKeyChecking=yes with the mounted known_hosts path. Mount the file read-only at /var/jenkins_home/.ssh/known_hosts (mode 600 on the host).

      file(credentialsId: 'dockerhub-token-file', variable: 'DOCKERHUB_TOKEN_FILE')
    ]) {
      sh '''
        SHORT_SHA="$(git rev-parse --short=8 HEAD)"
        API_TAG="pr-${CHANGE_ID}-${SHORT_SHA}"
        DOCKER_USER="$(tr -d '\n' < "$DOCKERHUB_USER_FILE")"

        docker run --rm --network host \
          -v /var/jenkins_home:/var/jenkins_home:ro \
          -v "${WORKSPACE}:/var/jenkins_home/workspace/${JOB_NAME}":ro \
          -v "${SSH_KEY}:/run/secrets/ssh_key:ro" \
          -v "${VAULT_PASS_FILE}:/run/secrets/vault_pass:ro" \
          -v "${DOCKERHUB_USER_FILE}:/run/secrets/dockerhub_user:ro" \
          -v "${DOCKERHUB_TOKEN_FILE}:/run/secrets/dockerhub_token:ro" \
          -v /var/jenkins_home/.ssh/known_hosts:/var/jenkins_home/.ssh/known_hosts:ro \
          -e ANSIBLE_HOST_KEY_CHECKING=True \
          -e DOCKERHUB_USER_FILE=/run/secrets/dockerhub_user \
          -e DOCKERHUB_TOKEN_FILE=/run/secrets/dockerhub_token \
          rmit-store-ansible-runner:1.0.0 \
          ansible-playbook \
            -i /var/jenkins_home/workspace/${JOB_NAME}/ansible/inventory/aws_ec2.yml \
            /var/jenkins_home/workspace/${JOB_NAME}/ansible/deploy.yml \
            --vault-password-file /run/secrets/vault_pass \
            --private-key /run/secrets/ssh_key \
            -e ansible_ssh_common_args=-o\ StrictHostKeyChecking=yes\ -o\ UserKnownHostsFile=/var/jenkins_home/.ssh/known_hosts \
            -e target=staging \
            -e api_image=${DOCKER_USER}/rmit-store-api:${API_TAG} \
            -e frontend_image=${DOCKER_USER}/rmit-store-frontend:${API_TAG}
      '''
    }
  }
}
post {
  always {
    sh 'docker image prune -f || true'
  }
}

Secret Files only — no secret values in runner env. DOCKERHUB_*_FILE vars hold paths, not passwords. Ansible reads file contents with lookup('file', ...) | trim. ANSIBLE_HOST_KEY_CHECKING=True overrides ansible.cfg. Runner uses --network host for IMDS/LabRole access.
