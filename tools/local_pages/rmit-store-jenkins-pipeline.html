🔧 RMIT Store: Jenkins PR and Production Pipelines

This is page 2 of the deployment guide. It is for the teammate who owns Jenkins. You will use two t3.small EC2 boxes: jenkins-server builds and pushes images, and ansible-server runs every deployment as a Jenkins build agent. You will make one pipeline for pull requests and one for protected main. Both use the existing jenkins/notify.groovy alert module. The AWS hosts, Ansible inventory, vault files, Docker Swarm services, and migration role come from page 1: Ansible and Swarm.

🎯 Overview — two paths, two control boxes

Jenkins and Ansible sit on separate EC2 hosts. Jenkins keeps the Docker socket and the registry token. ansible-server keeps the SSH deploy key, the vault password, and the only route into the four app boxes. Neither box can do the other one's job.

Jenkins still owns sequence. It runs ansible-server as a permanent build agent labelled ansible, so the deploy stage is an ordinary pipeline stage with normal console output, normal credential binding, and a red stage on failure. Nothing is triggered by a fire-and-forget remote command.

0.2 · Pull request path

PR opened, reopened, ready for review, or updated with a new commit
  → checkout latest PR commit
  → temporary Django and Vue checks
  → build and push:
      DOCKERHUB_USER/rmit-store-api:pr-PR_NUMBER-SHORTSHA
      DOCKERHUB_USER/rmit-store-frontend:pr-PR_NUMBER-SHORTSHA
  → Ansible runs migrations and deploys that exact tag to staging
  → curl-based live staging placeholder runs
  → Jenkins posts a green or red commit status to GitHub
  → existing notify.groovy emails the team on failure

All pull requests share staging. Only one deploy and live-check block runs at a time. A new commit aborts an older run of the same PR. The newest waiting PR gets the staging lock next.

Check the version before manual testing. Another PR may replace staging. /api/version/ tells you which commit is live.

0.3 · Production path

one human approval + green Jenkins PR status
  → a human presses Merge
  → GitHub creates a push to protected main
  → production job checks out the merged commit
  → temporary checks
  → build and push SHORTSHA tags
  → capture the previous production tag
  → Ansible runs migrations and deploys the exact new tag
  → smoke /healthz/, /readyz/, and /api/version/ through frontend
  → email on failure

No full end-to-end journey runs in production. A purchase test creates data. Run it on staging before Merge.

There is no automatic rollback. A failed production smoke test leaves the pipeline red, sends email, and prints the previous tag plus a manual rollback command. Production can remain broken until a person acts.

Checkpoint: you can trace both paths. PRs deploy pr-PR_NUMBER-SHORTSHA to shared staging. A protected main push deploys SHORTSHA to production. Both paths use Ansible migrations, exact image tags, GitHub status, and the existing email module.

1.2 · Security group rules

Port 8080 serves both the Jenkins UI and /github-webhook/. Limit it to team addresses and GitHub's current webhook networks.

jenkins-server-sg inbound:
  SSH         TCP 22     source TEAM_PUBLIC_IP/32
  Jenkins     TCP 8080   source TEAM_PUBLIC_IP/32
  Jenkins     TCP 8080   source each current GitHub hooks CIDR

ansible-server-sg inbound:
  SSH         TCP 22     source TEAM_PUBLIC_IP/32
  SSH         TCP 22     source jenkins-server-sg
  no other inbound rule

app Swarm security groups:
  SSH         TCP 22     source ansible-server-sg

# Get GitHub's current webhook CIDRs. Run on your laptop.
curl -s https://api.github.com/meta | jq -r '.hooks[]'

GitHub changes these CIDRs sometimes. Check them again before the demo. If your lab cannot add all GitHub ranges, use 0.0.0.0/0 on 8080 only as a recorded short-term limit. Keep the Jenkins login locked and use a webhook secret.

SSH flows in one direction only. Jenkins opens 22 on ansible-server to launch the agent, and ansible-server opens 22 on the app boxes to deploy. If you left jenkins-server-sg on the app groups from an earlier draft, remove it now. The split is only real once that rule is gone.

1.4 · Add swap on jenkins-server

A t3.small has 2 GiB of RAM. The Java controller and a Node production build can want that much at the same moment. Swap turns a hard out-of-memory kill into a slow build.

# jenkins-server
sudo dd if=/dev/zero of=/swapfile bs=1M count=2048 status=progress
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
free -h

Swap is a safety net, not headroom. If builds still get killed, the honest fixes are a larger instance type or moving image builds off this box. Record whichever one you chose.

2.2 · Complete production Dockerfile

# jenkins/production/Dockerfile
FROM jenkins/jenkins:lts-jdk21

USER root
RUN apt-get update \
    && apt-get install -y --no-install-recommends \
       ca-certificates curl docker.io git \
    && rm -rf /var/lib/apt/lists/*

RUN jenkins-plugin-cli --plugins \
    configuration-as-code \
    credentials-binding \
    email-ext \
    git \
    github \
    github-branch-source \
    lockable-resources \
    pipeline-stage-view \
    prometheus \
    ssh-slaves \
    workflow-aggregator

USER jenkins

github-branch-source discovers pull requests and reports the normal Jenkins commit status. No GitHub Checks plugin is installed, so this guide does not promise a GitHub Check Run.

ssh-slaves is the SSH Build Agents plugin. It is the one plugin the split adds. Jenkins uses it to open an SSH connection to ansible-server, copy the agent JAR, and start the agent process under Java.

The Docker CLI talks to the host daemon. The Compose file mounts the host socket in the next card. It stays on this box, so no image build can reach an app host.

Only two YAML files load. They are production.yaml and alerting.yaml. The ansible node is not declared here, because its SSH credential is easier to attach in the UI in Step 4.

2.5 · Complete Compose file

# jenkins/production/compose.yaml
services:
  jenkins:
    build:
      context: ../..
      dockerfile: jenkins/production/Dockerfile
    image: rmit-store-jenkins:1.0.0
    container_name: rmit-store-jenkins
    restart: unless-stopped
    user: "1000:1000"
    group_add:
      - "${DOCKER_GID}"
    ports:
      - "8080:8080"
    env_file:
      - /etc/rmit-jenkins/jenkins.env
    environment:
      JAVA_OPTS: "-Djenkins.install.runSetupWizard=false -Xms256m -Xmx1024m"
      CASC_JENKINS_CONFIG: "/var/jenkins_home/casc/production.yaml,/var/jenkins_home/casc/alerting.yaml"
    volumes:
      - /var/jenkins_home:/var/jenkins_home
      - /var/run/docker.sock:/var/run/docker.sock
      - ../casc/production.yaml:/var/jenkins_home/casc/production.yaml:ro
      - ../casc/alerting.yaml:/var/jenkins_home/casc/alerting.yaml:ro
    mem_limit: 1500m
    cpus: 1.5

The volume keeps jobs, plugins, build records, and credentials across restarts. The CPU and memory caps apply to Jenkins itself. Sibling image builds use the host daemon outside these caps.

These numbers are the t3.small budget. A 1 GiB Java heap plus a roughly 1.5 GiB container cap leaves about 500 MiB of RAM plus the swap file for the sibling docker build containers, which are not capped by Compose. If you later move to a t3.medium, raise -Xmx to 1536m and mem_limit to 3g.

The Docker socket is root-equivalent host access. A trusted PR can change Jenkinsfile.pr, control this host's daemon, and ask Jenkins for credentials, including the deploy key. Splitting the boxes removes the direct path from a build container to production, but it does not remove that credential path. It is acceptable only for this small course team, where every repo writer is trusted. Do not accept forked or outside PRs. A pipeline definition loaded from trusted main is future hardening.

Keep each ID exact. The two root Jenkinsfiles below refer to these strings. ansible-agent-ssh is the exception: only the node configuration in Step 4 uses it.

3.3 · Private Docker Hub repositories

Create two private repositories:
  DOCKERHUB_USER/rmit-store-api
  DOCKERHUB_USER/rmit-store-frontend

Create one Docker Hub access token with read and write access.
Store it only in dockerhub-creds.

PR tags look like pr-42-a1b2c3d4. Production tags look like a1b2c3d4. If both exact image tags exist on a rerun, the pipeline verifies and reuses them. If only one exists, it fails as a partial publish. It never overwrites either tag.

Never deploy only latest. An exact tag links GitHub, Docker Hub, Ansible, the running API, and rollback evidence.

3.4 · How secrets reach the deploy agent

Jenkins binds the SSH key and vault password only around the deploy shell, and that shell runs on ansible-server. The controller sends the secret to the agent for the duration of the block and writes it into the agent's own workspace. The shell turns off trace output. It writes the vault password to a mode-600 temporary file. A trap deletes it. ansible-playbook receives file paths, not secret text in command arguments. dockerhub-creds is bound only in the build and push stages, which never run on the Ansible box. Page 1 already stores the read-only deploy token in each encrypted Ansible vault.

set +x
umask 077
SECRET_DIR="$(mktemp -d "$WORKSPACE/.ci-secrets.XXXXXX")"
trap 'rm -rf "$SECRET_DIR"' EXIT INT TERM

printf '%s' "$ANSIBLE_VAULT_PASSWORD" > "$SECRET_DIR/vault-password"

Masking is a backup, not permission control. This course design does run trusted team PR code with deployment credentials. Branch protection does not make that code safe before the build. Only trusted teammates may write branches. A later hardened design loads the pipeline from trusted main and runs builds on isolated agents.

Checkpoint: the GitHub token is limited to one private repo and has Contents read, Pull requests read, and Commit statuses write. The two Docker Hub repos are private. All seven Jenkins credential IDs exist, including the separate ansible-agent-ssh key. No secret value appears in git.

🤖 Step 4 — Turn ansible-server into the deploy agent

4.1 · Install Ansible in a virtual environment

Where: on ansible-server. Save this as jenkins/ansible-agent/bootstrap.sh in the repo and run it once, so the next person can rebuild the box from the file instead of from memory.

#!/usr/bin/env bash
# jenkins/ansible-agent/bootstrap.sh
set -euo pipefail

VENV=/opt/ansible-venv
COLLECTIONS=/opt/ansible-collections

sudo python3 -m venv "$VENV"
sudo "$VENV/bin/pip" install --no-cache-dir --upgrade pip
sudo "$VENV/bin/pip" install --no-cache-dir 'ansible-core>=2.17,<2.19'

sudo mkdir -p "$COLLECTIONS"
sudo "$VENV/bin/ansible-galaxy" collection install \
  'community.docker:>=3.10.0,<5.0.0' -p "$COLLECTIONS"

# the agent runs as ec2-user and only needs to read these
sudo chmod -R a+rX "$VENV" "$COLLECTIONS"

"$VENV/bin/ansible-playbook" --version
ANSIBLE_COLLECTIONS_PATH="$COLLECTIONS" \
  "$VENV/bin/ansible-galaxy" collection list community.docker

A virtual environment at a fixed path is this design's dependency isolation. The old runner container did the same job, but a whole box that only ever runs Ansible does not need a second layer of packaging. Nothing else on the box uses Python.

Keep the bounds equal to page 1. These are the same version ranges as ansible/requirements.yml. If page 1 changes a bound, change it here too, or the same playbook behaves differently on a laptop and in the pipeline.

4.2 · Register the permanent Jenkins node

First teach the Jenkins container the host key of ansible-server, or the SSH launch will refuse to connect.

# jenkins-server
sudo mkdir -p /var/jenkins_home/.ssh
ssh-keyscan -H ANSIBLE_PRIVATE_IP | sudo tee -a /var/jenkins_home/.ssh/known_hosts
sudo chown -R 1000:1000 /var/jenkins_home/.ssh
sudo chmod 700 /var/jenkins_home/.ssh
sudo chmod 600 /var/jenkins_home/.ssh/known_hosts

Where: Manage Jenkins → Nodes → New Node.

Name                    ansible-server
Type                    Permanent Agent

Description             runs ansible-playbook only
Number of executors     1
Remote root directory   /opt/jenkins-agent
Labels                  ansible
Usage                   Only build jobs with label expressions
                        matching this node
Launch method           Launch agents via SSH
  Host                  ANSIBLE_PRIVATE_IP
  Credentials           ansible-agent-ssh
  Host Key Verification Known hosts file
  JavaPath              /usr/bin/java

Use the private IP. Both boxes are in one VPC, so agent traffic never leaves it. The Usage setting matters: it stops an unlabelled job from accidentally trying to build images on the box that holds the deploy key.

Do not choose "Non verifying" host key verification. It is offered and it would work. It also removes the only check that you are talking to your own box.

4.3 · Pin the app host keys on ansible-server

# ansible-server, as ec2-user, once per app host
mkdir -p ~/.ssh
chmod 700 ~/.ssh

for IP in STAGING_BACKEND_IP STAGING_FRONTEND_IP \
          PRODUCTION_BACKEND_IP PRODUCTION_FRONTEND_IP; do
  ssh-keyscan -H "$IP" >> ~/.ssh/known_hosts
done

chmod 600 ~/.ssh/known_hosts
ssh-keygen -F STAGING_BACKEND_IP -f ~/.ssh/known_hosts

These keys used to live in /var/jenkins_home/.ssh/known_hosts. They belong here now, because this is the box that opens the connections. The Jenkins box keeps a known_hosts file too, but it holds exactly one entry: ansible-server.

Use the same address form here that ansible_host uses in the page 1 inventories. A key scanned for a public IP does not match a connection made to the private IP.

Strict checking stays on. The deploy command below overrides the host_key_checking = False line in the page 1 ansible.cfg. Compare fingerprints with a teammate through a trusted channel; never accept an unknown key inside a pipeline.

4.4 · The deploy command Jenkins will run

export ANSIBLE_COLLECTIONS_PATH=/opt/ansible-collections
export ANSIBLE_HOST_KEY_CHECKING=True
export ANSIBLE_SSH_COMMON_ARGS="-o StrictHostKeyChecking=yes \
  -o UserKnownHostsFile=$HOME/.ssh/known_hosts"

/opt/ansible-venv/bin/ansible-playbook \
  -i ansible/inventories/staging.ini \
  ansible/site-swarm.yml \
  --private-key "$SSH_KEY" \
  --vault-password-file "$SECRET_DIR/vault-password" \
  -e target_environment=staging \
  -e "image_tag=${IMAGE_TAG}" \
  -e "git_commit=${GIT_COMMIT}" \
  -e "app_version=${IMAGE_TAG}"

This is a plain command, not a container invocation. The workspace, the credential files Jenkins binds, and known_hosts are all ordinary local files on this box, so nothing has to be mounted or path-matched. That simplicity is the main practical reward for giving Ansible its own instance.

ANSIBLE_COLLECTIONS_PATH is required. The bootstrap installed community.docker to a shared path, not into the agent user's home, so the playbook cannot find it without this line.

Use the absolute venv path. The Jenkins agent shell does not activate a virtual environment, and ansible-playbook is not on PATH.

4.5 · Prove the agent before touching the pipelines

Do this now. A broken agent looks exactly like a broken Jenkinsfile once a pipeline is running.

Manage Jenkins → Nodes → ansible-server
  Status must read "in sync" or "idle", not "offline"
  Log must show the agent JAR copied and the agent started

# ansible-server, prove the deploy path by hand first
cd ~ && git clone ASSIGNED_PRIVATE_REPO_URL check && cd check

ANSIBLE_COLLECTIONS_PATH=/opt/ansible-collections \
ANSIBLE_HOST_KEY_CHECKING=True \
/opt/ansible-venv/bin/ansible \
  -i ansible/inventories/staging.ini all -m ping \
  --private-key ~/.ssh/YOUR_DEPLOY_KEY.pem

Every host must answer pong. A timeout means the app security groups still name jenkins-server-sg instead of ansible-server-sg. A host key error means Step 4.3 scanned a different address form.

Delete the manual clone and any copied key afterwards. The pipeline supplies its own checkout and its own bound key. A spare private key sitting in a home directory is a real finding in the report.

4.6 · Deployment contract from page 1

ansible/site-swarm.yml must:
  1. accept target_environment=staging or production
  2. select ansible/group_vars/vault-staging.yml or
     ansible/group_vars/vault-production.yml
  3. read the Docker Hub deploy token from that encrypted vault
  4. use image_tag for both application images
  5. run python manage.py migrate --noinput with the new API image
  6. stop immediately if migration fails
  7. update API and frontend Swarm services to image_tag
  8. set GIT_COMMIT from git_commit and APP_VERSION from app_version
  9. wait for the service update to finish

Do not put migrations in a vague "the container starts them" step. The playbook runs them once, before the API service update. A failed migration leaves the old service image running.

Jenkins owns sequence; Ansible owns deployment. Jenkins selects one static inventory and passes target_environment, image_tag, git_commit, and app_version. Page 1 owns the playbook and vault selection. Splitting the boxes did not move this line; it only moved where the playbook process starts.

Checkpoint: ansible-server shows as an online Jenkins node with the ansible label and one executor. The venv reports a bounded ansible-core and can list community.docker. A manual ansible ... -m ping reaches all four app hosts with strict host key checking on. The manual clone and any copied key are deleted.

Read the two agent lines together. The pipeline-level agent { label 'builder' } gives every stage the Jenkins box by default, and the deploy stage overrides it with agent { label 'ansible' }. That is the whole split: checks, builds, and pushes cannot run where the deploy key lives, and the playbook cannot run where the Docker socket lives.

The deploy stage calls checkout scm again, because a second agent means a second workspace and skipDefaultCheckout(true) turns off the implicit checkout. It is the same PR commit, cloned on the other box. The variables it needs, IMAGE_TAG, GIT_COMMIT, and SHORT_SHA, were set with env. in the first stage and belong to the whole build, so they cross the node boundary without being passed anywhere.

Keeping the top-level agent instead of agent none is deliberate. The post block runs load('jenkins/notify.groovy') and docker image prune, and both need a workspace with the repo and a Docker daemon. With agent none there is no workspace at the end of the build and those steps fail.

The frontend smoke paths assume page 1 configures nginx or the Swarm ingress so /api/, /healthz/, and /readyz/ reach the API. The current supplied nginx.conf only serves static files. Do not mark this pipeline green until page 1 adds that routing.

The staging curl checks now run from ansible-server, inside the same stage as the deploy. They call the frontend's public port 80, which is open to 0.0.0.0/0, so no new security group rule is needed.

Swarm updates are asynchronous. Page 1 waits for the role, but each live curl still retries up to 30 times with a five-second pause. The pipeline fails after the last attempt. The version loop also requires the deployed response to contain SHORT_SHA.

These tests are temporary. python manage.py check, a Vue production build, the deliberate pass/fail switch, and curl calls prove pipeline wiring. They do not satisfy the final unit, integration, and Web UI testing rubric.

5.2 · Shared staging concurrency

disableConcurrentBuilds(abortPrevious: true) stops an old commit of the same PR. Without abortPrevious, the old run finishes first and the new run waits. Remove the option only if aborting builds causes trouble on your Jenkins version.

The existing notify.groovy treats ABORTED as a failure. An old run stopped by abortPrevious can send a failure email. That noise is the cost of making the latest commit win quickly. If the team removes abortPrevious, keep plain disableConcurrentBuilds() and wait for the old run.

lock(resource: 'rmit-store-staging', inversePrecedence: true) works across the PR child jobs. Only one deploy plus live-test block runs at once. The newest waiting run gets the lock next.

The single executor on ansible-server is a second, coarser limit on the same thing. Even without the lock, two deployments could not run at once. Keep the lock anyway: it is what makes the newest PR win, and it also covers the production job, which uses the other inventory but the same Swarm cluster pair.

An older run from a different PR can still remain in the lock queue. Cancel stale queue entries during the assignment demo. Jenkins has no per-PR staging copy in this design.

Ownership means the version that is live now. The version endpoint is the proof. Do not rely on the last green badge alone.

⚠️ Step 10 — Limits, fixes, and the final check

10.1 · Known limits

HTTPS
  Jenkins uses public HTTP on 8080. Login traffic is not encrypted.

Rollback
  production failure prints a command. It does not run it.

Controller
  one Jenkins controller is also the only build executor.
  a second job queues instead of running.

Docker socket
  Jenkins has root-equivalent control of jenkins-server.
  it cannot reach an app box, but it can still ask Jenkins
  for the deploy key inside a pipeline it defines.

Agent
  if ansible-server is offline, every deploy stage fails
  and no release can reach either environment.

Staging
  one shared environment. New PR deploys overwrite old ones.

Tests
  Django check, Vue build, deliberate failure, and curl are temporary.
  Real unit, integration, and Web UI suites are still required.

Capacity
  jenkins-server is a t3.small with 2 GiB of RAM and a 2 GiB swap file.
  sibling Docker builds are not capped by the Jenkins container limit,
  so a heavy npm build can still pressure the whole box.
  ansible-server is nearly idle between deployments.

Put these in the report. Specific limits are better than claims the demo cannot prove. In particular, do not describe the two-box split as full build isolation. It removes a network path, not the credential path.

10.2 · Fast fault map

Webhook delivery is red:
  check JENKINS_IP, port 8080 CIDR, trailing /github-webhook/, and secret

PR job does not appear:
  scan multibranch job, check github-token, PR discovery, and target main

Docker permission denied:
  re-read socket GID, rebuild runtime.env, recreate Jenkins container

Deploy stage waits forever in the queue:
  the ansible-server node is offline. Read Nodes → ansible-server → Log.
  usual causes: Java missing, ansible-agent-ssh key wrong,
  ansible-server-sg missing the jenkins-server-sg rule

ansible-playbook: not found:
  the stage ran on the wrong node, or the venv path is wrong.
  the stage must declare agent { label 'ansible' }

couldn't resolve module community.docker:
  ANSIBLE_COLLECTIONS_PATH is not set or the bootstrap installed
  the collection into root's home instead of /opt/ansible-collections

Ansible host is missing or unreachable:
  check the selected static INI file, BACKEND/FRONTEND IPs, SSH user,
  and that the app groups allow ansible-server-sg, not jenkins-server-sg

Build is killed with no error:
  out of memory on the 2 GiB Jenkins box. Check swap and dmesg.

SSH host key failed:
  compare fingerprint, then update known_hosts; never disable checking

Migration failed:
  stop. Do not update Swarm. Read migration output and target vault.

Health works but version is old:
  deployment failed. Check exact service image and GIT_COMMIT env.

Email missing:
  send a test email in Jenkins System page before debugging notify.groovy

Debug one layer at a time. Webhook, checkout, checks, registry, Ansible, Swarm, endpoint, then email.
