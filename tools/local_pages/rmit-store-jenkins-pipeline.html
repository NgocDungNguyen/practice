🔧 RMIT Store: Jenkins PR and Production Pipelines

This is page 2 of the deployment guide. It is for the teammate who owns Jenkins. You will run Jenkins on its own t3.medium EC2 box. You will make one pipeline for pull requests and one for protected main. Both use the existing jenkins/notify.groovy alert module. The AWS hosts, Ansible inventory, vault files, Docker Swarm services, and migration role come from page 1: Ansible and Swarm.

🎯 Overview — two paths, one Jenkins server

0.1 · The whole design

Jenkins and Ansible share one physical EC2 host. Their software stays separate. Jenkins is a long-running container. Ansible starts in a sibling runner container for one deploy, then exits.

0.2 · Pull request path

PR opened, reopened, ready for review, or updated with a new commit
  → checkout latest PR commit
  → temporary Django and Vue checks
  → build and push:
      DOCKERHUB_USER/rmit-store-api:pr-PR_NUMBER-SHORTSHA
      DOCKERHUB_USER/rmit-store-frontend:pr-PR_NUMBER-SHORTSHA
  → Ansible runs migrations and deploys that exact tag to staging
  → curl-based live staging placeholder runs
  → Jenkins posts a green or red commit status to GitHub
  → existing notify.groovy emails the team on failure

All pull requests share staging. Only one deploy and live-check block runs at a time. A new commit aborts an older run of the same PR. The newest waiting PR gets the staging lock next.

Check the version before manual testing. Another PR may replace staging. /api/version/ tells you which commit is live.

0.3 · Production path

one human approval + green Jenkins PR status
  → a human presses Merge
  → GitHub creates a push to protected main
  → production job checks out the merged commit
  → temporary checks
  → build and push SHORTSHA tags
  → capture the previous production tag
  → Ansible runs migrations and deploys the exact new tag
  → smoke /healthz/, /readyz/, and /api/version/ through frontend
  → email on failure

No full end-to-end journey runs in production. A purchase test creates data. Run it on staging before Merge.

There is no automatic rollback. A failed production smoke test leaves the pipeline red, sends email, and prints the previous tag plus a manual rollback command. Production can remain broken until a person acts.

Checkpoint: you can trace both paths. PRs deploy pr-PR_NUMBER-SHORTSHA to shared staging. A protected main push deploys SHORTSHA to production. Both paths use Ansible migrations, exact image tags, GitHub status, and the existing email module.

☁️ Step 1 — Create the Jenkins EC2 box

1.1 · Launch settings

Where: AWS console → EC2 → Launch instance.

Name              jenkins-server
AMI               Amazon Linux 2023, x86_64
Instance type     t3.medium
Storage           30 GiB gp3
IAM role          none needed
Security group    jenkins-server-sg

Use an Elastic IP if the Learner Lab allows it.
Write the public value down as JENKINS_IP.

The public URL is http://JENKINS_IP:8080. HTTPS is future work. Do not claim that this HTTP setup protects login traffic.

1.2 · Security group rules

Port 8080 serves both the Jenkins UI and /github-webhook/. Limit it to team addresses and GitHub's current webhook networks.

jenkins-server-sg inbound:
  SSH         TCP 22     source TEAM_PUBLIC_IP/32
  Jenkins     TCP 8080   source TEAM_PUBLIC_IP/32
  Jenkins     TCP 8080   source each current GitHub hooks CIDR

app Swarm security groups:
  SSH         TCP 22     source jenkins-server-sg

# Get GitHub's current webhook CIDRs. Run on your laptop.
curl -s https://api.github.com/meta | jq -r '.hooks[]'

GitHub changes these CIDRs sometimes. Check them again before the demo. If your lab cannot add all GitHub ranges, use 0.0.0.0/0 on 8080 only as a recorded short-term limit. Keep the Jenkins login locked and use a webhook secret.

A security group cannot allow one URL path. A CIDR rule opens all of port 8080 to that source. The Jenkins login still needs strong authentication.

2.5 · Complete Compose file

# jenkins/production/compose.yaml
services:
  jenkins:
    build:
      context: ../..
      dockerfile: jenkins/production/Dockerfile
    image: rmit-store-jenkins:1.0.0
    container_name: rmit-store-jenkins
    restart: unless-stopped
    user: "1000:1000"
    group_add:
      - "${DOCKER_GID}"
    ports:
      - "8080:8080"
    env_file:
      - /etc/rmit-jenkins/jenkins.env
    environment:
      JAVA_OPTS: "-Djenkins.install.runSetupWizard=false -Xms512m -Xmx1536m"
      CASC_JENKINS_CONFIG: "/var/jenkins_home/casc/production.yaml,/var/jenkins_home/casc/alerting.yaml"
    volumes:
      - /var/jenkins_home:/var/jenkins_home
      - /var/run/docker.sock:/var/run/docker.sock
      - ../casc/production.yaml:/var/jenkins_home/casc/production.yaml:ro
      - ../casc/alerting.yaml:/var/jenkins_home/casc/alerting.yaml:ro
    mem_limit: 3g
    cpus: 1.5

The volume keeps jobs, plugins, build records, and credentials across restarts. The CPU and memory caps apply to Jenkins itself. Sibling image builds use the host daemon outside these caps. Each Ansible runner gets its own limits in Step 4.

The Docker socket is root-equivalent host access. A trusted PR can change Jenkinsfile.pr, control the host daemon, and ask Jenkins for credentials. This is acceptable only for this small course team, where every repo writer is trusted. Do not accept forked or outside PRs. Isolated agents and a pipeline definition loaded from trusted main are future hardening.

🔐 Step 3 — Add credentials and GitHub access

3.1 · Fine-grained GitHub token

Where: GitHub → Settings → Developer settings → Personal access tokens → Fine-grained tokens.

Resource owner       the assigned course organisation
Repository access    only the assigned private repository
Expiration           after the assignment demo

Repository permissions:
  Contents           Read-only
  Pull requests      Read-only

  Metadata           Read-only, added by GitHub

This token reads source, discovers pull requests, and writes the normal Jenkins commit status. It does not need repository administration because you create the webhook by hand.

Do not grant Checks write access unless you add and configure a Checks plugin. This guide uses commit statuses for branch protection.

3.3 · Private Docker Hub repositories

Create two private repositories:
  DOCKERHUB_USER/rmit-store-api
  DOCKERHUB_USER/rmit-store-frontend

Create one Docker Hub access token with read and write access.
Store it only in dockerhub-creds.

PR tags look like pr-42-a1b2c3d4. Production tags look like a1b2c3d4. If both exact image tags exist on a rerun, the pipeline verifies and reuses them. If only one exists, it fails as a partial publish. It never overwrites either tag.

Never deploy only latest. An exact tag links GitHub, Docker Hub, Ansible, the running API, and rollback evidence.

3.4 · How secrets reach the runner

Jenkins binds the SSH key and vault password only around the deploy shell. The shell turns off trace output. It writes the vault password to a mode-600 temporary file. A trap deletes it. The child container receives file paths, not secret text in command arguments. dockerhub-creds is used only in image build and push stages. Page 1 already stores the read-only deploy token in each encrypted Ansible vault.

set +x
umask 077
SECRET_DIR="$(mktemp -d "$WORKSPACE/.ci-secrets.XXXXXX")"
trap 'rm -rf "$SECRET_DIR"' EXIT INT TERM

printf '%s' "$ANSIBLE_VAULT_PASSWORD" > "$SECRET_DIR/vault-password"

Masking is a backup, not permission control. This course design does run trusted team PR code with deployment credentials. Branch protection does not make that code safe before the build. Only trusted teammates may write branches. A later hardened design loads the pipeline from trusted main and runs builds on isolated agents.

Checkpoint: the GitHub token is limited to one private repo and has Contents read, Pull requests read, and Commit statuses write. The two Docker Hub repos are private. All six Jenkins credential IDs exist. No secret value appears in git.

4.3 · Coherent workspace mount

docker run --rm --network host --memory 768m --cpus 0.75 \
  -v "${WORKSPACE}:${WORKSPACE}:ro" \
  -v "${SSH_KEY}:/run/secrets/ssh-key:ro" \
  -v "${SECRET_DIR}/vault-password:/run/secrets/vault-password:ro" \
  -v /var/jenkins_home/.ssh/known_hosts:/run/known_hosts:ro \
  -w "${WORKSPACE}" \
  -e ANSIBLE_HOST_KEY_CHECKING=True \
  -e ANSIBLE_SSH_COMMON_ARGS="-o StrictHostKeyChecking=yes -o UserKnownHostsFile=/run/known_hosts" \
  rmit-store-ansible-runner:1.0.0 \
  ansible-playbook \
    -i ansible/inventories/staging.ini \
    ansible/site-swarm.yml \
    --private-key /run/secrets/ssh-key \
    --vault-password-file /run/secrets/vault-password \
    -e target_environment=staging \
    -e image_tag="$IMAGE_TAG" \
    -e git_commit="$GIT_COMMIT" \
    -e app_version="$IMAGE_TAG"

The Docker daemon runs on the host. It resolves bind-mount paths on the host. This works because the Jenkins container bind mounts host /var/jenkins_home at the same path, so WORKSPACE and Jenkins credential-file paths exist on both sides.

The runner has isolated dependencies and limits. Jenkins does not install Ansible or Python packages. Each runner gets 768 MiB and 0.75 CPU, then exits after the playbook ends.

4.4 · Deployment contract from page 1

ansible/site-swarm.yml must:
  1. accept target_environment=staging or production
  2. select ansible/group_vars/vault-staging.yml or
     ansible/group_vars/vault-production.yml
  3. read the Docker Hub deploy token from that encrypted vault
  4. use image_tag for both application images
  5. run python manage.py migrate --noinput with the new API image
  6. stop immediately if migration fails
  7. update API and frontend Swarm services to image_tag
  8. set GIT_COMMIT from git_commit and APP_VERSION from app_version
  9. wait for the service update to finish

Do not put migrations in a vague "the container starts them" step. The playbook runs them once, before the API service update. A failed migration leaves the old service image running.

Jenkins owns sequence; Ansible owns deployment. Jenkins selects one static inventory and passes target_environment, image_tag, git_commit, and app_version. Page 1 owns the playbook and vault selection.

4.5 · Pin SSH host keys

# jenkins-server, once per app host
sudo mkdir -p /var/jenkins_home/.ssh
sudo touch /var/jenkins_home/.ssh/known_hosts

for IP in STAGING_BACKEND_IP STAGING_FRONTEND_IP PRODUCTION_BACKEND_IP PRODUCTION_FRONTEND_IP; do
  ssh-keyscan -H "$IP" | sudo tee -a /var/jenkins_home/.ssh/known_hosts
done

sudo chown 1000:1000 /var/jenkins_home/.ssh/known_hosts
sudo chmod 600 /var/jenkins_home/.ssh/known_hosts

Compare fingerprints with a teammate through a trusted channel. Do not accept an unknown key in the pipeline.

Strict checking stays on. The runner command overrides any old host_key_checking=False setting.

Checkpoint: rmit-store-ansible-runner:1.0.0 contains bounded ansible-core, openssh-client, and community.docker. It reads a committed static inventory, mounts only workspace, SSH key, vault password, and known_hosts, runs migrations first, and exits after each deployment.

📦 Step 5 — Create root Jenkinsfile.pr

5.1 · Complete pull request pipeline

// Jenkinsfile.pr
pipeline {
  agent any

  options {
    skipDefaultCheckout(true)
    disableConcurrentBuilds(abortPrevious: true)
    timestamps()
    buildDiscarder(logRotator(numToKeepStr: '20'))
  }

  environment {
    BREAK_PIPELINE_TESTS = 'no'
    RUNNER_IMAGE = 'rmit-store-ansible-runner:1.0.0'
    STAGING_FRONTEND = 'http://STAGING_FRONTEND_IP'
  }

  stages {
    stage('Checkout latest PR commit') {
      steps {
        checkout scm
        script {
          env.GIT_COMMIT = sh(
            script: 'git rev-parse HEAD',
            returnStdout: true
          ).trim()
          env.SHORT_SHA = env.GIT_COMMIT.take(8)
          env.IMAGE_TAG = "pr-${env.CHANGE_ID}-${env.SHORT_SHA}"
        }
      }
      post {
        failure { script { env.FAILED_STAGE = env.STAGE_NAME } }
      }
    }

    stage('Guard PR target') {
      steps {
        script {
          if (!env.CHANGE_ID) {
            error('This job accepts pull request heads only')
          }
          if (env.CHANGE_TARGET != 'main') {
            error("PR target must be main, got ${env.CHANGE_TARGET}")
          }
        }
      }
      post {
        failure { script { env.FAILED_STAGE = env.STAGE_NAME } }
      }
    }

    stage('Temporary checks') {
      steps {
        sh '''
          set -eu

          docker run --rm \
            -v "$WORKSPACE/server:/src:ro" \
            -w /tmp/check \
            python:3.12-slim \
            sh -c 'cp -a /src/. . && \
              pip install --no-cache-dir -r requirements.txt >/tmp/pip.log && \
              python manage.py check'

          docker run --rm \
            -v "$WORKSPACE/client:/src:ro" \
            -w /tmp/check \
            node:22-slim \
            sh -c 'cp -a /src/. . && npm ci && npm run build'

          if [ "$BREAK_PIPELINE_TESTS" = "yes" ]; then
            echo "Deliberate temporary failure for the pipeline demo"
            exit 1
          fi

          # REPLACE HERE when the testing teammate finishes:
          #   backend unit + integration command
          #   frontend unit command
          #   Web UI command
        '''
      }
      post {
        failure { script { env.FAILED_STAGE = env.STAGE_NAME } }
      }
    }

    stage('Build and push immutable images') {
      steps {
        withCredentials([
          usernamePassword(
            credentialsId: 'dockerhub-creds',
            usernameVariable: 'DOCKERHUB_USER',
            passwordVariable: 'DOCKERHUB_TOKEN'
          )
        ]) {
          sh '''
            set +x
            set -eu
            printf '%s' "$DOCKERHUB_TOKEN" |
              docker login -u "$DOCKERHUB_USER" --password-stdin
            trap 'docker logout >/dev/null 2>&1 || true' EXIT

            API_IMAGE="$DOCKERHUB_USER/rmit-store-api:$IMAGE_TAG"
            FRONTEND_IMAGE="$DOCKERHUB_USER/rmit-store-frontend:$IMAGE_TAG"

            api_exists=no
            frontend_exists=no
            if docker manifest inspect "$API_IMAGE" >/dev/null 2>&1; then
              api_exists=yes
            fi
            if docker manifest inspect "$FRONTEND_IMAGE" >/dev/null 2>&1; then
              frontend_exists=yes
            fi

            if [ "$api_exists" = yes ] && [ "$frontend_exists" = yes ]; then
              echo "Both immutable tags exist. Verified and reusing $IMAGE_TAG."
            elif [ "$api_exists" = yes ] || [ "$frontend_exists" = yes ]; then
              echo "Partial publish: exactly one image has tag $IMAGE_TAG"
              exit 1
            else
              docker build -f Dockerfile.api -t "$API_IMAGE" .
              docker build -f Dockerfile.frontend -t "$FRONTEND_IMAGE" .
              docker push "$API_IMAGE"
              docker push "$FRONTEND_IMAGE"
            fi
          '''
        }
      }
      post {
        failure { script { env.FAILED_STAGE = env.STAGE_NAME } }
      }
    }

    stage('Deploy and test shared staging') {
      steps {
        script {
          lock(resource: 'rmit-store-staging', inversePrecedence: true) {
            withCredentials([
              sshUserPrivateKey(
                credentialsId: 'ec2-deploy-key',
                keyFileVariable: 'SSH_KEY'
              ),
              string(
                credentialsId: 'ansible-vault-password',
                variable: 'ANSIBLE_VAULT_PASSWORD'
              )
            ]) {
              sh '''
                set +x
                set -eu
                umask 077
                SECRET_DIR="$(mktemp -d "$WORKSPACE/.ci-secrets.XXXXXX")"
                trap 'rm -rf "$SECRET_DIR"' EXIT INT TERM

                printf '%s' "$ANSIBLE_VAULT_PASSWORD" > "$SECRET_DIR/vault-password"

                docker run --rm --network host --memory 768m --cpus 0.75 \
                  -v "${WORKSPACE}:${WORKSPACE}:ro" \
                  -v "${SSH_KEY}:/run/secrets/ssh-key:ro" \
                  -v "${SECRET_DIR}/vault-password:/run/secrets/vault-password:ro" \
                  -v /var/jenkins_home/.ssh/known_hosts:/run/known_hosts:ro \
                  -w "${WORKSPACE}" \
                  -e ANSIBLE_HOST_KEY_CHECKING=True \
                  -e ANSIBLE_SSH_COMMON_ARGS="-o StrictHostKeyChecking=yes -o UserKnownHostsFile=/run/known_hosts" \
                  "$RUNNER_IMAGE" \

5.2 · Shared staging concurrency

disableConcurrentBuilds(abortPrevious: true) stops an old commit of the same PR. Without abortPrevious, the old run finishes first and the new run waits. Remove the option only if aborting builds causes trouble on your Jenkins version.

The existing notify.groovy treats ABORTED as a failure. An old run stopped by abortPrevious can send a failure email. That noise is the cost of making the latest commit win quickly. If the team removes abortPrevious, keep plain disableConcurrentBuilds() and wait for the old run.

lock(resource: 'rmit-store-staging', inversePrecedence: true) works across the PR child jobs. Only one deploy plus live-test block runs at once. The newest waiting run gets the lock next.

An older run from a different PR can still remain in the lock queue. Cancel stale queue entries during the assignment demo. Jenkins has no per-PR staging copy in this design.

# Before a teammate starts manual staging tests:
curl -fsS http://STAGING_FRONTEND_IP/api/version/

# The "commit" value must match that PR's SHORTSHA.
# If it differs, staging belongs to another run.

Ownership means the version that is live now. The version endpoint is the proof. Do not rely on the last green badge alone.

pipeline {
  agent any

  options {
    skipDefaultCheckout(true)
    disableConcurrentBuilds()
    timestamps()
    buildDiscarder(logRotator(numToKeepStr: '20'))
  }

  environment {
    BREAK_PIPELINE_TESTS = 'no'

    PRODUCTION_FRONTEND = 'http://PRODUCTION_FRONTEND_IP'
  }

  stages {
    stage('Checkout merged main') {
      steps {
        checkout scm
        script {
          env.GIT_COMMIT = sh(
            script: 'git rev-parse HEAD',
            returnStdout: true
          ).trim()
          env.SHORT_SHA = env.GIT_COMMIT.take(8)
          env.IMAGE_TAG = env.SHORT_SHA
        }
      }
      post {
        failure { script { env.FAILED_STAGE = env.STAGE_NAME } }
      }

    stage('Guard protected main push') {
      steps {

          }
          def pushCauses = currentBuild.getBuildCauses(
            'com.cloudbees.jenkins.GitHubPushCause'
          )
          if (pushCauses.isEmpty()) {
            error('Production accepts a GitHub push event, not Build Now')
          }
        }
      }
      post {
        failure { script { env.FAILED_STAGE = env.STAGE_NAME } }
      }
    }

    stage('Temporary checks') {
      steps {
        sh '''
          set -eu

          docker run --rm \
            -v "$WORKSPACE/server:/src:ro" \
            -w /tmp/check \

            -v "$WORKSPACE/client:/src:ro" \
            -w /tmp/check \

          if [ "$BREAK_PIPELINE_TESTS" = "yes" ]; then
            echo "Deliberate temporary failure for the pipeline demo"
            exit 1
          fi

          # REPLACE HERE with the testing teammate's real commands.
        '''
      }
      post {
        failure { script { env.FAILED_STAGE = env.STAGE_NAME } }
      }
    }

    stage('Capture previous production commit') {
      steps {
        sh '''
          set -eu
          : > previous-production-commit.txt
          curl -fsS "$PRODUCTION_FRONTEND/api/version/" \
            > previous-production-version.json || true

          if [ -s previous-production-version.json ]; then
            sed -n \
              's/.*"commit"[[:space:]]*:[[:space:]]*"\([^"]*\)".*/\1/p' \
              previous-production-version.json \
              > previous-production-commit.txt
          fi

          echo "Previous production commit captured if the endpoint answered"
        '''
      }
      post {
        failure { script { env.FAILED_STAGE = env.STAGE_NAME } }
      }
    }

    stage('Build and push immutable images') {
      steps {
        withCredentials([
          usernamePassword(
            credentialsId: 'dockerhub-creds',
            usernameVariable: 'DOCKERHUB_USER',
            passwordVariable: 'DOCKERHUB_TOKEN'
          )
        ]) {
          sh '''
            set +x
            set -eu
            printf '%s' "$DOCKERHUB_TOKEN" |
              docker login -u "$DOCKERHUB_USER" --password-stdin
            trap 'docker logout >/dev/null 2>&1 || true' EXIT

            API_IMAGE="$DOCKERHUB_USER/rmit-store-api:$IMAGE_TAG"
            FRONTEND_IMAGE="$DOCKERHUB_USER/rmit-store-frontend:$IMAGE_TAG"

            api_exists=no
            frontend_exists=no
            if docker manifest inspect "$API_IMAGE" >/dev/null 2>&1; then
              api_exists=yes
            fi
            if docker manifest inspect "$FRONTEND_IMAGE" >/dev/null 2>&1; then
              frontend_exists=yes
            fi

            if [ "$api_exists" = yes ] && [ "$frontend_exists" = yes ]; then
              echo "Both immutable tags exist. Verified and reusing $IMAGE_TAG."
            elif [ "$api_exists" = yes ] || [ "$frontend_exists" = yes ]; then
              echo "Partial publish: exactly one image has tag $IMAGE_TAG"
              exit 1
            else

              docker build -f Dockerfile.frontend -t "$FRONTEND_IMAGE" .

        }
      }

        failure { script { env.FAILED_STAGE = env.STAGE_NAME } }
      }
    }

    stage('Deploy exact tag to production') {
      steps {
        withCredentials([
          sshUserPrivateKey(
            credentialsId: 'ec2-deploy-key',
            keyFileVariable: 'SSH_KEY'
          ),
          string(
            credentialsId: 'ansible-vault-password',
            variable: 'ANSIBLE_VAULT_PASSWORD'

            set -eu
            umask 077

      }

        failure { script { env.FAILED_STAGE = env.STAGE_NAME } }
      }

    stage('Production smoke through frontend') {

          set -eu

          retry_url() {
            url="$1"
            output="$2"
            attempt=1

                return 0
              fi

          retry_url "$PRODUCTION_FRONTEND/readyz/" production-ready.json

          attempt=1

            if curl -fsS "$PRODUCTION_FRONTEND/api/version/" \
                 > production-version.json &&
               grep -F "$SHORT_SHA" production-version.json >/dev/null; then
              cat production-version.json
              break
            fi

              exit 1
            fi
            echo "Waiting for version $SHORT_SHA, attempt $attempt/30"
            attempt=$((attempt + 1))
            sleep 5
          done
        '''
      }
      post {
        failure { script { env.FAILED_STAGE = env.STAGE_NAME } }
      }
    }
  }

  post {
    failure {
      script {
        def oldCommit = fileExists('previous-production-commit.txt') ?
          readFile('previous-production-commit.txt').trim() : ''
        def oldTag = oldCommit.take(8)

        if (oldCommit ==~ /(?i)[0-9a-f]{8,40}/) {
          echo """
PREVIOUS PRODUCTION TAG: ${oldTag}
NO AUTOMATIC ROLLBACK WAS RUN.

Manual rollback command, run through the same credential-bound runner:
ansible-playbook -i ansible/inventories/production.ini ansible/site-swarm.yml \\
  --private-key /run/secrets/ssh-key \\
  --vault-password-file /run/secrets/vault-password \\
  -e target_environment=production \\
  -e image_tag=${oldTag} \\
  -e git_commit=${oldCommit} \\
  -e app_version=${oldTag}
"""
        } else {
          echo """
PREVIOUS PRODUCTION TAG: unavailable
NO AUTOMATIC ROLLBACK WAS RUN.
Find the last green production job and its immutable Docker Hub tag.
Then run the same manual Ansible command with that verified tag.
"""
        }
      }
    }
    always {
      script {
        load('jenkins/notify.groovy').notifyTeam()
      }
      sh 'docker image prune -f || true'
    }
  }
}

The version response uses the app's real JSON field, "commit". The pipeline saves its first eight characters because production images use the eight-character tag.

The production curls also retry 30 times with five-second pauses. This covers the short gap while Swarm replaces tasks, even though the page 1 role already waits. Exhausting the retries makes the stage red.

⚠️ Step 10 — Limits, fixes, and the final check

10.1 · Known limits

HTTPS
  Jenkins uses public HTTP on 8080. Login traffic is not encrypted.

Rollback
  production failure prints a command. It does not run it.

Controller
  one Jenkins controller is also the only build executor.

Docker socket
  Jenkins has root-equivalent control of its EC2 host.

Staging
  one shared environment. New PR deploys overwrite old ones.

Tests
  Django check, Vue build, deliberate failure, and curl are temporary.
  Real unit, integration, and Web UI suites are still required.

Capacity
  sibling Docker builds are not capped by the Jenkins limit
  each Ansible runner has its own 768 MiB and 0.75 CPU limit

Put these in the report. Specific limits are better than claims the demo cannot prove.

10.2 · Fast fault map

Webhook delivery is red:
  check JENKINS_IP, port 8080 CIDR, trailing /github-webhook/, and secret

PR job does not appear:
  scan multibranch job, check github-token, PR discovery, and target main

Docker permission denied:
  re-read socket GID, rebuild runtime.env, recreate Jenkins container

Ansible host is missing or unreachable:
  check the selected static INI file, BACKEND/FRONTEND IPs, SSH user, and SG

SSH host key failed:
  compare fingerprint, then update known_hosts; never disable checking

Migration failed:
  stop. Do not update Swarm. Read migration output and target vault.

Health works but version is old:
  deployment failed. Check exact service image and GIT_COMMIT env.

Email missing:
  send a test email in Jenkins System page before debugging notify.groovy

Debug one layer at a time. Webhook, checkout, checks, registry, Ansible, Swarm, endpoint, then email.
