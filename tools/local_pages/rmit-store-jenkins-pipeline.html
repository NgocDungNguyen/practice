🔧 RMIT Store: Jenkins PR and Production Pipelines

This is the detailed guide for the teammate who owns Jenkins. Start with the end-to-end CI/CD map. Jenkins owns one ordered flow: pull code, run unit tests, call Ansible to build, push, and deploy, run E2E tests against the deployed application, then publish the result. The AWS hosts, inventories, vault files, image tasks, Docker Swarm services, and migration role come from the Ansible and Swarm runbook.

🎯 Overview — one ordered flow, two control boxes

0.1 · The whole design

GitHub private repo

        ▼

│  1. Pull code                               │
│  2. Unit test                               │

                    ▼

                     │

Jenkins and Ansible sit on separate EC2 hosts. Jenkins controls order and reporting. ansible-server has Docker, the registry token, the SSH deploy key, and the vault password because it owns build, push, migration, and deployment.

Jenkins runs ansible-server as a permanent agent labelled ansible. Stage 3 is therefore a normal Jenkins stage with console output and a red result on any Ansible failure.

0.2 · Pull request path

PR opened, reopened, ready for review, or updated with a new commit
  → checkout latest PR commit
  → temporary unit tests
  → Ansible builds and pushes:
      DOCKERHUB_USER/rmit-store-api:pr-PR_NUMBER-SHORTSHA
      DOCKERHUB_USER/rmit-store-frontend:pr-PR_NUMBER-SHORTSHA
  → Ansible migrates and deploys that exact tag to staging
  → Jenkins runs the temporary E2E test against staging
  → Jenkins posts a green or red commit status to GitHub
  → existing notify.groovy emails the team on failure

All pull requests share staging. Only one deploy and live-check block runs at a time. A new commit aborts an older run of the same PR. The newest waiting PR gets the staging lock next.

Check the version before manual testing. Another PR may replace staging. /api/version/ tells you which commit is live.

0.3 · Production path

one human approval + green Jenkins PR status
  → a human presses Merge
  → GitHub creates a push to protected main
  → production job checks out the merged commit
  → temporary unit tests
  → Ansible builds and pushes SHORTSHA tags
  → capture the previous production tag
  → Ansible migrates and deploys the exact new tag
  → Jenkins runs the deployed-environment E2E checks
  → email on failure

The current E2E stage uses read-only health, readiness, version, and product checks. When the testing teammate supplies the real suite, keep write-heavy purchase journeys on staging and use a read-only production subset.

There is no automatic rollback. A failed production E2E test leaves the pipeline red, sends email, and prints the previous tag plus a manual rollback command. Production can remain broken until a person acts.

Checkpoint: both jobs use the same stage order. Jenkins pulls and unit-tests the commit. Ansible builds, pushes, and deploys its immutable tag. Jenkins then runs E2E and publishes the result.

🧱 Required flow: keep these stages in order

The five Jenkins stages

1. Pull code
2. Unit test
3. Ansible: build, push, deploy
4. E2E test
5. Result

GitHub is the source and trigger. Jenkins is the CI system. Do not add a GitHub Actions workflow for this path.

Temporary tests are allowed

Unit test placeholder:
  Django system check + Vue build + deliberate failure switch

E2E placeholder after deployment:
  /healthz/ + /readyz/ + /api/version/ + /api/products/

The testing teammate will replace these commands. Keep the stage names and positions unchanged: the unit test must gate Ansible, and E2E must target the deployment created by Ansible.

The handoff artifact

# release-manifest.env, archived by the successful Jenkins build
GIT_COMMIT=FULL_COMMIT_SHA
IMAGE_TAG=COMMIT_BASED_TAG
API_IMAGE=DOCKERHUB_USER/rmit-store-api:COMMIT_BASED_TAG
FRONTEND_IMAGE=DOCKERHUB_USER/rmit-store-frontend:COMMIT_BASED_TAG

Ansible writes this manifest after it pushes and deploys the pair. Jenkins archives it as evidence. The tag identifies the two images and the commit exercised by E2E.

The pipeline is done when

  • A real webhook starts the correct Jenkins job.
  • The deliberate unit failure turns the build red and prevents Ansible from running.
  • Ansible builds, pushes, and deploys API and frontend images with the same immutable tag.
  • The E2E stage runs only after Ansible succeeds.
  • The Jenkins build exposes release-manifest.env as an archived artifact.
  • The console output and archived manifest contain no credentials.

A green result includes deployment proof. It means the post-deployment E2E stage passed against the expected commit.

Checkpoint: the stage view reads Pull code, Unit test, Ansible build/push/deploy, E2E test, Result. A failure skips every stage to its right.

Port 8080 serves both the Jenkins UI and /github-webhook/. Limit it to team addresses and GitHub's current webhook networks.

  SSH         TCP 22     source ansible-server-sg

# Get GitHub's current webhook CIDRs. Run on your laptop.
curl -s https://api.github.com/meta | jq -r '.hooks[]'

SSH flows in one direction only. Jenkins opens 22 on ansible-server to launch the agent, and ansible-server opens 22 on the app boxes to deploy. If you left jenkins-server-sg on the app groups from an earlier draft, remove it now. The split is only real once that rule is gone.

1.4 · Add swap on jenkins-server

A t3.small has 2 GiB of RAM. The Java controller and a Node production build can want that much at the same moment. Swap turns a hard out-of-memory kill into a slow build.

# jenkins-server
sudo dd if=/dev/zero of=/swapfile bs=1M count=2048 status=progress
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
free -h

Swap is a safety net, not headroom. If temporary unit-test containers still get killed, use a larger instance or a separate test agent. Release image builds already run on ansible-server.

2.2 · Complete production Dockerfile

# jenkins/production/Dockerfile
FROM jenkins/jenkins:lts-jdk21

USER root
RUN apt-get update \
    && apt-get install -y --no-install-recommends \
       ca-certificates curl git \
    && install -m 0755 -d /etc/apt/keyrings \
    && curl -fsSL https://download.docker.com/linux/debian/gpg \
       -o /etc/apt/keyrings/docker.asc \
    && chmod a+r /etc/apt/keyrings/docker.asc \
    && . /etc/os-release \
    && echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/debian $VERSION_CODENAME stable" \
       > /etc/apt/sources.list.d/docker.list \
    && apt-get update \
    && apt-get install -y --no-install-recommends \
       docker-ce-cli docker-buildx-plugin \
    && rm -rf /var/lib/apt/lists/*

RUN jenkins-plugin-cli --plugins \
    configuration-as-code \
    credentials-binding \
    email-ext \
    git \
    github \
    github-branch-source \
    lockable-resources \
    pipeline-stage-view \
    prometheus \
    ssh-slaves \
    workflow-aggregator

USER jenkins

github-branch-source discovers pull requests and reports the normal Jenkins commit status. No GitHub Checks plugin is installed, so this guide does not promise a GitHub Check Run.

ssh-slaves is the SSH Build Agents plugin. It is the one plugin the split adds. Jenkins uses it to open an SSH connection to ansible-server, copy the agent JAR, and start the agent process under Java.

Install the official Docker CLI, not Debian's docker.io package. The live Jenkins image proved that docker.io can leave this container without /usr/bin/docker. The CLI above talks to the host daemon through the socket mounted in the next card. No Docker daemon runs inside Jenkins.

2.5 · Complete Compose file

# jenkins/production/compose.yaml
services:
  jenkins:
    build:
      context: ../..
      dockerfile: jenkins/production/Dockerfile
    image: rmit-store-jenkins:1.0.0
    container_name: rmit-store-jenkins
    restart: unless-stopped
    user: "1000:1000"
    group_add:
      - "${DOCKER_GID}"
    ports:
      - "8080:8080"
    env_file:
      - /etc/rmit-jenkins/jenkins.env
    environment:
      JAVA_OPTS: "-Djenkins.install.runSetupWizard=false -Xms256m -Xmx1024m"
      CASC_JENKINS_CONFIG: "/var/jenkins_home/casc/production.yaml,/var/jenkins_home/casc/alerting.yaml"
    volumes:
      - /var/jenkins_home:/var/jenkins_home
      - /var/run/docker.sock:/var/run/docker.sock
      - ../casc/production.yaml:/var/jenkins_home/casc/production.yaml:ro
      - ../casc/alerting.yaml:/var/jenkins_home/casc/alerting.yaml:ro
    mem_limit: 1500m
    cpus: 1.5

The volume keeps jobs, plugins, build records, and credentials across restarts. The CPU and memory caps apply to Jenkins itself. Temporary unit-test containers use the host daemon outside these caps. Release image builds run on ansible-server.

These numbers are the t3.small budget. A 1 GiB Java heap plus a roughly 1.5 GiB container cap leaves about 500 MiB plus swap for temporary unit-test containers. If you later move to a t3.medium, raise -Xmx to 1536m and mem_limit to 3g.

The Docker socket is root-equivalent host access. A trusted PR can change Jenkinsfile.pr, control the Jenkins host daemon, and ask Jenkins for credentials. The Ansible agent is more privileged because it also has Docker and the route into the app hosts. This is acceptable only for this small course team, where every repo writer is trusted. Do not accept forked or outside PRs.

3.3 · Private Docker Hub repositories

Create two private repositories:
  DOCKERHUB_USER/rmit-store-api
  DOCKERHUB_USER/rmit-store-frontend

Create one Docker Hub access token with read and write access.
Store it only in dockerhub-creds.

PR tags look like pr-42-a1b2c3d4. Production tags look like a1b2c3d4. The Ansible image role checks both exact tags before building. If both exist, it reuses them. If only one exists, it fails as a partial publish. It never overwrites either tag.

Never deploy only latest. An exact tag links GitHub, Docker Hub, Ansible, the running API, and rollback evidence.

3.4 · How secrets reach the deploy agent

Jenkins binds Docker Hub credentials, the SSH key, and the vault password only around the Ansible stage on ansible-server. The shell turns off trace output and exports the Docker Hub values for Ansible's environment lookups. It writes the vault password to a mode-600 temporary file. A trap removes it when the stage exits. ansible-playbook receives file paths and non-secret release facts in its arguments, never secret text.

set +x
umask 077
SECRET_DIR="$(mktemp -d "$WORKSPACE/.ci-secrets.XXXXXX")"
trap 'rm -rf "$SECRET_DIR"' EXIT INT TERM

printf '%s' "$ANSIBLE_VAULT_PASSWORD" > "$SECRET_DIR/vault-password"

Masking is a backup, not permission control. This course design does run trusted team PR code with deployment credentials. Branch protection does not make that code safe before the build. Only trusted teammates may write branches. A later hardened design loads the pipeline from trusted main and runs builds on isolated agents.

Checkpoint: the GitHub token is limited to one private repo and has Contents read, Pull requests read, and Commit statuses write. The two Docker Hub repos are private. All seven Jenkins credential IDs exist, including the separate ansible-agent-ssh key. dockerhub-creds is available to the Ansible stage. No secret value appears in git.

🤖 Step 4 — Turn ansible-server into the delivery agent

4.1 · Install Ansible in a virtual environment

Where: on ansible-server. Save this as jenkins/ansible-agent/bootstrap.sh in the repo and run it once, so the next person can rebuild the box from the file instead of from memory.

#!/usr/bin/env bash
# jenkins/ansible-agent/bootstrap.sh
set -euo pipefail

VENV=/opt/ansible-venv
COLLECTIONS=/opt/ansible-collections

sudo python3 -m venv "$VENV"
sudo "$VENV/bin/pip" install --no-cache-dir --upgrade pip
sudo "$VENV/bin/pip" install --no-cache-dir 'ansible-core>=2.17,<2.19'

sudo mkdir -p "$COLLECTIONS"
sudo "$VENV/bin/ansible-galaxy" collection install \
  'community.docker:>=3.10.0,<5.0.0' -p "$COLLECTIONS"

# the agent runs as ec2-user and only needs to read these
sudo chmod -R a+rX "$VENV" "$COLLECTIONS"

"$VENV/bin/ansible-playbook" --version
ANSIBLE_COLLECTIONS_PATH="$COLLECTIONS" \
  "$VENV/bin/ansible-galaxy" collection list community.docker

A virtual environment at a fixed path is this design's dependency isolation. The old runner container did the same job, but a whole box that only ever runs Ansible does not need a second layer of packaging. Nothing else on the box uses Python.

Keep the bounds equal to page 1. These are the same version ranges as ansible/requirements.yml. If page 1 changes a bound, change it here too, or the same playbook behaves differently on a laptop and in the pipeline.

4.2 · Register the permanent Jenkins node

First teach the Jenkins container the host key of ansible-server, or the SSH launch will refuse to connect.

sudo chown -R 1000:1000 /var/jenkins_home/.ssh
sudo chmod 700 /var/jenkins_home/.ssh
sudo chmod 600 /var/jenkins_home/.ssh/known_hosts

Number of executors     1
Remote root directory   /opt/jenkins-agent

4.3 · Pin the app host keys on ansible-server

# ansible-server, as ec2-user, once per app host
mkdir -p ~/.ssh
chmod 700 ~/.ssh

for IP in STAGING_IP \
          PRODUCTION_BACKEND_IP PRODUCTION_FRONTEND_IP; do
  ssh-keyscan -H "$IP" >> ~/.ssh/known_hosts
done

chmod 600 ~/.ssh/known_hosts
ssh-keygen -F STAGING_IP -f ~/.ssh/known_hosts

These keys used to live in /var/jenkins_home/.ssh/known_hosts. They belong here now, because this is the box that opens the connections. The Jenkins box keeps a known_hosts file too, but it holds exactly one entry: ansible-server.

Use the same address form here that ansible_host uses in the page 1 inventories. A key scanned for a public IP does not match a connection made to the private IP.

The frontend smoke paths assume page 1 configures nginx or the Swarm ingress so /api/, /healthz/, and /readyz/ reach the API. The current supplied nginx.conf only serves static files. Do not mark this pipeline green until page 1 adds that routing.

The E2E stage runs from jenkins-server after Ansible returns. It calls the frontend's public port 80, so no new security-group rule is needed. The playbook already waits for readiness and the expected commit before it returns.

These tests are temporary. python manage.py check, a Vue production build, the deliberate pass/fail switch, and curl calls prove pipeline wiring. They do not satisfy the final unit, integration, and Web UI testing rubric.

5.2 · Shared staging concurrency

disableConcurrentBuilds(abortPrevious: true) stops an old commit of the same PR. Without abortPrevious, the old run finishes first and the new run waits. Remove the option only if aborting builds causes trouble on your Jenkins version.

The existing notify.groovy treats ABORTED as a failure. An old run stopped by abortPrevious can send a failure email. That noise is the cost of making the latest commit win quickly. If the team removes abortPrevious, keep plain disableConcurrentBuilds() and wait for the old run.

lock(resource: 'rmit-store-staging', inversePrecedence: true) is a pipeline option. It keeps build, deployment, and E2E together so another PR cannot replace staging between the Ansible stage and its test. The newest waiting run gets the lock next.

The single executor on ansible-server is a second, coarser limit on the same thing. Even without the lock, two deployments could not run at once. Keep the lock anyway: it is what makes the newest PR win, and it also covers the production job, which uses the other inventory but the same Swarm cluster pair.

An older run from a different PR can still remain in the lock queue. Cancel stale queue entries during the assignment demo. Jenkins has no per-PR staging copy in this design.

# If it differs, staging belongs to another run.

Ownership means the version that is live now. The version endpoint is the proof. Do not rely on the last green badge alone.

⚠️ Step 10 — Limits, fixes, and the final check

10.1 · Known limits

HTTPS
  Jenkins uses public HTTP on 8080. Login traffic is not encrypted.

Rollback
  production failure prints a command. It does not run it.

Controller
  one Jenkins controller is also the only unit-test executor.
  a second job queues instead of running.

Docker socket
  Jenkins has root-equivalent control of jenkins-server.
  ansible-server also has Docker and the SSH route to app hosts.
  only trusted team branches may run this pipeline.

Agent
  if ansible-server is offline, every build/push/deploy stage fails
  and no release can reach either environment.

Staging
  one shared environment. New PR deploys overwrite old ones.

Tests
  Django check, Vue build, deliberate failure, and curl are temporary.
  Real unit, integration, and Web UI suites are still required.

Capacity
  jenkins-server is a t3.small with 2 GiB of RAM and a 2 GiB swap file.
  temporary unit-test containers are outside the Jenkins container limit.
  ansible-server also needs enough disk and memory for both image builds.

Put these in the report. Specific limits are better than claims the demo cannot prove. In particular, do not describe the two-box split as full build isolation. It removes a network path, not the credential path.

10.2 · Fast fault map

Webhook delivery is red:
  check JENKINS_IP, port 8080 CIDR, trailing /github-webhook/, and secret

PR job does not appear:
  scan multibranch job, check github-token, PR discovery, and target main

Docker permission denied during Unit test:
  re-read socket GID, rebuild runtime.env, recreate Jenkins container

Docker permission denied during the Ansible stage:
  log out of ansible-server after adding ec2-user to the docker group,
  log in again, then run docker version

Ansible stage waits forever in the queue:
  the ansible-server node is offline. Read Nodes → ansible-server → Log.
  usual causes: Java missing, ansible-agent-ssh key wrong,
  ansible-server-sg missing the jenkins-server-sg rule

ansible-playbook: not found:
  the stage ran on the wrong node, or the venv path is wrong.
  the stage must declare agent { label 'ansible' }

couldn't resolve module community.docker:
  ANSIBLE_COLLECTIONS_PATH is not set or the bootstrap installed
  the collection into root's home instead of /opt/ansible-collections

Ansible host is missing or unreachable:
  check the selected static INI file, BACKEND/FRONTEND IPs, SSH user,
  and that the app groups allow ansible-server-sg, not jenkins-server-sg

Build is killed with no error:
  identify the node in the stage view. Unit test uses jenkins-server;
  image build uses ansible-server. Check memory and dmesg there.

SSH host key failed:
  compare fingerprint, then update known_hosts; never disable checking

Migration failed:
  stop. Do not update Swarm. Read migration output and target vault.

Health works but version is old:
  deployment failed. Check exact service image and GIT_COMMIT env.

Email missing:
  send a test email in Jenkins System page before debugging notify.groovy

Debug in stage order. Webhook, Pull code, Unit test, Ansible build/push/deploy, E2E, Result, then email.
