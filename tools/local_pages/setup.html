🧰 Practice Environment Setup

Stand up the Weeks 4–6 delivery stack — Docker, Maven, Tomcat, and Jenkins — from a blank machine, verify every layer, then reset it to a clean slate so you can drill the whole build again with /grill-me.

🎯 What you are building

The practice topology

The course runs the delivery stack across small Amazon Linux 2023 EC2 instances. Two servers reproduce the Week 4–5 architecture; Docker gets its own host in Week 6.

jenkins-server : 8080  # Jenkins UI, builds the WAR with Maven
tomcat-server  : 8080  # Tomcat 9, receives and serves the WAR
docker-host    : —     # Docker Engine, images and containers

Use when: you want a faithful rebuild of the lab environment. One instance can host everything if you move ports around — see the port-clash drill below.

The install order

Each layer depends on the one before it, which is why the sequence matters and is worth memorising.

1. Java (Corretto 21)   # Maven, Tomcat, and Jenkins all run on the JVM
2. Maven                # builds the WAR; needs a JDK, not just a JRE
3. Tomcat 9             # serves the WAR; needs a JRE
4. Jenkins LTS          # orchestrates 2 → 3; needs Java 17 or 21
5. Docker               # independent of the JVM stack

Remember: Java first, always. Everything except Docker is a JVM application.

Why separate servers: Jenkins and Tomcat both default to port 8080, and keeping them apart also separates credentials, blast radius, and resource contention — the same reasoning the Week 5 lab asks you about.

☁️ Start from clean machines

Launch the EC2 instances

In the AWS console launch Amazon Linux 2023 instances (t2.micro or t3.micro is enough), all sharing one key pair so practice stays simple.

# Security group inbound rules
SSH   22    My IP        # shell access
HTTP  8080  My IP        # Jenkins UI / Tomcat UI
# plus 8080 from the Jenkins SG on the Tomcat SG (deployment)

Security: never open 8080 to 0.0.0.0/0 — an unlocked Jenkins on the open internet is compromised within hours.

Connect and orient yourself

SSH in with your key and confirm what machine you are on before installing anything — the Week 2 reflex.

ssh -i labsuser.pem ec2-user@<public-ip>
whoami
cat /etc/os-release
sudo yum update -y

Use when: every fresh instance, before any install. yum update first avoids stale-package surprises later.

Ghostty: make clear work on EC2

Ghostty sets TERM=xterm-ghostty, which Amazon Linux does not have in its terminfo database — so clear, top, and nano complain about an unknown terminal. Send your terminal's terminfo to the instance once, from your Mac:

infocmp -x xterm-ghostty | \
    ssh -i "devops_key.pem" ec2-user@<ec2-endpoint> -- sudo tic -x -

Remember: with sudo, the entry lands in root's ~/.terminfo (covers sudo su - shells); run it again without sudo for plain ec2-user sessions. Quick fallback either way: export TERM=xterm-256color.

Cost and cleanup: stop instances when you finish a practice session and terminate them when you finish the drill entirely. The clean-slate section below covers both paths.

No AWS credit to spare? The macOS section near the end shows how to practise the same yum commands inside an amazonlinux:2023 Docker container for free.

☕ Step 1 — Java 21 (Corretto)

Install the JDK

Amazon Corretto is AWS's OpenJDK build. On the build machine install the -devel package so you get javac — Maven compiles source, so a JRE alone is not enough.

sudo yum install -y java-21-amazon-corretto-devel
java -version
javac -version

Remember: the labs install java-21-amazon-corretto; the -devel variant adds the compiler and JDK tools. On a Tomcat-only box the plain package is fine.

Set JAVA_HOME persistently

Maven and Tomcat resolve the JVM through JAVA_HOME. Derive it from the real java binary so the line survives any architecture or version change.

echo 'export JAVA_HOME=$(dirname $(dirname $(readlink -f $(which java))))' >> ~/.bashrc
source ~/.bashrc
echo $JAVA_HOME

Remember: JAVA_HOME points at the JVM install directory; PATH decides which executables your shell finds. They solve different problems.

Checkpoint: java -version, javac -version, and echo $JAVA_HOME all report Corretto 21 — including in a brand-new SSH session.

📦 Step 2 — Maven

Download and unpack to /opt

Maven ships as a binary tarball from the Apache CDN — pinned here to 3.9.16. If the download ever 404s, the version was superseded: grab the new one from maven.apache.org/download.cgi.

cd /tmp
wget https://dlcdn.apache.org/maven/maven-3/3.9.16/binaries/apache-maven-3.9.16-bin.tar.gz
sudo tar -xzf apache-maven-3.9.16-bin.tar.gz -C /opt
sudo ln -s /opt/apache-maven-3.9.16 /opt/maven

Tip: the /opt/maven symlink means upgrades only ever touch the link — your PATH line never changes.

Put mvn on the PATH and verify

A tarball install is invisible to your shell until its bin directory is on the PATH — this is exactly the Week 4 "mvn: command not found" challenge.

echo 'export PATH=/opt/maven/bin:$PATH' >> ~/.bashrc
source ~/.bashrc
mvn -version

Use when: mvn: command not found — it is almost always a PATH problem, not a broken install.

Checkpoint: mvn -version prints the Maven version and the Corretto 21 JVM it found via JAVA_HOME.

🐈 Step 3 — Tomcat 9

Download, unpack, and start

Same tarball pattern as Maven — pinned here to 9.0.120. If the download ever 404s, grab the current 9.0.x from tomcat.apache.org/download-90.cgi.

cd /tmp
wget https://dlcdn.apache.org/tomcat/tomcat-9/v9.0.120/bin/apache-tomcat-9.0.120.tar.gz
sudo tar -xzf apache-tomcat-9.0.120.tar.gz -C /opt
sudo ln -s /opt/apache-tomcat-9.0.120 /opt/tomcat
sudo /opt/tomcat/bin/startup.sh
curl -I http://localhost:8080

Use when: curl returns HTTP/1.1 200, Tomcat is up; then open http://<tomcat-ip>:8080 in a browser for the cat splash page.

Create the manager user Jenkins will use

Remote deployment goes through Tomcat's manager application, which ships with no users at all. Add one to /opt/tomcat/conf/tomcat-users.xml just above the closing tag.

<role rolename="manager-gui"/>
<role rolename="manager-script"/>
<user username="deployer" password="<strong-password>"
      roles="manager-gui,manager-script"/>

Remember: manager-gui is for humans in a browser; manager-script is the text/API interface Jenkins uses. Jenkins needs manager-script.

Allow the manager app to be reached remotely

By default the manager app only accepts connections from localhost via a RemoteAddrValve in webapps/manager/META-INF/context.xml. Comment the valve out, then restart.

sudo nano /opt/tomcat/webapps/manager/META-INF/context.xml
# wrap the <Valve className="...RemoteAddrValve".../> element
# in <!-- ... --> comment markers
sudo /opt/tomcat/bin/shutdown.sh
sudo /opt/tomcat/bin/startup.sh

Security: in anything beyond a lab, restrict the valve's allow pattern to the Jenkins server's IP instead of removing it.

Optional: startup shortcuts or a systemd service

Symlinks give you quick manual control; a systemd unit (the Week 4 challenge) makes Tomcat survive reboots like a real service.

sudo ln -s /opt/tomcat/bin/startup.sh  /usr/local/bin/tomcatup
sudo ln -s /opt/tomcat/bin/shutdown.sh /usr/local/bin/tomcatdown
tomcatup
sudo systemctl status tomcat   # only after the Challenge 4 unit file exists

Tip: if you write the systemd unit, stop using the shortcut scripts — mixing the two leaves systemd's view of the service state wrong.

Checkpoint: the Tomcat splash page loads from your browser, and http://<tomcat-ip>:8080/manager/html accepts the deployer login.

🤵 Step 4 — Jenkins LTS

Add the repo and install

Jenkins is not in the Amazon Linux repos — add the official Jenkins yum repository and its signing key first, exactly as in Week 5. Install on its own server (or plan ports first).

sudo wget -O /etc/yum.repos.d/jenkins.repo \
    https://pkg.jenkins.io/redhat-stable/jenkins.repo
sudo rpm --import https://pkg.jenkins.io/redhat-stable/jenkins.io-2023.key
sudo yum upgrade -y
sudo yum install -y fontconfig java-21-amazon-corretto
sudo yum install -y jenkins git

Remember: fontconfig is a real dependency (Jenkins renders images headlessly), and Jenkins needs Git on the box to clone your repository.

Start it and unlock the UI

Enable the service, then trade the generated secret for your first admin account in the browser.

sudo systemctl daemon-reload
sudo systemctl enable --now jenkins
sudo systemctl status jenkins
sudo cat /var/lib/jenkins/secrets/initialAdminPassword

Use when: the unlock screen at http://<jenkins-ip>:8080 asks for the initial admin password — paste the secret, choose Install suggested plugins, create your admin user.

Install the two lab plugins

Under Manage Jenkins → Plugins → Available, add the two plugins the Week 5 pipeline depends on, then restart if prompted.

Maven Integration     # adds the "Maven project" job type
Deploy to container   # adds the WAR-to-Tomcat post-build action

Remember: "Deploy to container" talks to Tomcat's manager-script role — that is why you created the deployer user in Step 3.

Tell Jenkins where its tools are

Under Manage Jenkins → Tools, register the JDK and Maven so jobs can resolve them by name.

JDK    name: corretto-21   JAVA_HOME: output of `echo $JAVA_HOME`
Maven  name: maven-3.9     MAVEN_HOME: /opt/maven
# or tick "Install automatically" for Maven

Tip: the names you choose here are what job configuration dropdowns show later — keep them descriptive.

Checkpoint: you can log in to Jenkins at http://<jenkins-ip>:8080, and both plugins appear under Installed plugins.

Security: the unlock secret lives at /var/lib/jenkins/secrets/initialAdminPassword and everything Jenkins knows lives under /var/lib/jenkins — treat that directory as the crown jewels.

🐳 Step 5 — Docker Engine

Install, enable, and join the docker group

On Amazon Linux, Docker installs straight from the default repos. Adding ec2-user to the docker group removes the need for sudo on every command.

sudo yum install -y docker
sudo systemctl enable --now docker
sudo usermod -aG docker ec2-user
exit   # group membership loads on next login — reconnect now

Security: docker-group membership is effectively root on that host (containers can mount /). Fine in a lab; a real decision in production.

Verify with hello-world

The canonical smoke test pulls a tiny image and runs it — proving the daemon, the registry connection, and your group membership in one go.

docker run hello-world
docker ps -a
docker images

Use when: "Hello from Docker!" prints without sudo, the engine is ready for the Week 6 Tomcat-image labs.

Checkpoint: docker run hello-world succeeds as ec2-user with no sudo.

🔁 Wire it together: one WAR through the pipeline

Generate and build a webapp with Maven

The Week 4 archetype gives you a minimal WAR project — build it once by hand so you know what Jenkins is about to automate, then push it to GitHub.

mvn archetype:generate -DgroupId=com.rmit.practice \
    -DartifactId=practice-webapp \
    -DarchetypeArtifactId=maven-archetype-webapp \
    -DinteractiveMode=false
cd practice-webapp
mvn clean package
ls target/*.war

Remember: clean deletes target/, package compiles and zips the WAR. The WAR is just a zip with a mandated layout.

Create the Jenkins job

This is the Week 5 flow end-to-end: source from Git, build with Maven, ship to Tomcat as a post-build action.

New Item → Maven project (or Freestyle)
  Source Code Management : Git → your repo URL
  Build                  : clean package
  Post-build             : Deploy war/ear to a container
    WAR/EAR files : **/target/*.war
    Context path  : /practice
    Container     : Tomcat 9.x
    Credentials   : deployer / <strong-password>
    Tomcat URL    : http://<tomcat-ip>:8080

Tip: use the Tomcat server's private IP if both instances share a VPC — traffic stays inside the network and survives public-IP changes on stop/start.

Checkpoint: Build Now goes green and http://<tomcat-ip>:8080/practice/ serves the archetype's "Hello World!" page. That is the entire delivery stack working.

Task: break it on purpose — stop Tomcat and rebuild, mistype the credentials, delete the WAR glob — and read each failure in the Jenkins console output. Diagnosing these is prime /grill-me material.

🧹 Reset to a clean slate

Undeploy, keep the stack

The lightest reset: remove your app but leave every tool installed, ready for the next practice deployment.

sudo rm -rf /opt/tomcat/webapps/practice*
rm -rf ~/.m2/repository       # force Maven to re-download everything
rm -rf ~/practice-webapp      # regenerate from the archetype next run

Use when: you want to re-drill the Maven → Jenkins → Tomcat flow without reinstalling the tools.

Factory-reset Jenkins

Jenkins keeps all state — jobs, plugins, credentials, users — in one directory. Deleting it returns you to the unlock screen.

sudo systemctl stop jenkins
sudo rm -rf /var/lib/jenkins
sudo systemctl start jenkins
sudo cat /var/lib/jenkins/secrets/initialAdminPassword

Remember: one directory, all state — this is also why backing up /var/lib/jenkins is backing up Jenkins.

Factory-reset Tomcat

Because Tomcat lives in one directory from a tarball, a reset is delete-and-re-extract.

sudo /opt/tomcat/bin/shutdown.sh
sudo rm -rf /opt/apache-tomcat-9.0.120 /opt/tomcat
sudo tar -xzf /tmp/apache-tomcat-9.0.120.tar.gz -C /opt
sudo ln -s /opt/apache-tomcat-9.0.120 /opt/tomcat

Tip: keep the downloaded tarballs in /tmp (or re-download) — re-extracting is faster than re-configuring.

Wipe Docker clean

One command removes every stopped container, unused image, network, and — with the flag — every volume.

docker system prune -a --volumes
docker ps -a      # empty
docker images     # empty

Warning: --volumes deletes data volumes too. In a practice lab that is the point; on a shared box it is a career moment.

Cost and cleanup: the true clean slate is terminating the EC2 instances in the AWS console — no instance, no bill. Rebuilding from this page afterwards is the practice.

Challenge: script the whole rebuild (Steps 1–4 on a fresh instance) in a single Bash file — that is Week 4's Challenge 6, and being able to explain each line is exactly what /grill-me will probe.

💻 Local fallback on macOS

Native tools via Homebrew

For quick Maven practice on your Mac, Homebrew covers the build side of the stack.

brew install openjdk@21 maven
brew install --cask docker    # Docker Desktop; launch it once
java -version && mvn -version && docker run hello-world

Remember: follow Homebrew's caveat about linking openjdk@21 into your PATH — brew info openjdk@21 reprints it.

Jenkins and Tomcat as containers

Containers give the cleanest reset story on a laptop: state lives in named volumes, and different host ports sidestep the 8080 clash.

docker run -d --name jenkins -p 8090:8080 \
    -v jenkins_home:/var/jenkins_home jenkins/jenkins:lts-jdk21
docker run -d --name tomcat -p 8081:8080 tomcat:9.0
# full reset:
docker rm -f jenkins tomcat && docker volume rm jenkins_home

Use when: Jenkins at localhost:8090, Tomcat at localhost:8081 — two 8080-native apps coexisting because port mapping decouples host from container.

Drill the exact lab commands for free

The labs use yum on Amazon Linux, not brew — so practise the real commands inside a throwaway Amazon Linux container.

docker run -it --rm amazonlinux:2023 bash
# now inside the container:
yum install -y java-21-amazon-corretto-devel wget tar gzip
# ...run Steps 1–3 exactly as written above, then `exit` — all gone

Tip: --rm deletes the container on exit — every run starts from a genuinely clean slate, which is ideal for repetition drills.

Important: systemctl does not run inside these containers and Homebrew paths differ from the labs — when /grill-me asks, answer with the Amazon Linux commands, not the macOS ones.
