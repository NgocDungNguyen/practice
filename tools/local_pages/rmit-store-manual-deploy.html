🛒 RMIT Store: Manual Deploy (A–E)

Do the Assignment 2 pipeline the right way — by hand first. This follows the repo README's own Plan A–E exactly, taking the Django + Vue store from your laptop to Docker Compose. It stops at Plan E: Plan F (Jenkins, Ansible, CloudFormation, Kubernetes) is the automation pipeline — a separate job for later.

🎯 What you are building, and the A–E map

The golden rule

The assignment says it plainly: do not automate a process you do not yet understand. Each step is something a pipeline will later do for you — you do it by hand once first, so you know what "good" looks like.

A  Run it locally             # on your laptop
B  Deploy to one EC2 by hand  # the whole app on one AWS box
C  Split across servers       # DB / API / frontend apart, + S3, + RDS
D  Containerise with Docker   # images; no Node in prod
E  Docker Compose             # one file describes all three tiers

Then stop. Plan F (Jenkins, Ansible, CloudFormation, Kubernetes, monitoring) is the automation pipeline — later.

The three tiers

Three things you can deploy independently. Remember the ports — each one becomes a security-group rule or a container port later.

Frontend  Vue 3 (Vite)   -> static files   (nginx, port 80)
Backend   Django + DRF   -> gunicorn        (port 8000)
Database  PostgreSQL     -> stateful        (port 5432)
Images    uploads        -> local disk / S3 (Step C)

Repo: github.com/TomHuynhSG/COSC2767-RMIT-Store-Django-Vue — read its README. This guide uses the same Plan A–E letters, so an instruction that says "Plan C" means the same thing here.

The two ideas that make the whole thing work. (1) The frontend reads its API URL from client/public/config.js at page load, not at build time — so one built artifact deploys everywhere, you just edit a text file. (2) python manage.py migrate is a deploy step — it must run, in order, before new code serves traffic. Keep both in mind from Step A; Steps C, D and E are mostly about honouring them across more machines.

Where the letters lead. A–B run the whole app on one box. C is the first time it lives on more than one machine — which is exactly when uploaded images break and you need S3. D and E are about packaging so that "more than one machine" stops being a manual chore. Plan F automates all of it.

🖥️ Step A — Run it locally (Plan A)

A0 · Install the runtimes

You need three things. Install them, then prove they are on your PATH.

# Python 3.11+, Node 20+, PostgreSQL 14+
# macOS Postgres: brew install postgresql@16 && brew services start postgresql@16
python3 --version
node --version
psql --version

Use when: a fresh machine. If any command errors, fix that before going on.

A1 · Get the code

Clone your team's fork of the repo and step into it.

git clone <your-repository-url>
cd COSC2767-RMIT-Store-Django-Vue

Use when: the very start. Use your team's fork — you need push access for the pipeline later.

A2 · Create the database

Make a role and a database for the app. macOS/Homebrew can run psql directly.

# macOS (Homebrew)
psql -d postgres -c "CREATE ROLE rmit LOGIN PASSWORD 'rmit' CREATEDB;"
psql -d postgres -c "CREATE DATABASE rmit_store OWNER rmit;"

# Linux: prefix both with  sudo -u postgres
psql -U rmit -d rmit_store -c "SELECT version();"

Use when: once per machine. If SELECT version() works, Django will connect.

A3 · Set up the API

A virtualenv keeps the Python packages isolated. Copy the example env file — the defaults are fine for local dev.

cd server
python3 -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env             # open it and read the comments

Remember: read server/.env. Each variable becomes a real deployment decision later.

A4 · Migrate and seed

migrate builds the tables; seed_demo fills them with a real catalogue and demo accounts. Seeding is idempotent.

python manage.py migrate

python manage.py seed_demo \
    --admin-email admin@rmit.edu.au \
    --admin-password 'RmitStore2767!' \
    --demo-users

Gives you: 47 products, an admin, a demo member, a demo seller. Add --no-images to finish in seconds while testing.

A5 · Run the API (terminal 1)

This command does not return — it holds the terminal open. Leave it running.

python manage.py runserver 0.0.0.0:8000

curl http://localhost:8000/healthz/   # {"status": "ok"}
curl http://localhost:8000/readyz/    # {"database": "ok", "storage": "ok"}

Explore: http://localhost:8000/api/docs/ drives the whole backend with no frontend running.

A6 · Run the frontend (terminal 2)

Leave the API running and open a second terminal. Vite serves the SPA and proxies /api to port 8000, so the browser sees one origin.

cd /path/to/COSC2767-RMIT-Store-Django-Vue/client
npm install
cp .env.example .env
npm run dev                      # open http://localhost:5173

Proof: product photos load. Grey placeholder boxes = SPA up but API not (check terminal 1).

A7 · Build the real artifact

npm run dev is not deployment. See what you actually ship: static files in dist/. There is no Node in production.

cd client
npm run build                    # produces client/dist/
npx vite preview --port 4173

# the trick — repoint the built artifact WITHOUT rebuilding:
nano dist/config.js              # set API_BASE_URL to http://localhost:8000/api

The whole lesson: hard-reload :4173 with the network tab open — requests move to the new API, and the hashed bundle filename is byte-for-byte unchanged. This is what Steps C–E lean on.

Done with A when: the store loads at localhost:5173 with real images, and curl /readyz/ returns both ok. Walk acceptance journeys A and B from the README so you know what a working deploy looks like.

☁️ Step B — Deploy to one EC2 by hand (Plan B)

Stay as ec2-user the whole way. Do not sudo su - or sudo -i. If you become root, the clone lands in /root/, nginx cannot traverse into it, and you get a 403 on every product image with nothing obviously wrong. Check with whoami (should print ec2-user). Use sudo only on the individual commands already written with it.

B1 · Launch the instance

Amazon Linux 2023. t3.small is comfortable; t3.micro works but the frontend build is memory-hungry.

# Security group inbound rules
22    My IP      # SSH
8000  Anywhere   # API (temporary)
5173  Anywhere   # dev server (temporary)
80    Anywhere   # nginx, from Step B9

Never open 5432 to the world. Scope it to My IP only if you need a GUI client.

B2 · Install the runtimes

SSH in, then install git, Python, Postgres and Node.

sudo dnf update -y
sudo dnf install -y git python3.11 python3.11-pip postgresql16 postgresql16-server

curl -fsSL https://rpm.nodesource.com/setup_22.x | sudo bash -
sudo dnf install -y nodejs

python3.11 --version && node --version

Use when: a fresh instance, right after first login.

B3 · Start PostgreSQL

Initialise the cluster, start it, and create the same role and database as local.

sudo postgresql-setup --initdb
sudo systemctl enable --now postgresql

sudo -u postgres psql -c "CREATE ROLE rmit LOGIN PASSWORD 'rmit' CREATEDB;"
sudo -u postgres psql -c "CREATE DATABASE rmit_store OWNER rmit;"

Use when: once per DB instance. One more fix follows — do not skip it.

B3b · Allow password logins (do not skip)

Amazon Linux's fresh initdb uses ident auth on 127.0.0.1, so Django is refused with "Ident authentication failed". Switch TCP lines to scram-sha-256.

sudo sed -i 's/^\(host.*\)ident$/\1scram-sha-256/' /var/lib/pgsql/data/pg_hba.conf
sudo systemctl reload postgresql

PGPASSWORD=rmit psql -h 127.0.0.1 -U rmit -d rmit_store -c "SELECT 1;"

Why: Django connects over TCP with a password. If SELECT 1 works, every later step can reach the DB.

B4 · Code and dependencies

Clone into ec2-user's home — later paths expect it there.

cd ~
git clone <your-repository-url>
cd COSC2767-RMIT-Store-Django-Vue/server
python3.11 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

Must be: /home/ec2-user/COSC2767-.... Not /root/.

B5 · Configure the API

Copy the env file and set the values that matter for a real host.

SECRET_KEY=<generate a real one>
ALLOWED_HOSTS=<your-ec2-public-ip>,localhost,127.0.0.1
CLIENT_URL=http://<your-ec2-public-ip>:5173
CORS_ALLOWED_ORIGINS=http://<your-ec2-public-ip>:5173
DATABASE_URL=postgres://rmit:rmit@localhost:5432/rmit_store

Use localhost in DATABASE_URL when the DB is on the same box — routing out to the public IP and back is slower and often blocked. (This changes in Step C.)

B6 · Migrate, seed, run (terminal 1)

Same two DB commands, then the dev server. It holds the terminal open — leave it.

python manage.py migrate
python manage.py seed_demo --admin-email admin@rmit.edu.au \
                           --admin-password 'RmitStore2767!' --demo-users

python manage.py runserver 0.0.0.0:8000
# check http://<your-ec2-public-ip>:8000/healthz/

Leave running. Open a second SSH terminal for the frontend.

B7 · Run the frontend (terminal 2)

Second SSH session. No virtualenv needed — the client is a Node project.

cd ~/COSC2767-RMIT-Store-Django-Vue/client
npm install
cp .env.example .env
npm run dev -- --host 0.0.0.0
# open http://<your-ec2-public-ip>:5173

Now: the app runs on AWS — but it is not a deployment yet (both processes die when SSH closes).

B9 · Serve it properly — nginx + gunicorn + systemd

Do it the real way: nginx owns port 80, serves the built SPA and images from disk, and reverse-proxies API traffic to gunicorn on 127.0.0.1:8000. One origin, so CORS never enters the picture (yet — Step C changes that).

B9.1 · Build the SPA, install nginx

cd ~/COSC2767-RMIT-Store-Django-Vue/client
npm run build

sudo dnf install -y nginx
sudo systemctl enable --now nginx
sudo cp -r dist/* /usr/share/nginx/html/

Expected: page loads, nothing works yet — nothing proxies /api/ until B9.4. Keep config.js at default API_BASE_URL: "/api".

B9.2 · Reconfigure the API for prod

Same file as B5 — reopen server/.env and change these lines now that you are going to production.

nano ~/COSC2767-RMIT-Store-Django-Vue/server/.env
DJANGO_SETTINGS_MODULE=config.settings.prod
ALLOWED_HOSTS=<your-ec2-public-ip>,127.0.0.1,localhost
CLIENT_URL=http://<your-ec2-public-ip>
CORS_ALLOWED_ORIGINS=http://<your-ec2-public-ip>
CSRF_TRUSTED_ORIGINS=http://<your-ec2-public-ip>
SESSION_COOKIE_SECURE=False
CSRF_COOKIE_SECURE=False

Gotcha: on plain HTTP, leaving the cookie flags True makes the admin accept your password then bounce you back to login. Turn them on the day you add TLS.

B9.3 · gunicorn under systemd

python manage.py collectstatic --noinput
sudo nano /etc/systemd/system/rmit-api.service
[Unit]
Description=RMIT Store API (gunicorn)
After=network.target postgresql.service

[Service]
User=ec2-user
WorkingDirectory=/home/ec2-user/COSC2767-RMIT-Store-Django-Vue/server
ExecStart=/home/ec2-user/COSC2767-RMIT-Store-Django-Vue/server/.venv/bin/gunicorn \
    config.wsgi:application --bind 127.0.0.1:8000 --workers 3 \
    --env DJANGO_SETTINGS_MODULE=config.settings.prod
Restart=always

[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload
sudo systemctl enable --now rmit-api

Bind 127.0.0.1 — once nginx is in front, gunicorn should not be reachable from outside. Logs: journalctl -u rmit-api -f.

B9.4 · Configure nginx

Create a new config file. Everything below goes inside one server { } block — the location lines are not valid on their own.

sudo nano /etc/nginx/conf.d/rmit-store.conf
server {
    listen       80 default_server;
    listen  [::]:80 default_server;
    server_name  _;

    root  /usr/share/nginx/html;   # the built SPA from B9.1
    index index.html;

    client_max_body_size 10M;      # product images are bigger than the 1M default

    # serve the SPA; unknown paths are Vue routes, so fall back to index.html
    location / { try_files $uri $uri/ /index.html; }
    location = /config.js { add_header Cache-Control "no-store"; }

    # forward API-shaped paths to gunicorn
    location ~ ^/(api|admin|healthz|readyz)(/|$) {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host              $host;     # load-bearing!
        proxy_set_header X-Forwarded-Host  $host;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # serve uploaded images and Django static files straight off disk
    location /media/  { alias /home/ec2-user/COSC2767-RMIT-Store-Django-Vue/server/media/; }
    location /static/ { alias /home/ec2-user/COSC2767-RMIT-Store-Django-Vue/server/staticfiles/; }
}

Save (Ctrl-O, Enter), exit (Ctrl-X), then let nginx reach /media/, test the config, and reload:

chmod o+x /home/ec2-user      # let nginx traverse to /media/
sudo nginx -t && sudo systemctl reload nginx

Why Host $host matters: without it Django builds every image_url as http://127.0.0.1:8000/..., which resolves to the browser's machine, and every image breaks with a fake "CORS" error.

B9.5 · Verify

IP=<your-ec2-public-ip>
curl -I  http://$IP/                 # 200, text/html
curl -s  http://$IP/readyz/          # {"database": "ok", "storage": "ok"}
curl -sI http://$IP/shop             # 200 — SPA fallback works
curl -s  http://$IP/api/products/ | grep -o '"image_url":"[^"]*"' | head -1

Read the last line: the image URL must be on your public IP with no port. 502 = gunicorn down. 400 = IP missing from ALLOWED_HOSTS. 403 on /media/ = the chmod o+x did not happen.

B9.6 · Close the extra ports

# in the security group, DELETE inbound 8000 and 5173
# keep 22 (SSH) and 80 (nginx)

Re-run B9.5 after. If a check only passed because you were quietly hitting port 8000, this is where you catch it.

Done with B when: the store works entirely through port 80, images load, and only ports 22 and 80 are open. You have deployed the whole app by hand on one box.

🌐 Step C — Split across servers (Plan C)

What changes and why. In Plan B everything shared one box and one origin. Plan C pulls the tiers apart: the database onto managed AWS RDS, the API on one instance, the frontend on another. Two things bite the moment you do — CORS (the browser now talks to two origins) and uploaded images (they live on one API box, so a second one 404s them). Solving both is the point of this step, and doing it by hand now makes the CloudFormation template in Plan F far easier.

C1 · Plan the topology

Three roles. The database is AWS RDS (managed, no box to run), the other two are EC2. Decide names and private/public reach before launching.

RDS (PostgreSQL)  # managed database — private, no public access
api-server        # Django + gunicorn (repeat B2–B9.3 here, minus nginx SPA)
frontend-server   # nginx serving the built SPA + proxying /api to api-server

Security group per box

Create three security groups: rds-sg, api-server-sg, frontend-server-sg. All rules below are Inbound rules — inbound means "who is allowed to connect TO this box." Leave Outbound at its default (All traffic → 0.0.0.0/0) on all three, or the boxes can't reach GitHub, dnf, or S3.

The trick for internal traffic: set the source to another security group, not an IP — then it keeps working even when private IPs change. (You can only point at an SG that already exists, so make all three empty first, then add rules.)

# rds-sg — INBOUND        TYPE         PORT   SOURCE               WHY
  rule 1                  PostgreSQL   5432   api-server-sg        only the API may query the DB
# Public access on the RDS instance = No. No other inbound rule.
# api-server-sg — INBOUND TYPE         PORT   SOURCE               WHY
  rule 1                  SSH          22     My IP                admin only
  rule 2                  Custom TCP   8000   frontend-server-sg   only the frontend reaches the API
# nothing else open to the internet
# frontend-server-sg — INBOUND  TYPE   PORT   SOURCE               WHY
  rule 1                  SSH          22     My IP                admin only
  rule 2                  HTTP         80     Anywhere 0.0.0.0/0   public storefront — NOT your IP
# this is the ONLY box the public can reach

Common mistake: adding these under the Outbound tab. They go in Inbound rules → Edit inbound rules. Port 80 must be Anywhere, not your IP, or no one else can load the store.

Traffic only flows one way: public → frontend (80) → api (8000) → db (5432). Each box opens its port only to the box in front of it. That is the whole security model.

Use when: you are ready to scale or separate concerns. Each box is a smaller blast radius and can be sized independently.

C1b · One SSH key for cloning on every box

Your repo is private, so every instance needs an SSH key to git clone it. Don't make three keys and register three times — make one key, add it to GitHub once, then copy it to the other boxes.

1. Make the key on the first box (api-server)

# -N ''  = no passphrase, so servers can clone unattended
ssh-keygen -t ed25519 -C "rmit-store-deploy" -f ~/.ssh/id_ed25519 -N ''
cat ~/.ssh/id_ed25519.pub          # copy this whole line

2. Register the PUBLIC half on GitHub — once

Pick one:

  • Deploy key (recommended, safest): your repo → Settings → Deploy keys → Add deploy key → paste the .pub line. Leave "Allow write access" unchecked — clone-only, and it's scoped to this one repo.
  • Account SSH key: github.com → Settings → SSH and GPG keys — works too, but grants access to all your repos, so it's broader than you need.

3. Copy the same key onto the other boxes (copy-paste)

The key already lives on the api-server (you made it in step 1). You're SSH'd into both boxes from your laptop, so just copy the key text across — no .pem juggling needed.

# --- on the API-SERVER: print both halves, copy each block ---
cat ~/.ssh/id_ed25519        # the PRIVATE key (starts -----BEGIN ...)
cat ~/.ssh/id_ed25519.pub    # the PUBLIC key  (one line, ssh-ed25519 ...)
# --- on the FRONTEND-SERVER: paste each block into a file ---
mkdir -p ~/.ssh && chmod 700 ~/.ssh

nano ~/.ssh/id_ed25519       # paste the PRIVATE block, save
nano ~/.ssh/id_ed25519.pub   # paste the PUBLIC block, save

# lock the private key down (git/ssh refuses loose perms)
chmod 600 ~/.ssh/id_ed25519

Careful: ~/.ssh/id_ed25519 is the private key — the secret. Only paste it onto your own instances, never into GitHub, chat, or the report.

4. Clone with the SSH URL on each box

ssh -T git@github.com     # first time: type "yes"; expect "Hi ...! You've successfully authenticated"
git clone git@github.com:<your-team>/COSC2767-RMIT-Store-Django-Vue.git

Note the URL form: use git@github.com:... (SSH), not https://... — only the SSH URL uses the key. Safer alternative: skip copying the private key entirely and use agent forwarding — ssh -A — so the key never lands on any server. Mention whichever you chose in the report.

C2 · Database on AWS RDS

Move Postgres off the API box and onto managed AWS RDS — you get automated backups and a stable endpoint, and there is no database server to patch. State and justify this choice in the report.

Create the RDS instance (AWS console, no SSH)

  1. RDS → Create database → Standard create → engine PostgreSQL.
  2. Template Free tier (or Dev/Test). Instance class db.t3.micro is fine.
  3. DB instance identifier rmit-store — this is just AWS's name for the box. Use a hyphen, not an underscore (underscores are rejected here).
  4. Master username rmit, set a master password (write it down — you need it in C3).
  5. Under Additional configuration, Initial database name rmit_store — this is the actual Postgres database, and here an underscore is fine. (Skip this and no database is created — Django will fail to connect.)
  6. Connectivity → Public access: No. Put it in the same VPC as the api-server.
  7. VPC security group → create new, or attach rds-sg: inbound 5432, source = the api-server's security group (not an IP).
  8. Create it. When status is Available, open the instance and copy the Endpoint — e.g. rmit-store.abc123.ap-southeast-2.rds.amazonaws.com. That is your DB host for C3.

Rule: the database is never reachable from the internet. Leave Public access = No. Only the api-server's security group may reach port 5432.

C2b · Launch & provision the api-server

The box that runs Django. It's Plan B's API half — but with no Postgres server (that's RDS now) and no SPA/nginx (that's the frontend box).

# 1. Launch EC2 → Amazon Linux 2023, t3.small, security group = api-server-sg, your key pair
# 2. SSH in. Install runtimes. postgresql16 here is the psql CLIENT only (to test RDS) — no server.
sudo dnf update -y
sudo dnf install -y git python3.11 python3.11-pip postgresql16
# 3. This is the box you MAKE the deploy key on (C1b steps 1–2), then clone over SSH
cd ~
git clone git@github.com:<your-team>/COSC2767-RMIT-Store-Django-Vue.git
cd COSC2767-RMIT-Store-Django-Vue/server
python3.11 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env

Now edit server/.env: point DATABASE_URL at RDS (C3), turn on S3 (C6), and allow the frontend origin (C5). Then migrate, seed, collect static, and start gunicorn:

python manage.py migrate
python manage.py seed_demo --admin-email admin@rmit.edu.au \
                           --admin-password 'RmitStore2767!' --demo-users
python manage.py collectstatic --noinput
sudo nano /etc/systemd/system/rmit-api.service   # same unit as B9.3, ONE change

Paste the whole file — all four sections. The only change from B9.3 is --bind 0.0.0.0:8000 (so the browser reaches gunicorn directly, since there's no nginx on this box).

[Unit]

After=network.target

[Service]
User=ec2-user
WorkingDirectory=/home/ec2-user/COSC2767-RMIT-Store-Django-Vue/server

Cloned into a different folder? If your git clone made a folder that isn't COSC2767-RMIT-Store-Django-Vue (check with pwd), fix both WorkingDirectory and the ExecStart path to match — e.g. /home/ec2-user/a2/server. Missing the [Install] section is what causes "unit files have no installation config".

sudo systemctl daemon-reload
sudo systemctl enable --now rmit-api
curl -s http://<api-server-public-dns>:8000/healthz/    # {"status": "ok"}

Difference from Plan B: gunicorn binds 0.0.0.0:8000, not 127.0.0.1 — there's no nginx in front on this box, the browser talks to it directly. That's why api-server-sg opens 8000 to Anywhere.

C3 · Configure the api-server .env (for RDS)

On the api-server, edit server/.env. These are the only lines you change from the shipped example — everything else (email, JWT, tax, throttles) keeps its default.

# api-server  server/.env  — fill the <...> from your own AWS console
DJANGO_SETTINGS_MODULE=config.settings.prod
SECRET_KEY=<generate a real one — see below>
DEBUG=False
ALLOWED_HOSTS=<api-public-ip>,<api-private-ip>,127.0.0.1
CLIENT_URL=http://<frontend-public-ip>

# RDS endpoint + master password from C2:
DATABASE_URL=postgres://rmit:<master-pw>@<rds-endpoint>:5432/rmit_store

# the FRONTEND's origin (where the browser loads the page), NOT the API's:
CORS_ALLOWED_ORIGINS=http://<frontend-public-ip>
CSRF_TRUSTED_ORIGINS=http://<frontend-public-ip>

# shared images — flip on in C6. Region must match YOUR region (e.g. us-east-1):
USE_S3=False
AWS_S3_REGION_NAME=<your-region>

Generate a real SECRET_KEY (never reuse one you've shared):

python3 -c 'from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())'

No frontend box yet? You can still bring the API up. Put the api-server's own address in CLIENT_URL/CORS_ALLOWED_ORIGINS/CSRF_TRUSTED_ORIGINS as a placeholder and test with curl — CORS only matters once a browser loads the SPA from the frontend box. Come back and set the real frontend address in C5.

# prove the API box can reach RDS before migrating:
PGPASSWORD=<master-pw> psql -h <rds-endpoint> -U rmit -d rmit_store -c "SELECT 1;"
python manage.py migrate      # run migrations from the api-server

Verify the API is really up (and talking to RDS)

Restart the service so it picks up the new .env, then hit the health endpoints. Run these from the api-server first (localhost), then from your laptop against the public IP.

sudo systemctl restart rmit-api
sudo systemctl status rmit-api --no-pager      # should say: active (running)

# 1. liveness — the process is alive (touches nothing)
curl -s http://127.0.0.1:8000/healthz/         # {"status": "ok"}

# 2. readiness — THIS proves the RDS + storage connection
curl -s http://127.0.0.1:8000/readyz/          # {"database": "ok", "storage": "ok"}

# 3. the API actually returns data from the DB you just migrated + seeded
curl -s http://127.0.0.1:8000/api/products/ | head -c 200

# 4. from your LAPTOP — proves the security group + 0.0.0.0 bind are right
curl -s http://<api-public-ip>:8000/readyz/

Read the result:

  • readyz returns database: ok → green light, the api-server reached RDS.
  • database: error or a 503 → wrong DATABASE_URL, or the rds-sg blocks 5432.
  • Works on localhost but hangs from your laptop → the api-server-sg isn't opening 8000.
  • psql itself hangs → the rds-sg isn't allowing the api-server-sg on 5432. Fix the security group, not the password.

Leave AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY unset — the IAM role in C7 handles S3 credentials.

C3b · Launch & provision the frontend-server

This box only serves static files. No Python, no database — just Node (to build the SPA) and nginx (to serve it).

# 1. Launch EC2 → Amazon Linux 2023, t3.small (the build is memory-hungry),
#    security group = frontend-server-sg, your key pair
# 2. SSH in. Install nginx + Node + git.
sudo dnf update -y
sudo dnf install -y git nginx
curl -fsSL https://rpm.nodesource.com/setup_22.x | sudo bash -
sudo dnf install -y nodejs
sudo systemctl enable --now nginx
# 3. Copy the SAME deploy key here (C1b step 3), then clone + build the SPA
cd ~
git clone git@github.com:<your-team>/COSC2767-RMIT-Store-Django-Vue.git
cd COSC2767-RMIT-Store-Django-Vue/client
npm install
cp .env.example .env
npm run build                        # produces dist/
sudo cp -r dist/* /usr/share/nginx/html/

Now: the SPA loads on port 80 but points nowhere yet — C4 aims it at the api-server. If deep links like /shop 404, add the SPA fallback: put location / { try_files $uri $uri/ /index.html; } in /etc/nginx/conf.d/rmit-store.conf (the location / line from B9.4) and sudo systemctl reload nginx.

C4 · Point the frontend at the API — no rebuild

This is the A7 trick in production. On the frontend-server, edit the deployed config.js to name the API's address. You do not rebuild the bundle.

# frontend-server: /usr/share/nginx/html/config.js
#   API_BASE_URL: "http://<api-server-public-dns>:8000/api"
sudo nano /usr/share/nginx/html/config.js

To change the API endpoint, this is the ONLY file you touch — no npm run build, no copy. config.js is read at page load, so editing the deployed file is enough. After saving, hard refresh the browser (Cmd/Ctrl+Shift+R) — nginx serves config.js with no-store, but the browser may still cache it. If you did rebuild (because you changed app code), also redeploy the bundle: sudo cp -r dist/* /usr/share/nginx/html/.

The payoff: the same dist/ you built once now points at any API by editing one text file. Remember it — Plan F promotes builds this way.

C5 · Fix CORS (the thing that "suddenly" breaks)

The browser now loads the SPA from one origin and calls the API on another — a cross-origin request. The browser blocks it unless the API says the frontend's origin is allowed. Add it on the api-server.

# api-server  server/.env  — use the FRONTEND's public origin
CORS_ALLOWED_ORIGINS=http://<frontend-server-public-dns>
CSRF_TRUSTED_ORIGINS=http://<frontend-server-public-dns>
ALLOWED_HOSTS=<api-server-public-dns>,<api-private-ip>,127.0.0.1
sudo systemctl restart rmit-api

Why it appears now and not in B: Plan B put both tiers behind one nginx, so there was only one origin and CORS never applied. Split them and it does. (You can also keep the frontend nginx proxying /api to the api-server to stay single-origin — a valid design; note which you chose in the report.)

C6 · Shared media with S3 (images stop breaking)

Uploads land on one API box's server/media/. Add a second API box and half the images 404, intermittently. S3 gives every box one shared store — no code change, the backend is chosen by config.

Run this on the api-server (it has the AWS CLI and, after C7, an IAM role that's allowed to make buckets). Or run it from your laptop if you have aws configure set up. Either way it only needs to be run once — a bucket is global, not per-box.

Bucket names are global and unique — swap <yourteam> for something like group7. If you get BucketAlreadyExists, pick a different suffix.

If you're in us-east-1 (the common case)

us-east-1 does not take a LocationConstraint — it's the one-line form:

aws s3api create-bucket --bucket rmit-store-media-<yourteam> --region us-east-1

Any other region

Every other region needs the LocationConstraint flag. Put your region (check the top-right of the console) in both spots:

aws s3api create-bucket \
  --bucket rmit-store-media-<yourteam> \
  --region <your-region> \
  --create-bucket-configuration LocationConstraint=<your-region>
# api-server  server/.env   (us-east-1 shown)
USE_S3=True
AWS_STORAGE_BUCKET_NAME=rmit-store-media-<yourteam>
AWS_S3_REGION_NAME=us-east-1

Restart the API so it picks up the new config, then re-seed so the demo images upload to S3:

sudo systemctl restart rmit-api
cd ~/a2/server && source .venv/bin/activate && python3 manage.py seed_demo

Let the browser read the images (public read)

Product image URLs point straight at the bucket (https://rmit-store-media-<yourteam>.s3.amazonaws.com/...). New buckets block public access, so the browser gets 403 and images look broken. Open the bucket in the S3 console and do both:

1. Turn off "Block all public access" — bucket → Permissions tab → Block public access → Edit → untick Block all public access → Save → type confirm.

2. Add a read-only bucket policy — same Permissions tab → Bucket policy → Edit → paste (swap in your bucket name):

{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "PublicReadMedia",
    "Effect": "Allow",
    "Principal": "*",
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::rmit-store-media-<yourteam>/*"
  }]
}

This grants read-only. s3:GetObject only lets the public view images — nobody can upload or delete. Writes still go through the api-server's IAM role (C7).

Test: upload a product image in /admin/ (or open a seeded product), confirm the object is under media/products/ in the bucket and the image renders in the browser — then it survives an instance being replaced.

C7 · IAM role, not access keys

boto3 uses the default credential chain, so give the api-server an instance role that can write to the bucket — no long-lived keys in any .env.

# attach an instance profile to the api-server whose policy allows,
# scoped to arn:aws:s3:::rmit-store-media-<yourteam>/* :
#   s3:GetObject, s3:PutObject, s3:DeleteObject
# note: NO AWS_ACCESS_KEY_ID / SECRET in .env — the role provides them

Why: a leaked key in a repo is classic marker-bait. An instance role rotates automatically and never sits in a file.

C8 · Security groups, tightly

Every port is a deliberate rule. This is the layout Plan F's load balancer will sit on top of.

frontend-sg:  80   from anywhere        22 from My IP
api-sg:       80   from frontend-sg     22 from My IP   # or 8000 if not fronted
db-sg:        5432 from api-sg ONLY
# nothing open to 0.0.0.0/0 that does not have to be

Reference by security group, not IP where you can — it keeps working when instances are replaced.

Done with C when: the DB is on its own instance/RDS and private, the API and frontend are on separate boxes talking cross-origin without CORS errors, images upload to S3 and survive an instance swap, and no AWS keys sit in any file. You have now proven the app runs split — the shape every later step packages.

📌 Elastic IP — survive Learner Lab restarts

The annoyance. Every time you stop and restart the Learner Lab, your EC2 public DNS/IP changes. That breaks the frontend's config.js and the api-server's .env, so the store stops working until you hunt down and edit every hardcoded address. An Elastic IP is a fixed public IP you pin to an instance once — it stays put across restarts, so you set the address once and never touch it again.

What changes on restart, what doesn't

EC2 public DNS / IP   -> CHANGES every restart   (the pain)
RDS endpoint          -> stays the same          (DATABASE_URL is safe)
Elastic IP (once set) -> stays the same          (the fix)

Only the two EC2 boxes need pinning. RDS already has a stable endpoint, so DATABASE_URL never changes.

Pin a fixed IP to each box

Do this for both the api-server and the frontend-server.

  1. EC2 console → Elastic IPs (left menu, under Network & Security) → Allocate Elastic IP address → Allocate.
  2. Select the new IP → Actions → Associate Elastic IP address.
  3. Resource type Instance → pick the instance → Associate.
  4. Repeat for the second instance (allocate a second Elastic IP).

Learner Lab tip: keep the Elastic IP associated with a running instance. AWS charges for an Elastic IP that is allocated but attached to nothing — associated-and-running is free.

Use the fixed IPs (set once)

Now put the Elastic IPs where the old changing DNS used to be:

# frontend-server: edit the DEPLOYED config.js (no rebuild — see C4), then hard-refresh
#   /usr/share/nginx/html/config.js
API_BASE_URL: "http://<api-elastic-ip>:8000/api"
# api-server  server/.env
ALLOWED_HOSTS=<api-elastic-ip>
CLIENT_URL=http://<frontend-elastic-ip>
CORS_ALLOWED_ORIGINS=http://<frontend-elastic-ip>
CSRF_TRUSTED_ORIGINS=http://<frontend-elastic-ip>
# api-server: reload the new .env
sudo systemctl restart rmit-api

Payoff: restart the lab as many times as you like — the addresses hold, the store keeps working, no re-editing. This is also exactly what the CloudFormation/Ansible work in Plan F automates.

🐳 Step D — Containerise with Docker (Plan D)

Why now. Plan C worked but every box was set up by hand. A container captures that setup as a file, so the next box is docker run instead of an afternoon. The repo ships no Dockerfiles — writing them is the assignment. Below is a correct starting shape based on the README's rules.

Read the order first. Cards D1–D5 just write files (the recipes). Writing a Dockerfile does not build anything. The actual docker build and docker run happen in D6. So: write the files, then build & run in D6.

D1 · Dockerfile for the API

Where: on the api-server box, make a new file Dockerfile.api at the repo root (the folder holding server/).

Package Django + gunicorn. The key decision: migrate touches the database, so it belongs at run time (entrypoint), not in the image build. collectstatic needs no DB, so it can run at build.

FROM python:3.12-slim
WORKDIR /app
COPY server/requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY server/ .
RUN python manage.py collectstatic --noinput
EXPOSE 8000
COPY entrypoint.sh /entrypoint.sh
RUN chmod +x /entrypoint.sh
ENTRYPOINT ["/entrypoint.sh"]

The RUN chmod +x line is not optional: git usually drops the executable bit, so without it the container dies with "/entrypoint.sh": permission denied. Baking the chmod into the image fixes it for every clone.

This card only writes the recipe file. You build it into the rmit-api image in D6.

Pin the image (python:3.12-slim, not latest) so a rebuild next week is the same build this week.

D2 · The API entrypoint

Where: on the api-server box, make a new file entrypoint.sh at the repo root, then run chmod +x entrypoint.sh.

Run migrations, then hand off to gunicorn as PID 1 with exec.

#!/bin/sh
set -e
python manage.py migrate --noinput
exec gunicorn config.wsgi:application \
    --bind 0.0.0.0:8000 --workers 3 \
    --env DJANGO_SETTINGS_MODULE=config.settings.prod

Why exec: gunicorn becomes PID 1 and receives Docker's stop signals, so the container shuts down cleanly instead of being killed.

D3 · Dockerfile for the frontend

Where: on the frontend-server box, make a new file Dockerfile.frontend at the repo root (the folder holding client/). You also need an nginx.conf next to it.

Multi-stage: Node builds the bundle, then the result is copied into an nginx image. The final image must not contain Node.

# build stage
FROM node:22-slim AS build
WORKDIR /app
COPY client/package*.json ./
RUN npm ci
COPY client/ .
RUN npm run build

# runtime stage — nginx only, no Node
FROM nginx:alpine
COPY --from=build /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf

That last line needs a second file — make nginx.conf at the repo root too (next to Dockerfile.frontend). Without it the build fails with "/nginx.conf": not found:

server {
    listen 80;
    server_name _;
    root /usr/share/nginx/html;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }
}

The try_files ... /index.html line matters: the store is a Vue single-page app, so refreshing a deep link like /products must still serve index.html and let Vue route it. Without it, any refresh off the home page 404s.

This card only writes the two recipe files (Dockerfile.frontend + nginx.conf). You turn them into the rmit-frontend image in D6 with docker build — don't run anything yet.

Prove it (after D6): docker run --rm rmit-frontend which node finds nothing. That is the point of the multi-stage build.

D4 · Keep config.js a runtime thing

Where: on the frontend-server box, edit /opt/rmit/config.js so API_BASE_URL points at the API Elastic IP, then mount it into the container as shown.

Remember A7/C4: the API URL is read at page load. Do not bake it into the image — inject it when the container starts, so one image works in every environment.

# this is the D6 run command — only works AFTER you build the image.
# mount an environment-specific config.js over the baked-in one:
docker run -d -p 80:80 \
  -v /opt/rmit/config.js:/usr/share/nginx/html/config.js:ro \
  rmit-frontend

Shown here to explain the mount. The /opt/rmit/config.js file must exist first, and you run this in D6 after docker build.

Trap — create the file BEFORE the first run. If /opt/rmit/config.js does not exist when you docker run, Docker silently creates it as an empty directory, and the next run fails with not a directory: Are you trying to mount a directory onto a file? A -v mount must match types — file onto file. Fix it once:

# if the run made a folder by mistake, delete it and make a real file:
sudo docker rm web
sudo rm -rf /opt/rmit/config.js
sudo mkdir -p /opt/rmit
# seed it from the image's baked-in config, then set the API IP:
sudo docker run --rm rmit-frontend cat /usr/share/nginx/html/config.js \
  | sudo tee /opt/rmit/config.js
sudo nano /opt/rmit/config.js          # set API_BASE_URL to the API Elastic IP
ls -l /opt/rmit/config.js              # must be a FILE, not a directory

This is a one-time fix. Once it is a real file it stays a file — rebuilds, restarts and IP edits never bring the error back.

Why: build the image once, promote the same artifact — the idea Plan F's pipeline depends on.

D5 · A .dockerignore

Where: make a new file .dockerignore at the repo root on each box (api-server and frontend-server) — wherever you run docker build.

Keep build context small and secrets out of the image.

# .dockerignore
**/.venv
**/node_modules
**/.env
**/__pycache__
server/media
server/staticfiles
.git

Never copy .env into an image — pass config at run time with --env-file or an orchestrator secret.

D6 · Build, run, verify

Where: run the API lines on the api-server box, and the frontend lines on the frontend-server box — each from the repo root.

Free the ports first. Step C left the rmit-api systemd service on :8000 and nginx on :80. The containers want those same ports, so a run fails with bind: address already in use. Stop the old services before running the containers:

# api-server: stop the Step C service that holds :8000
sudo systemctl stop rmit-api
# frontend-server: stop the Step C nginx that holds :80
sudo systemctl stop nginx
# on the api-server box:
docker build -t rmit-api -f Dockerfile.api .
docker run -d --name api -p 8000:8000 --env-file server/.env rmit-api
curl http://localhost:8000/healthz/    # {"status": "ok"}

# on the frontend-server box:
docker build -t rmit-frontend -f Dockerfile.frontend .
docker run -d --name web -p 80:80 \
  -v /opt/rmit/config.js:/usr/share/nginx/html/config.js:ro \
  rmit-frontend

A failed run still leaves a container with that name, so a retry hits name already in use. Clear it before re-running: sudo docker rm api (or web).

Use when: proving the containers work before Compose. The DB can stay as RDS from Step C, or become a container in Step E.

D7 · Survive a lab restart

By default a Learner Lab reboot leaves Docker off and your containers down. Three one-time commands per box make everything come back on its own.

# on the api-server box:
sudo systemctl enable docker                       # Docker starts at boot
sudo systemctl disable --now rmit-api              # kill the Step C service that steals :8000
sudo docker update --restart unless-stopped api    # container auto-starts on boot

# on the frontend-server box:
sudo systemctl enable docker
sudo systemctl disable --now nginx                 # kill the Step C nginx that steals :80
sudo docker update --restart unless-stopped web

disable --now stops the old Step C service and stops it auto-starting, so it never fights the container for the port. unless-stopped means the container comes back on boot unless you stopped it on purpose.

After a restart, nothing to re-run — just verify: curl http://localhost:8000/healthz/ on the api box, and open the FE Elastic IP in a browser. The Elastic IPs hold, so config.js and server/.env stay correct.

Catch: docker update --restart only affects a container that already exists. If you docker rm and recreate one, add --restart unless-stopped to that docker run so the policy sticks.

Done with D when: both images build, the API image runs migrations on startup and stops cleanly, the frontend image has no Node in it, config.js is injected at run time, and the store works from containers. Next: one file to run all of them together.

🧱 Step E — Docker Compose (Plan E)

What Compose adds. Step D ran containers one docker run at a time. Compose describes the database, the API and the frontend in one file and starts them together, on one network, with the startup order handled for you. It is the last manual step — real multi-host orchestration (Swarm/Kubernetes) is Plan F.

Which box. Unlike Step D (split across two boxes), Step E runs the whole stack on ONE box — db, api and web together. Do it all on the api-server box. Compose brings its own db container, so you don't use the Step C RDS here. Every command and file below lives at the repo root on that one box.

Install two plugins first. Amazon Linux 2023's docker comes from Amazon's repo, not Docker's — so sudo dnf install docker-compose-plugin just says No match for argument. You must drop the plugin binaries in by hand. Compose also builds with buildx, so install both, or you'll hit unknown shorthand flag: 'd' (no Compose) then compose build requires buildx 0.17.0 or later (no buildx).

# make the plugin folder once:
sudo mkdir -p /usr/local/lib/docker/cli-plugins

# 1) Compose:
sudo curl -SL https://github.com/docker/compose/releases/latest/download/docker-compose-linux-x86_64 \
  -o /usr/local/lib/docker/cli-plugins/docker-compose
sudo chmod +x /usr/local/lib/docker/cli-plugins/docker-compose

# 2) buildx (pin a current version — buildx has no 'latest' file):
sudo curl -SL https://github.com/docker/buildx/releases/download/v0.36.1/buildx-v0.36.1.linux-amd64 \
  -o /usr/local/lib/docker/cli-plugins/docker-buildx
sudo chmod +x /usr/local/lib/docker/cli-plugins/docker-buildx

# verify both:
sudo docker compose version      # Docker Compose version v2.x+
sudo docker buildx version       # github.com/docker/buildx v0.36.1

Check the newest buildx tag at github.com/docker/buildx/releases and swap the version if v0.36.1 is stale. Docker's official plugin docs: docs.docker.com/compose/install/linux.

E1 · The compose file

File: make a new file docker-compose.yml at the repo root on the api-server box.

Three services on one network. The API and frontend build from the Dockerfiles you wrote in Step D.

services:
  db:
    image: postgres:16
    environment:
      POSTGRES_USER: rmit
      POSTGRES_PASSWORD: rmit
      POSTGRES_DB: rmit_store
    volumes: [ "pgdata:/var/lib/postgresql/data" ]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U rmit"]
      interval: 5s
      retries: 10

  api:
    build: { context: ., dockerfile: Dockerfile.api }
    env_file: server/.env
    ports: [ "8000:8000" ]     # browser hits the API directly (Step C design)
    depends_on:
      db: { condition: service_healthy }

  web:
    build: { context: ., dockerfile: Dockerfile.frontend }
    ports: [ "80:80" ]
    depends_on: [ api ]

volumes: { pgdata: {} }

Publish :8000 or the store can't talk to the API. nginx (web) only serves the built Vue files on :80 — it does not proxy /api. The browser calls the API straight at <api-ip>:8000 (the same design as Step C), so config.js API_BASE_URL must be http://<api-ip>:8000/api. Skip the api ports and the page loads but every product/login call fails.

Note the volume: pgdata keeps the database on disk, so docker compose down does not wipe your catalogue.

E2 · Wait for the database, don't crash-loop

File: keep editing the same docker-compose.yml — add the api.healthcheck block below into the api service.

The db healthcheck plus depends_on: condition: service_healthy makes the API wait until Postgres actually answers — not just until its container exists.

# already in E1:
#   db.healthcheck  -> pg_isready
#   api.depends_on.db.condition: service_healthy
# add a readiness check on the API too, so web waits for a working API:
  api:
    healthcheck:
      test: ["CMD-SHELL", "curl -f http://localhost:8000/readyz/ || exit 1"]
      interval: 10s
      retries: 5

Why: without it the API starts before the DB is ready, fails to connect, and restarts in a loop that looks like a bug. /readyz/ is exactly the probe for this.

E3 · Where do migrations run?

File: same docker-compose.yml. Pick Option A (nothing to add) or Option B (paste the migrate service and the api.depends_on below).

Three containers start at once — you must decide who runs migrate, exactly once, before the API serves traffic. Two clean options.

# Option A (simplest): the API entrypoint from D2 runs migrate on start.
#   Fine for one API replica. With several, they race — usually harmless
#   (migrations are transactional) but noisy.

# Option B (cleaner): a one-shot migrate service that runs and exits,
#   and the API waits for it to finish successfully.
  migrate:
    build: { context: ., dockerfile: Dockerfile.api }
    env_file: server/.env
    entrypoint: []                       # MUST clear the entrypoint, see below
    command: python manage.py migrate --noinput
    depends_on:
      db: { condition: service_healthy }
  api:
    depends_on:
      migrate: { condition: service_completed_successfully }

The gotcha that makes Option B hang. Dockerfile.api ends in ENTRYPOINT ["/entrypoint.sh"], and that script always finishes with exec gunicorn. So a bare command: is ignored — the migrate container runs gunicorn and never exits, and api waits on it forever (docker compose ps shows migrate stuck Up, not Exited (0)). Adding entrypoint: [] clears that, so command runs directly and the container exits when migrate finishes.

For the report: naming where migrations run and what happens if they fail is exactly the operational decision the assignment is probing.

E4 · Run it and verify

Where: run these on the api-server box, from the repo root (where docker-compose.yml is).

Free the ports first. If the one-off api/web containers from D6 (or the Step C services) are still holding :80 and :8000, Compose can't bind and you'll hit address already in use. Clear them — the || true means "don't error if they aren't there":

sudo docker rm -f api web 2>/dev/null || true   # remove D6 containers IF they exist
sudo systemctl stop rmit-api nginx 2>/dev/null || true   # stop Step C services IF running

No such container: api here is fine — it just means you never made the D6 containers, so there is nothing to clean up. Move on.

One command brings the whole stack up. Seed once the DB is healthy.

docker compose up -d --build
docker compose ps            # all healthy?

# seed the catalogue (once):
docker compose exec api python manage.py seed_demo \
    --admin-email admin@rmit.edu.au --admin-password 'RmitStore2767!' --demo-users

# API lives on :8000 (NOT behind nginx on :80):
curl -s http://localhost:8000/readyz/       # {"database": "ok", "storage": "ok"}
curl -s http://localhost:8000/api/version/  # the build you just ran

# the store page is nginx on :80 — this returns HTML, which is correct:
curl -s http://localhost/                   # <!doctype html> ... RMIT Store

Don't be fooled: curl localhost/readyz/ (port 80) returns the store's HTML, not JSON — because nginx sends every unknown path to index.html. That is not a bug. The API check must use :8000.

Logs: docker compose logs -f api. Tear down: docker compose down (add -v to also drop the DB volume).

E5 · Know the ceiling

Compose runs on one host. It is perfect for local dev and a single demo box, but it does not spread containers across machines or scale a tier to many replicas.

# the moment you scale the API to 2+ replicas across hosts, uploaded
# images on local disk break again — which is why Step C added S3.
# multi-host scaling itself is Plan F: Docker Swarm or Kubernetes.

This is the handoff line to the automation pipeline. Stop here.

Done with E when: docker compose up -d --build brings the whole store up with the API waiting for a healthy database, migrations run exactly once, and /readyz/ is green. You can now start, stop and rebuild the entire app with one command.
