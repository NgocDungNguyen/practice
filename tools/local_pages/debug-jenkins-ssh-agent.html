🧯 Debug Log: Jenkins SSH Agent Failure

A real debugging session: the DockerTest job died with [ssh-agent] Unable to start agent before reaching any build step. How the investigation went from a wrong first hypothesis to a one-line root cause in config.xml — and what it teaches about debugging services.

💥 The failure

What broke

The Week 6 pipeline job (Jenkins builds the WAR, then scps it to the Docker EC2 as dockeradmin) failed instantly — before checkout, before any shell step ran.

FATAL: [ssh-agent] Unable to start agent
java.lang.IllegalArgumentException:
  Not an ssh-agent executable path
  (filename must be ssh-agent(.exe))
    at ...ExecRemoteAgent.toSSHAgentPath

Remember: the stack trace names the exact class and method that threw — that is a map, not noise. toSSHAgentPath only validates a path string.

Why it fails this early

The job had Build Environment → SSH Agent ticked, so Jenkins tries to launch a real ssh-agent process on the controller before anything else. If that wrapper throws, nothing after it — checkout, build, deploy — ever runs.

Build Environment wrappers   → run FIRST
SCM checkout                 → never reached
Build / post-build (scp)     → never reached

Use when: a build dies with zero build output — check the wrappers before suspecting your own script, key, or network.

Note: at this point nothing about the SSH key, the Docker host's IP, or StrictHostKeyChecking had been reached — chasing those first would have been wasted time.

🔍 The investigation, step by step

Hypothesis 1: the binary is missing — wrong

"Not an ssh-agent executable path" reads like openssh-clients was never installed. Checking as root found the binary just fine — which disproves nothing, because root's login shell is not the Jenkins process.

which ssh-agent
# /usr/bin/ssh-agent   ← exists, but this is ROOT's PATH

Remember: a service resolves commands from the environment of its own process, not from whatever shell you happen to be debugging in.

Hypothesis 2: Jenkins has a broken PATH — also wrong

So check the environment the Jenkins JVM actually sees: once as the jenkins user, and once by reading the live process's environment straight from /proc.

sudo -u jenkins -s /bin/bash -c 'echo $PATH; which ssh-agent'
# /usr/bin/ssh-agent  ✓

sudo tr '\0' '\n' < /proc/$(pgrep -f jenkins.war | head -1)/environ \
    | grep '^PATH='
# PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin  ✓

Use when: any "command not found"-shaped error from a systemd service — /proc/<pid>/environ is the ground truth for what a running process inherited.

Step 3: stop guessing, read the configuration

PATH was fine and the binary existed, so the plugin had to be rejecting something it was given. Two greps: the plugin version, and what the job actually stored for the wrapper.

grep -i '^Plugin-Version' \
  /var/lib/jenkins/plugins/ssh-agent/META-INF/MANIFEST.MF
# Plugin-Version: 416.v4d76015a_5d68

grep -i -A8 sshagent /var/lib/jenkins/jobs/DockerTest/config.xml

Remember: every Jenkins job is a readable XML file under /var/lib/jenkins/jobs/<name>/config.xml — what the UI saved is often more honest than what the UI shows.

The smoking gun

The job's wrapper config contained one suspicious line: an executable field that was present but empty.

<com...sshagent.SSHAgentBuildWrapper plugin="ssh-agent@416...">
  <credentialIds>
    <string>dockeradmin-key</string>
  </credentialIds>
  <ignoreMissing>false</ignoreMissing>
  <timeout>1</timeout>
  <executable></executable>   <!-- ← the bug -->
</com...sshagent.SSHAgentBuildWrapper>

Remember: "present but empty" and "absent" are different states to a program — <executable></executable> deserializes to "", not to "unset".

🎯 Root cause and fix

Root cause

SSH Agent plugin 416 added an optional "Executable" override. Saving the job with the field blank serialized <executable></executable>, and the plugin treats the empty string as a configured path rather than "use the PATH". An empty string has no filename, so the ssh-agent(.exe) filename check throws.

""  →  toSSHAgentPath("")  →  no filename
    →  IllegalArgumentException
# PATH, binary, credentials: all irrelevant

Remember: the error message pointed at the executable path all along — the misleading part was assuming the path came from PATH lookup instead of configuration.

The durable fix

Set the field explicitly so there is nothing ambiguous left to deserialize: job → Configure → Build Environment → SSH Agent → Advanced → Executable.

/usr/bin/ssh-agent

Use when: fixing it for good. Deleting the empty element from config.xml and reloading also works, but re-saving the job in the UI with a blank field brings the bug straight back.

Checkpoint: after setting the executable and re-running, the wrapper starts the agent, checkout proceeds, and the post-build scp is finally reached.

Important: spotted during the session — the job targeted dockeradmin@172.31.26.68 while an earlier screenshot used ...17.236. Make sure the address is your Docker EC2's current private IP, and use the same one in any manual ssh test.

🧠 Lessons worth keeping

The plugin was optional all along

The lab's deploy step is a plain scp in an Execute-shell block. That needs no wrapper — only a key pair owned by the jenkins user, trusted by dockeradmin on the Docker host, verified by hand before touching Jenkins.

sudo -u jenkins -s /bin/bash
ssh-keygen -t rsa -b 2048 -N '' -f ~/.ssh/id_rsa
cat ~/.ssh/id_rsa.pub   # → append to dockeradmin's authorized_keys

sudo -u jenkins ssh -o StrictHostKeyChecking=no \
  dockeradmin@<docker-private-ip> hostname   # must print the host

Use when: a plugin is fighting you and the underlying task is one command — removing the moving part is a legitimate fix.

Debugging habits this session proves

Each step of the investigation is a reusable move — the same sequence applies to almost any "service can't find X" failure.

1. Read the stack trace: WHICH class/method threw?
2. Wrappers run first — zero build output means
   the failure is before your code
3. root's shell ≠ the service's environment
4. /proc/<pid>/environ = what the process REALLY sees
5. When env checks out, read the stored CONFIG
6. "Empty" and "unset" are not the same value

Tip: two hypotheses were tested and disproven with evidence before the config was read — cheap checks first, but never stop at "looks fine".

Security: never load root's private key into Jenkins credentials because it was the one lying around — generate a dedicated key pair for the jenkins user so it can be rotated or revoked without touching root.
