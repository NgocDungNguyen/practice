🔑 SSH Keys & GitHub Private Repos

Everything key-related in one place: how key-pair auth actually works, generating and protecting keys, connecting to GitHub over SSH, getting Jenkins into private repos with a PAT or an SSH key, server-to-server access, and what to check when it all says Permission denied.

🧠 How key-pair auth works

Two files, one rule

A key pair is two matching files. The private key proves who you are and never leaves the machine it was made on; the public key is safe to hand out and gets copied to whatever you want to log in to.

~/.ssh/id_rsa       # PRIVATE — stays put, never shared
~/.ssh/id_rsa.pub   # PUBLIC  — copy to GitHub / servers

# who holds what:
GitHub account      ← your public key
remote server       ← your public key (in authorized_keys)
Jenkins credential  ← a private key (its own, dedicated)

Remember: if you are ever pasting a private key somewhere, stop and ask why — the only legitimate case in this course is the Jenkins credential store.

Who is authenticating to whom

Every SSH problem gets easier once you name the two ends. The course uses three distinct pairs — do not reuse one key for everything.

you        → EC2        : AWS .pem key (downloaded once)
you        → GitHub     : your laptop's key pair
jenkins    → GitHub     : the jenkins user's key pair
jenkins    → docker EC2 : the jenkins user's key pair
                          (public half in dockeradmin's
                           authorized_keys)

Remember: the identity that runs the command owns the key. Jenkins jobs run as the jenkins user — your keys and root's keys are invisible to it.

Security: a leaked private key is a leaked identity. Never commit one to a repository, never paste one into chat or a wiki, and give each machine/service its own pair so any single key can be revoked without breaking everything else.

🧰 Generate and protect keys

Generate a pair (the Week 3 way)

One command, two Enters (default location, no passphrase for lab use). The comment just labels the key so you can recognise it later on GitHub.

ssh-keygen -t rsa -b 4096 -C "your_email@example.com"
ls -l ~/.ssh/          # id_rsa + id_rsa.pub
cat ~/.ssh/id_rsa.pub  # the shareable half

Use when: any machine or service user needs its own identity — run it as that user, on that machine.

Permissions: SSH refuses sloppy keys

SSH will silently ignore (or loudly reject) keys other users can read. These are the numbers that matter, including the AWS .pem rule from Week 3.

chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_rsa ~/.ssh/authorized_keys
chmod 400 devops_project_key.pem   # AWS key, read-only
# symptom of getting this wrong:
# "WARNING: UNPROTECTED PRIVATE KEY FILE!"

Remember: 7-0-0 on the directory, 6-0-0 (or 400) on the files. "Permissions are too open" is a refusal, not a warning.

ssh-agent: type the passphrase once

If a key has a passphrase, the agent holds it unlocked for your session. (This is the same ssh-agent the Jenkins plugin from the debug log tries to launch.)

eval "$(ssh-agent -s)"   # start the agent
ssh-add ~/.ssh/id_rsa    # load the key
ssh-add -l               # list what is loaded

Use when: Git keeps prompting for a passphrase, or a tool needs key auth without interactive prompts.

Note: lab keys skip the passphrase for convenience. On anything real, set one — it is the difference between "stolen file" and "stolen identity".

🐙 GitHub over SSH from your machine

Register the key, then prove it

GitHub gets your public key: Settings → SSH and GPG keys → New SSH key, paste, save. Then test before touching any repo.

cat ~/.ssh/id_rsa.pub    # copy this to GitHub
ssh -T git@github.com
# "Hi ! You've successfully authenticated,
#  but GitHub does not provide shell access."

Use when: that greeting is the checkpoint — if ssh -T fails, no git clone will succeed either, so always test here first.

SSH remotes vs HTTPS remotes

The URL scheme decides the auth method. HTTPS URLs ask for username + token; SSH URLs use your key silently. Switching an existing clone is one command.

git clone git@github.com:<user>/<repo>.git   # SSH form

git remote -v                                # what am I using?
git remote set-url origin git@github.com:<user>/<repo>.git

Remember: git@github.com: (colon) = SSH; https://github.com/ = HTTPS. Half of all "it keeps asking for a password" problems are just the wrong remote form.

Checkpoint: ssh -T git@github.com greets you by username, and git clone of your private repo works with the git@github.com: URL and no password prompt.

🎫 Private repos over HTTPS: the PAT

Generate the token (Week 5, Challenge 2)

A classic Personal Access Token stands in for your password over HTTPS. GitHub: Settings → Developer settings → Personal access tokens → Tokens (classic) → Generate new token, with the scopes the lab lists.

repo             # full control of private repositories
admin:repo_hook  # read repo webhooks (Challenge 1 tie-in)
delete_repo      # delete repositories

Remember: the token is shown once — copy it immediately. Treat it exactly like a password, because to Git it is one.

Give the PAT to Jenkins

Manage Jenkins → Credentials → System → Global credentials → Add Credentials. Then any job whose Git URL is the HTTPS form can select this credential.

Kind     : Username with password
Username : your GitHub username
Password : the PAT (not your real password)
ID       : github-pat        # recognisable name

Job → SCM → Repository URL:
https://github.com/<user>/<private-repo>.git
Credentials: github-pat

Use when: the job clones over HTTPS. If the repo URL starts with git@, this credential type is the wrong one — that is the SSH section below.

Security: never bake a PAT into a repo URL, a script, or a Dockerfile — anyone who can read the job config or build log can read the token. The Jenkins credential store exists precisely so the token appears nowhere in plain text.

🤵 Private repos in Jenkins over SSH

1 · A key pair for the Jenkins server (Challenge 3)

SSH into the Jenkins EC2 and generate the pair there — this key belongs to the Jenkins box, not to you. Public half goes to GitHub like before.

ssh-keygen -t rsa -b 4096 -C "jenkins@your-company.com"
# Enter, Enter (default path ~/.ssh/id_rsa, no passphrase)
cat ~/.ssh/id_rsa.pub    # → GitHub → Settings → SSH keys

Tip: for a course lab this works from your login user's home; the strictest version generates it as the jenkins service user (sudo -u jenkins ssh-keygen ...) so ownership matches the process that will use it.

2 · The private key becomes a Jenkins credential

Manage Jenkins → Credentials → Global → Add Credentials, and this time the kind is the SSH one.

Kind        : SSH Username with Private Key
Username    : git                # GitHub's SSH user is always "git"
Private Key : Enter directly → paste output of: cat ~/.ssh/id_rsa
ID          : ssh-key-github
Description : SSH key for GitHub

Remember: username git, not your GitHub name — the SSH URL is git@github.com:..., so the SSH user is git and the key itself identifies your account.

3 · Host key verification + the job

First connections to a brand-new host trigger the authenticity prompt; a headless Jenkins cannot answer it. Tell Jenkins how to handle GitHub's host key, then point the job at the SSH URL.

Manage Jenkins → Security →
  Git Host Key Verification Configuration
  → "Accept first connection"

Job → SCM → Repository URL:
git@github.com:<user>/<private-repo>.git
Credentials: ssh-key-github

Use when: the build fails with "Host key verification failed" even though the credential is correct — this setting, not the key, is the fix.

Checkpoint: a job pointed at git@github.com:<user>/<private-repo>.git with the ssh-key-github credential clones successfully — check the build's console output for the checkout step.

🖥️ Server-to-server: Jenkins → another EC2

The authorized_keys pattern

Same idea, no GitHub in the middle: the calling machine's public key goes into the receiving user's ~/.ssh/authorized_keys. This is how the Week 6 job scps the WAR to the Docker host as dockeradmin.

# on the Jenkins EC2, as the user that will connect:
sudo -u jenkins -s /bin/bash
ssh-keygen -t rsa -b 2048 -N '' -f ~/.ssh/id_rsa
cat ~/.ssh/id_rsa.pub

# on the Docker EC2, as dockeradmin:
echo "<that public key>" >> ~/.ssh/authorized_keys
chmod 700 ~/.ssh && chmod 600 ~/.ssh/authorized_keys

Remember: generate as jenkins, authorize on dockeradmin — caller's public key, receiver's authorized_keys. Getting the direction backwards is the classic mistake.

Prove it by hand before wiring Jenkins

One manual command as the service user settles whether the key setup works — before any plugin, wrapper, or job config can confuse the picture.

sudo -u jenkins ssh -o StrictHostKeyChecking=no \
    dockeradmin@<docker-private-ip> hostname
# prints the Docker host's name → keys are correct
# now a post-build "Execute shell" scp will work too

Use when: always — if this works and the Jenkins job still fails, the problem is job configuration, not SSH (see the SSH Agent debug log for exactly that situation).

Note: use the Docker EC2's private IP when both instances share a VPC — it survives stop/start, and the traffic never leaves the network.

🚑 When it breaks: the checklist

"Permission denied (publickey)"

The server never saw an acceptable key. Work the list in order — it is almost always one of these four.

1. right key?   ssh -i ~/.ssh/id_rsa user@host
2. right USER?  ec2-user vs root vs dockeradmin
3. permissions? chmod 700 ~/.ssh; chmod 600 keys
4. is the pub key actually in the server's
   ~/.ssh/authorized_keys — of THAT user?
# see everything SSH tried:
ssh -vT git@github.com

Use when: any publickey rejection — -v shows which keys were offered and which were refused, turning guesswork into reading.

Other classics, fast

Each of these has one specific cause — recognising the message is most of the fix.

"Host key verification failed"
  → first contact prompt unanswered; in Jenkins set
    Git Host Key Verification → Accept first connection

"UNPROTECTED PRIVATE KEY FILE"
  → chmod 400 the .pem / 600 the id_rsa

asks for a password on git push
  → remote is the HTTPS URL; set-url to git@github.com:

"Not an ssh-agent executable path"
  → the plugin's empty Executable field, not your key

Remember: the last one has its own full write-up — the Jenkins SSH Agent debug log on this shelf.

Question: ssh -T git@github.com greets you fine, but the Jenkins job cloning the same repo fails with publickey denied. Whose key did you test, and whose key does the job use? That distinction is the whole answer — explain it before peeking at the "who is authenticating to whom" card above.
